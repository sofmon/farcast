# FarSight CLI — `farcast`

> The operator's command line for FarCast — install instances, run repositories, watch costs.

`farcast` is the command line face of [FarSight](../README.md), the FarCast UX layer. The same "farcast" product provides a GUI (the app world map; on macOS the app is to bundle this CLI), a server (tile registry, sessions and layout state inside an instance), and this CLI. The CLI is what operators and automation use to provision instances, deploy repositories, connect through FatLine, and monitor spending.

This document specifies the CLI phase by phase — the scaffold (1.1) and each command landed since: `install` (1.3), `release` (1.4), and `connect` + `redeploy` (2.3). **Phase 1.1 — the CLI scaffold** (implemented): the command framework, the two commands that work from day one (`version`, `help`), local configuration handling, and the human/JSON output model. **Phase 1.3 — `farcast install`** (implemented): the first command that does real, billable work — interactively provisioning a cloud instance through Planck under a mandatory cost limit. The scaffold is what makes `install` a small, uniform addition.

> **Status.** **Phase 1.1 (scaffold) — implemented** (`go test -race`, `go vet`, and `golangci-lint` all clean): argument parsing and subcommand routing, `farcast version`, `farcast help`, local config file handling, and human + JSON output formatting. **Phase 1.3 (`farcast install`) — implemented** (`go test -race`, `go vet`, `golangci-lint` all clean): interactive provisioning through [Planck](../../planck/README.md), a mandatory cost limit, a management-API + DNS-endpoint health check, the instance's own container image registry ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)), and record-before-create local persistence of instance metadata + credentials + kubeconfig. **Phase 1.4 (`farcast release`) — implemented** (`go test -race`, `go vet`, `golangci-lint` all clean): the destructive counterpart that tears the cluster down through Planck, deletes the instance's registry with it, and removes local state, initiating the cloud delete before removing the record so a failed delete call never strands billable infrastructure (deletion completes asynchronously — see the 1.4 known limitation). **Phase 2.3 (`farcast connect`) — implemented** (`go test -race`, `go vet`, `golangci-lint` all clean): it mints the per-instance mTLS identity (CA key kept local), re-ensures the instance's registry and sources FatLine's image from it — putting that image there itself, with **no container engine on the operator's machine** ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)); since [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M1 (built 2026-11-13, walked 2026-11-14) a release farcast pushes the images it carries, and a farcast checkout is needed only for `--source` or a farcast built from source; a release farcast is built by `farcast-release` on the pinned base's three documents under `internal/image/base/`, and `./check.sh` checks that its builds are byte-identical on the dev Mac (the second-host gate has not run) — bootstrap-deploys FatLine via kubectl **pinned to the image's digest** ([ADR 0006](../../docs/adr/0006-connect-bootstrap-kubectl.md)), provisions its public mTLS load-balancer carrier under a cost-confirmation gate ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)), dials the tunnel, and reports status. The orchestration is unit-tested against a fake cluster runner, a fake registry provider, a fake image builder and an injected tunnel dial; the real public-NLB path is `//go:build integration`, never run by `./check.sh` (cost pillar), as is the one test that pulls from a real public registry. **`farcast redeploy` — implemented** (same clean bar): the operational counterpart to the bootstrap — it re-renders and re-applies FatLine's workload for an already-connected instance, resolving the image through the *same* code `connect` uses, so a FatLine security fix rolls out without `release` and a reinstall; it never re-provisions the carrier and never re-mints the CA, and it re-applies even when the digest is unchanged (the failure it was built for lived in the workload template, not the image). Every remaining command is **registered but stubbed** — it appears in `help` and routes correctly, but exits non-zero with a "not yet implemented" message naming its [`PLAN.md`](../../PLAN.md) phase (`run`/`ps`/`logs`/`costs` → 4.3, and so on).

## What the CLI is — and isn't

**It is** the operator-side client. It runs on a laptop or in CI, holds the operator's cloud credentials locally, and drives instances. It is deliberately small, dependency-light, and secure by construction — it handles cloud admin credentials, so its supply-chain surface is a security concern, not just a packaging one.

**It is not** the [farcast SDK](../../sdk/go/README.md). The SDK is the syscall surface for applications running *inside* an instance; the CLI is the operator tool *outside* it. They do not share code and the CLI does not import the SDK. The two meet only on the wire — the CLI talks to a running instance through FatLine, in later phases.

**It is not** the GUI or the server. Those are separate FarSight components: the native client (Phase 7, [ADR 0021](../../docs/adr/0021-farsight-native-client.md)) and the Go server (later). The CLI is a standalone Go binary now. The macOS app will bundle it and drive it, once the CLI has the consent protocol ADR 0021 decision 6 requires (`--plan` and `--confirm <digest>`, never a bare `--yes`). *(2026-11-16: [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.6 is begun. `kernel confirm`, `kernel meter` and `reader grant`, and since 2026-11-17 `connect`, `redeploy`, `build`, `kernel deploy`, `storage deploy`, `storage key pin` and `storage key rotate`, take `--plan` and `--confirm <digest>` ([plans and confirmation](#plans-and-confirmation)), built and not walked. No other command does yet: on the others, `run` among them, `--plan` is an unknown flag. The gated commands that write only to Google or to this machine, such as `install` and `release`, wait for ADR 0021 step 3. Progress events are not built.)*

## Design principles

1. **Minimal dependencies, for security.** The CLI stores cloud admin credentials. Every third-party dependency is attack surface against those credentials, so the scaffold is built on the Go standard library (plus the already-vendored YAML library for config) — and every surface added since has held that line: the container-image path added at 2.3 is standard library end to end and grew the vendored module count by nothing. See [Decisions](#decisions) for the CLI-framework choice this implies.
2. **Results and diagnostics are separate streams.** Command *results* go to **stdout** (human text or JSON, per `--output`). *Diagnostics* go to **stderr** (and only when `--verbose`). A caller can always `farcast … --output json | jq` without log noise on stdout.
3. **Every command is scriptable.** Anything a command prints in human mode it can also emit as JSON, so the CLI is automation-first. Exit codes are meaningful.
4. **Secure local state by construction.** The config directory is `0700`, credential files are `0600`, and the CLI refuses (or repairs, with a warning) state that is more permissive. Credentials never leave the operator's machine except through an explicit, declared channel.
5. **The structure precedes the features.** 1.1 builds the routing, output, and config machinery so that every later command is a small, uniform addition — register a `Command`, return a typed result, done.

## Module & build

Per the repository convention ([AGENTS.md](../../AGENTS.md) → "Conventions"), FarCast is a **single Go module** rooted at `github.com/sofmon/farcast`; only `sdk/go/` is separate. The CLI is therefore part of the root module:

- **Binary:** `farcast`
- **Entry point:** `github.com/sofmon/farcast/farsight/cli/cmd/farcast`
- **Packages:** `github.com/sofmon/farcast/farsight/cli/internal/...`

> **Note (cleanup, done).** The stray per-module `go.mod` files — this one plus the seven other unimplemented modules — have been removed, so every package except `sdk/go` now lives in the root module per the single-module convention. Only `go.mod` (root) and `sdk/go/go.mod` remain.

**A developer build** (from the repository root):

```bash
go build -o farcast ./farsight/cli/cmd/farcast
```

It carries no components. With no `--source`, and no operator or development build recorded for the instance to keep, it compiles each of FarCast's own images from the farcast checkout it finds and deploys it, whatever is deployed now (a release's image included), after its build confirmation, which `--yes` answers; it records the image as a development build ([below](#where-fatlines-image-comes-from-adr-0007)). The version-skew guard and `--embedded` apply only to a farcast that carries components. Its version comes from the VCS data Go embeds (`runtime/debug.ReadBuildInfo`), then `dev`; a version, commit and date can still be stamped with `-X …/internal/buildinfo.Version=…` (and `Commit`, `Date`), but a farcast whose version is `dev`, carries `+dirty`, or was built from a modified tree never pushes components it carries.

**A release** is built with the release tool, `farcast-release` ([ADR 0023](../../docs/adr/0023-one-download-farcast.md) decision 4, M1), from a clean commit and with exactly the Go that go.mod's `toolchain` line names:

```bash
GOTOOLCHAIN=go1.27.4 go run ./farsight/cli/cmd/farcast-release build -out <new empty dir outside the checkout>
```

It compiles the four components (fatline, shrike, technocore, datasphered) for linux/amd64 with one recipe (`-trimpath -mod=vendor -buildvcs=false "-ldflags=-s -w"`, an environment built from an allowlist), packs each into a deterministic gzip layer, assembles each image on the digest-pinned distroless base's three documents, committed under `internal/image/base/` (fetched 2026-11-13 anonymously from gcr.io and checked against `BaseImage`'s digest chain; a base bump is `farcast-release base -write`, reviewed and committed), and writes the layers and a digest table. It then builds `farcast` for `darwin/arm64`, `darwin/amd64`, `linux/amd64` and `linux/arm64` (`-targets` chooses; `windows/amd64` is allowed and untested), with the layers and the table embedded through `go build -overlay` under the build tag `farcast_embedded`, stamped by Go itself (`-buildvcs=true`, no `-X`). It refuses another Go, a tree with uncommitted changes (`-allow-dirty` builds one whose components refuse to push) and an output directory inside the checkout. The output:

```
<out>/components/{datasphered,fatline,shrike,technocore}   the four binaries
<out>/layers/{…}.tar.gz, <out>/layers/digests.json          the layers, and the table farcast carries
<out>/farcast-<goos>-<goarch>                               farcast, with them embedded
<out>/THIRD_PARTY_NOTICES                                   the licences of the Go runtime and the 31 vendored modules
<out>/SHA256SUMS                                            every file above, sorted (not signed: signing is ADR 0023 M4/M5)
<out>/overlay.json                                          the go build -overlay map farcast was linked with (absolute paths; not in SHA256SUMS)
```

**Verifying a release without trusting it.** `shasum -a 256 -c SHA256SUMS`; `tar -xzf layers/fatline.tar.gz` gives `fatline` (mode 0755, mtime 0), whose sha256 is the table's `binary_sha256`; rebuild at the same commit with the command above, from a full clone with the release's tags, and `diff` the two `SHA256SUMS` files (the `farcast-*` lines depend on the tags, because Go stamps farcast's version from them; the components and layers do not); and `go version -m farcast-…` shows `-tags=farcast_embedded`, `vcs.revision` and `vcs.modified=false` without running it. `farcast version` prints each component's Go and digests, but a binary's own output proves nothing about itself. `./check.sh` step 3b rebuilds the components, layers and the Linux farcast three times and requires identical bytes; a second host OS is an operator step ([runbook](../../docs/runbooks/adr-0023-m1-walk.md), R0), not yet run.

**Go.** go.mod's `toolchain` line (`go1.27.4`) is the exact Go FarCast's components and release executables are built with, and the minimum Go for a source build; its `go 1.26` line is unchanged. `./check.sh` runs under exactly that release, `gofmt` included, and when it is not in the module cache it stops and prints the one command that fetches it, checked against sum.golang.org. `--source` and a source build's fallback use the Go on `PATH` — a plain install, Homebrew, or a version manager's shim, which is asked where its `GOROOT` is — never download a toolchain, and refuse a Go older than the checkout's `toolchain` line. A release farcast needs no Go at all.


### Releases and Go security releases

A release freezes the Go standard library inside FatLine (mutual TLS on a public load balancer), Shrike, TechnoCore and the keyholder at that release's patch level ([ADR 0023](../../docs/adr/0023-one-download-farcast.md) decision 6). So:

- **Each component's Go is shown.** `farcast version` prints the Go release and digests of each component a farcast carries, and `farcast world` carries the Go of each component's deployed image as `go`, from this machine's record of where it came from.
- **FarCast never phones home.** There is no updater, feed or in-app check, so the operator watches Go's own release announcements.
- **Sofmon re-releases within N days of a Go security release that touches a linked package.** N is not yet set.
- **`--source` is the operator's own patch path.** It builds a component with the Go on this machine and keeps it deployed until `--embedded` replaces it; every command that keeps it says which Go it carries and which Go this farcast carries.

### The process environment

`farcast` sets `GOOGLE_API_USE_CLIENT_CERTIFICATE=false` and unsets `GOOGLE_EXTERNAL_ACCOUNT_ALLOW_EXECUTABLES` in its own process before anything else runs ([ADR 0023](../../docs/adr/0023-one-download-farcast.md) decision 1, M0): the vendored Google libraries then never start a certificate provider or an executable credential source. The cost is stated there too: **an organization that enforces certificate-based access refuses this CLI.** `./check.sh` step 1b lists every place it can see where the shipped binaries can start a program, and compares that list with the reviewed `exec-allowlist.txt`, whose header states what the check cannot see.

Since ADR 0023 M2.3 (built 2026-11-14, with the first in-process cluster client), it also unsets three variables first: `GOOGLE_SDK_GO_LOGGING_LEVEL`, which would make a Google library built with no logger of its own log request and response bodies, a token among them, to stderr; and `SSL_CERT_FILE` and `SSL_CERT_DIR`, which would replace the roots a cluster's `*.gke.goog` endpoint and Google's APIs are trusted on (always on Linux; on macOS and Windows under `GODEBUG=x509sslcertoverrideplatform=1`). The cost: a private root this machine adds only through those variables, such as a TLS-inspecting proxy's, is not trusted by `farcast`.

### Global flags

| Flag | Default | Meaning |
|---|---|---|
| `-o`, `--output {human\|json}` | `human` | Format for command **results** on stdout. |
| `-v`, `--verbose` | off | Emit diagnostic logs on stderr. |
| `--config <dir>` | OS default | Override the config directory (also `FARCAST_CONFIG_HOME`). |
| `-h`, `--help` | — | Show help for `farcast` or the named command. |
| `--version` | — | Shorthand for `farcast version`. |

(The standard library `flag` package treats `-flag` and `--flag` as equivalent, so both spellings work. Bundled short flags like `-vo` are not supported — a deliberate, minor trade-off of staying on the standard library.)

A group's line is parsed with the flags of the first word that names one of its subcommands. A line where that word is a global flag's value placed between the group and its subcommand, such as `farcast kernel --config confirm meter …` with a config directory named `confirm`, is refused as a usage error that names both *(since 2026-11-16, ADR 0023 M2.6, built, not walked)*: it would otherwise run `meter` with `confirm`'s flags, and `meter`'s own `--plan` or `--confirm` would be read and ignored. Put global flags before the group or after the subcommand.

## Output model

**Two streams, never mixed:**

- **stdout** — command results. Human text by default; a single JSON value with `--output json`.
- **stderr** — diagnostics (text, only with `--verbose`) and error messages.

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Runtime error (the command ran but failed) |
| `2` | Usage error (unknown command, bad flag, missing argument) — no JSON envelope, in either mode |
| `3` | `keeper run --once` only: this device cannot keep the instance until a person acts (see [what a pass exits with](#what-a-pass-exits-with)) |
| `4` | `keeper run --once` only: the pass did not finish — a replica or the tunnel did not answer; the next pass retries |

**Errors** are formatted to match the mode: in human mode a `farcast: <message>` line on stderr; in JSON mode a `{"error":{"message":…,"code":…,"kind":…}}` object on stdout, so automation parses failures the same way it parses results. `kind` (since 2026-11-12) is one of a closed set — [Error kinds](#error-kinds) — and is additive: `message` and `code` are what they were. Exit `2` is the exception: a usage error, a flag that does not parse and an unknown command print prose on stderr and no envelope, in either mode.

**Text from the cluster is quoted when it could rewrite the terminal.** *(Since 2026-11-10.)* Some human output prints text that a cluster component, a tunnel peer or a repository's manifest chose: a route name, a refusal reason, a node or application name. Where it does, the CLI prints that text Go-quoted (`strconv.QuoteToGraphic`) whenever it holds a non-printing character or is not valid UTF-8. That catches an escape sequence, a carriage return or a bidi override. Otherwise the text prints as it is. This covers:
- `usage`: the tunnel table's peer, route and refusal reasons, application names, the monitor replica's name and the network error;
- `connect`: the relaying node and the allowlist;
- `run`: application names, and in its review the Containerfile, the build context and each declared host;
- `storage state`: the shared-node line and the scopes;
- `keeper run`: each replica's phase, boot label and reason, and the fleet's verdict.

It also covers every per-replica row of `storage state`, `storage unseal` and `storage seal` (error, phase, hold reason, key difference, key pin and note, and unseal's line on why the newest keys are not in use yet), the per-replica warnings a hand-over prints when a replica does not answer or refuses the keys, and error messages — which, being often several lines long, are not quoted whole: the `farcast: <message>` line keeps an error's line breaks and tabs and prints each other non-printing character as its Go escape in place (`\x1b`, `\r`, `\u202e`, and `\x9b` for a byte that is not UTF-8), so a keyholder's refusal text reads as text. `--output json` is unchanged and carries the text as it arrived, inside a JSON string.

## Configuration & credential storage

FarCast has **zero central dependency** ([AGENTS.md](../../AGENTS.md)): there is no account, no registry, no phone-home. All operator state lives locally.

**Location.** The config directory is resolved as, in order:

1. `--config <dir>` flag, else
2. `FARCAST_CONFIG_HOME` environment variable, else
3. `os.UserConfigDir()/farcast` — i.e. `~/Library/Application Support/farcast` (macOS), `~/.config/farcast` (Linux/XDG), `%AppData%\farcast` (Windows).

**On-disk layout** (schema fleshed out as the commands that own it land):

```
<config-dir>/                         (0700)
├── config.yaml                       (0600)  CLI preferences (default output, etc.)
└── instances/                        (0700)
    └── <instance-name>/              (0700)  one directory per installed instance
        ├── metadata.yaml             (0600)  non-secret: provider, project, region, cluster
        │                                      name + endpoint, status, cost limit, registry,
        │                                      timestamps
        ├── credentials.yaml          (0600)  secret: cloud provider credential (SA key JSON);
        │                                      since ADR 0023 M2.5 also the writing commands'
        │                                      cluster identity
        ├── kubeconfig.yaml           (0600)  secret: cluster-access kubeconfig; since ADR 0023
        │                                      M2.5 read only by kubectl, for the applies, until M2.7
        ├── reader.key                (0600)  secret: the reader identity's RSA key  (ADR 0023 M2.3)
        ├── reader.crt                (0600)  its self-signed certificate, the one Cloud Shell uploads
        ├── reader.key.next           (0600)  a rotated reader key and its certificate, until
        ├── reader.crt.next           (0600)  'reader record' switches to them
        ├── cluster-ca.crt            (0600)  a loopback (test) cluster's CA, which the rehearsal
        │                                      writes; beside a Google endpoint it is refused
        │                                      (ADR 0023 M2.4)
        └── datasphere/               (0700)  storage keys  (3.3)
            └── keys.yaml             (0600)  secret: the instance's DataSphere keyring —
                                               the one file whose loss is permanent, total
                                               loss of everything in the bucket
```

**Security.** Credentials are secrets the cloud provider would love and an attacker would love more:

- The directory is created `0700` and credential files `0600`. On load, the CLI checks permissions and **refuses to read** (or repairs, with a stderr warning) anything group/world-readable.
- Non-secret metadata is kept separate from secret credentials, so a command that only needs metadata never opens the credential file.
- Plaintext-at-rest with `0600` matches the baseline of `aws`/`gcloud`. Hardening — OS keychain integration, or encrypting credentials with an operator passphrase — is noted for a later phase, consistent with FarCast's security-first posture.

**Format.** YAML, via the already-vendored `github.com/goccy/go-yaml` (the same library the manifest parser uses), keeping the dependency set unchanged and the files operator-readable. See [Decisions](#decisions).

**Phase 1.1 delivered** the `config` package — path resolution, `0700`/`0600` enforcement, and typed load/save of `config.yaml`. **Phase 1.3 adds the instance store** above — typed `metadata.yaml` / `credentials.yaml` / `kubeconfig.yaml` per instance, created and written by [`farcast install`](#farcast-install--provision-an-instance-phase-13) under the same permission rules, with a write-ordering that keeps a cluster from ever existing un-recorded (see that section).

## `farcast install` — provision an instance (Phase 1.3)

`farcast install` turns "a cloud account + a cost limit" into "a running FarCast instance." It is the first command that does real, billable work: it provisions a managed Kubernetes cluster through [Planck](../../planck/README.md) ([GKE Autopilot](../../docs/adr/0003-gke-autopilot.md) today), gives the instance the container image registry it owns ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)), confirms the control plane is reachable, and records everything needed to operate and later tear the instance down — all under the strict local-state rules above.

It is **interactive by default** and **fully scriptable**: every prompt has a matching flag, so an operator can run it conversationally while automation runs it unattended.

### Flow

1. **Resolve inputs** from flags, then interactive prompts (human mode + TTY only) for whatever is missing. The mandatory cost limit is never defaulted, and since ADR 0023 M2.5 neither is `--credentials`.
2. **Select the provider** from those Planck has registered (`planck.Providers()`) — today just `gke`.
3. **Validate credentials** — `planck.Open` then `Validate`, before creating anything. Bad credentials fail here, fast and free.
4. **Confirm** — show a summary (provider, region, cluster name, cost limit) and require a yes. `--yes` skips it; it is required when non-interactive. This is the last step before money is spent.
5. **Record intent** — write `metadata.yaml` (status `provisioning`) and `credentials.yaml` *before* provisioning, so a cluster can never exist un-recorded.
6. **Provision** — `CreateCluster` blocks until the cluster is `RUNNING` (several minutes), with progress on stderr.
7. **Record the access path** — write `kubeconfig.yaml` and the cluster's endpoint into metadata.
8. **Ensure the registry** — create the instance's own image repository and grant its cluster pull access on it (see [The instance's registry](#the-instances-registry) below). A failure here is a **warning, not a failed install**: the cluster above is already billable, so aborting would strand it, and the next `farcast connect` re-ensures the registry anyway.
9. **Health check** — confirm the instance is alive via the GKE management API (`ClusterStatus == RUNNING`) plus the IAM-gated DNS endpoint; the control plane is private, so there is no public IP to dial ([ADR 0004](../../docs/adr/0004-private-control-plane.md)).
10. **Finalize** — update metadata to `running` (or `unreachable`), print the result.

### Command surface

```
farcast install [flags]
```

| Flag | Required | Meaning |
|---|---|---|
| `--name <name>` | yes | Instance name — the local-state key and the basis for the cluster name (`farcast-<name>`). DNS-label form. |
| `--provider <id>` | no | Cloud provider (default: the sole registered one, `gke`). |
| `--project <id>` | yes for `gke` | Cloud project (GCP project ID). |
| `--region <region>` | no | Cloud region (default: the provider's, `us-central1`). |
| `--credentials <path>` | **yes** | Path to a credential file (GCP service-account key JSON). Required since ADR 0023 M2.5 (built 2026-11-15): farcast reads an instance's cluster, and writes its storage key pin, as the service account whose key this names, never as Application Default Credentials. Missing in an unattended run, or left blank at the prompt, it is a usage error (exit `2`), before anything is created. So is a path naming a file that is empty, holds only white space (`/dev/null`, a key whose download failed) or is not a service-account key farcast uses: the file is parsed as the instance's writer will parse it, before the provider is opened, and no refusal quotes it. Planck reads an empty key as Application Default Credentials, so without this an empty file would install as this machine's ADC. *(Until M2.5, omitting it used Application Default Credentials. An instance installed that way is refused by the commands that write to the cluster, `credential_missing`: [who the writing commands run as](#who-the-writing-commands-run-as).)* |
| `--cost-limit <amount>` | **yes** | Monthly spend ceiling, in USD. **No default, no "unlimited" — install will not proceed without it.** Must be > 0. |
| `--yes`, `-y` | no | Skip the confirmation prompt; required when running non-interactively. |

Global flags (`--output`, `--verbose`, `--config`) apply as everywhere; with `--output json` the command prints one JSON result object and never prompts.

**Interactive vs. unattended.** The CLI prompts only when the session is interactive — human output mode *and* stdin is a terminal (detected via `os.ModeCharDevice`; no dependency). Otherwise every required value must come from a flag, `--yes` is required, and a missing value is a usage error (exit 2) rather than a hung prompt. Prompts go to **stderr** and answers are read from **stdin**, so stdout carries only the result and `farcast install … --output json | jq` stays clean.

### The mandatory cost limit

FarCast treats cost control as a safeguard, not a dashboard ([root README](../../README.md#cost-control)). `install` enforces this at the one point where it is structural — the moment the instance is created:

- **No default and no skip.** Omitting `--cost-limit` unattended is a usage error; interactively, the prompt repeats until a valid positive amount is given.
- The limit is persisted in `metadata.yaml`. **Enforcement belongs to TechnoCore** ([phase 4.1](../../technocore/README.md)); 1.3 *captures and persists* the ceiling so the enforcement loop and every cost-aware command have an authoritative value to read. Recording it at install time is what makes "no instance without a limit" a property of the system rather than a habit.
- **A limit below the instance floor is flagged where the number is chosen.** An instance costs something standing still — the Autopilot cluster's own managed workloads, the load-balancer carrier, and the system tier's Pods — so a limit under that total is one TechnoCore would reach before a single application ran, and could not fix, because it never stops the tunnel or the key holder. `install` prints the breakdown against the **fully provisioned** floor rather than what happens to be deployed at that moment: an instance installed today runs almost nothing, and checking against *that* would pass a figure the operator is guaranteed to breach two commands later. It warns rather than refuses — the figures model a published rate card and the cluster line has never been checked against an invoice ([ADR 0009](../../docs/adr/0009-technocore-kernel-and-cost-metering.md) decisions 4 and 10) — and a deliberately low limit is legitimate for an instance meant to be torn down within the month.

For 1.3 the limit is a monthly USD amount (`{amount, currency: USD, period: monthly}` in metadata, with currency/period fixed); generalizing currency and window is a later refinement.

### Provisioning through Planck

`install` names no cloud. It blank-imports `planck/providers` (so adapters self-register), then drives the neutral interface:

```go
p, err := planck.Open(provider, planck.Config{Project: project, Location: region, Credentials: cred})
if err := p.Validate(ctx); err != nil { /* bad credentials — fail before creating */ }
cluster, err := p.CreateCluster(ctx, planck.ClusterSpec{Name: clusterName, Location: region, Labels: farcastLabels})
// blocks until RUNNING; cluster.Kubeconfig reaches the control plane
```

Cluster shape — Autopilot, node management, networking — is entirely Planck's concern; `install` supplies a name, a region, and FarCast resource labels and gets back a ready `*planck.Cluster`. Planck provisions a **private control plane** (no public IP; IAM-gated DNS-based endpoint — [ADR 0004](../../docs/adr/0004-private-control-plane.md)), so `Cluster.Endpoint` is a DNS FQDN and the kubeconfig targets it. `CreateCluster` is idempotent, so re-running after a partial failure resumes rather than duplicates. The cluster name is derived as `farcast-<instance>` and validated against the provider's rules before anything is created.

### The instance's registry

Kubernetes puts code into a Pod exactly one way — the kubelet pulls an image from a registry — so *some* registry is structural; the only question is whose. FarCast's answer is that the instance owns one ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)). Pulling FarCast's own images out of a feed Sofmon publishes would make every instance's security boundary depend on a third party's artifact server, which is exactly the phone-home shape the zero-central-dependency pillar rejects.

So `install` ensures a Docker-format repository named **`farcast-<instance>`** in the instance's own region and project — instance identity, like the cluster and the CA — and every image the instance ever runs is named from the prefix it yields:

```
prefix:   us-central1-docker.pkg.dev/<project>/farcast-prod
FarCast:  <prefix>/system/fatline:<version>            ← FarCast's own images (2.3)
apps:     <prefix>/app/<deployment>/<app>:<git-sha>    ← application images (phase 4)
```

The `system/` prefix costs one path segment now and prevents both a rename migration later and an operator app named `fatline`. The ensure is **idempotent** — `connect` re-runs it defensively on every connect — and it is Planck's `RegistryProvider`, an *optional* provider capability, so a cloud whose adapter cannot host images is still a perfectly good provider for a cluster ([Planck](../../planck/README.md)).

**Pull access is an explicit, repository-scoped grant.** The ensure binds `roles/artifactregistry.reader` **on that one repository** to the cluster's node service account — today the project's default Compute Engine account, whose email Planck derives from the project *number* (the cluster object reports the account as the literal `default`). It is deliberately not a project-level grant: the node account is shared, so a project-scoped role would hand every workload in the project the instance's images. Nor does it lean on that account's automatic project `Editor` role, which is org-policy-conditional — a pull relying on it works by accident and breaks on a hardened project. The principal that was granted is recorded in metadata, so the grant is auditable from local state without opening a cloud console.

**The installer credential needs one role more than 1.3 asked for:** `roles/artifactregistry.admin` — the narrowest predefined role that can create repositories, covering repository create/delete and repository-level `setIamPolicy`, and nothing at project scope, so the CLI's credential never holds project-IAM power. It is a re-apply for operators who provisioned their service account earlier ([Phase 1 runbook](../../docs/runbooks/phase-1-validation.md)); without it the ensure fails with a permission error naming what is missing, and the install continues with a warning.

**Cost is surfaced, not gated.** Artifact Registry bills storage; FatLine's image is ~20 MB and same-region pulls are free, so the registry is effectively `~$0/mo` beside the ~$18/mo load balancer that *does* earn a confirmation gate ([`connect`](#farcast-connect--open-a-fatline-tunnel-phase-23)). `install` prints it as a line item and asks nothing — gating cents would train the operator to click through the gate that matters.

### Health check

"Basic health check confirms the instance is alive" (PLAN 1.3). `CreateCluster` already waits for `RUNNING`; the health check re-confirms it independently and verifies the operator's own access path. Because FarCast clusters have a **private control plane with no public IP** ([ADR 0004](../../docs/adr/0004-private-control-plane.md)), there is no public endpoint to dial directly — the operator reaches the API server through GKE's IAM-gated **DNS-based endpoint**. So the check is two cheap, dependency-free steps: (1) re-query the GKE **management API** for `ClusterStatus == RUNNING` (configuration-independent, always reachable), and (2) optionally make one IAM-authenticated request to the DNS endpoint to confirm the operator can reach the control plane.

A deeper check — API-server `/healthz`, FarCast components, workloads — needs the in-cluster components and TechnoCore and lands with them. If it fails, the cluster is **kept** (it is billable, and the failure may be transient networking): the instance is recorded `unreachable`, the operator is warned, and the command exits non-zero so automation notices.

### Local state & atomicity

`install` fills in the instance store from [Configuration & credential storage](#configuration--credential-storage). Because an un-recorded cluster is an untracked bill, it writes the local record **before** provisioning:

1. **Reserve** `instances/<name>/`; refuse if it already exists — no silent clobber (release first, or pick another name).
2. **Write** `credentials.yaml` and `metadata.yaml` with `status: provisioning`.
3. **`CreateCluster`.** On error, leave the record (`status: provisioning`/`error`), direct the operator to `farcast release <name>`, exit 1. That includes a cluster that does not read back as system-only logging: the GKE adapter refuses to return one ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md)).
4. **On success**, record `cloud_logging: system` only when the provider says it read the cluster back that way. Then write `kubeconfig.yaml`, ensure the instance's registry (a failure here is a warning, never an abort — the cluster is already billable), run the health check, then update `metadata.yaml` (`status: running` | `unreachable`, plus the endpoint and the registry).

So an interruption at any point — failure, `Ctrl-C` (the root context is cancelled on `SIGINT`), crash — always leaves a local record carrying the deterministic cluster name and the credentials, which `farcast release` (1.4) can act on. The metadata/credentials split means `release`, `costs`, and `ps` read non-secret metadata without ever opening a secret file.

### Output

Human:

```
✓ instance "prod" installed
  provider:    gke
  region:      us-central1
  cluster:     farcast-prod
  endpoint:    a1b2c3d4.us-central1.gke.goog
  registry:    us-central1-docker.pkg.dev/<project>/farcast-prod (instance images, ~$0/mo)
  cost limit:  USD 50.00 / monthly
  app logs:    kept on the cluster's nodes, configured not to be sent to the provider's logging
               (the provider's read-back; that it is honoured is unwalked, ADR 0019)
               (the provider still keeps its system logs, events, audit log and metrics)
  state:       running
  config:      ~/Library/Application Support/farcast/instances/prod
```

(The `registry` line is omitted when the provider has no registry capability, or when the ensure failed — in which case the warning naming why is already on stderr.)

The `app logs` line and `cloud_logging: system` record what the provider reported when the cluster's logging config was read back ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md)). They are the provider's word about its configuration. Whether Autopilot honours it is unwalked: the next walk counts the container log entries the provider actually received.

JSON (`--output json`) — a single object, the same data:

```json
{"name":"prod","provider":"gke","region":"us-central1","cluster":"farcast-prod","endpoint":"a1b2c3d4.us-central1.gke.goog","registry":"us-central1-docker.pkg.dev/<project>/farcast-prod","status":"running","cost_limit":{"amount":50,"currency":"USD","period":"monthly"},"cloud_logging":"system","config_path":"…/farcast/instances/prod"}
```

## `farcast release` — tear down an instance (Phase 1.4)

`farcast release <instance>` is the counterpart to [`install`](#farcast-install--provision-an-instance-phase-13): it destroys an instance's cloud resources and removes its local state. It is the one routinely **destructive** command, so it confirms deliberately and orders its steps so a failure never strands billable infrastructure.

### Flow

1. **Resolve the instance** — the positional `<instance>` argument; load its `metadata.yaml` and `credentials.yaml` from local state. An unknown instance is an error.
2. **Open the provider** — `planck.Open` with the *stored* provider, project, region, and credentials (the ones `install` recorded), so release needs no cloud flags beyond the name.
3. **Confirm** — show what will be destroyed and require confirmation (retype the instance name). `--yes` skips it; it is required when non-interactive. This is the point of no return.
4. **Mark deleting** — update `metadata.yaml` to `status: deleting`, so an interrupted release stays visible in local state.
5. **Destroy the cluster** — `DeleteCluster` waits until GKE reports the cluster gone, bounded at 15 minutes. In human output, `-y` included, stderr says so as it starts and then once a minute with the time waited — elapsed time only, never a claim about the cluster's state. *(Until 2026-11-10 a `-y` release printed nothing through the walk's six-minute wait.)* If the wait runs out, or is interrupted, the record is **kept** and release says the cluster is still being deleted and to re-run it — which then waits on the delete already running. Deleting an already-absent cluster succeeds (idempotent). *(Until 2026-10-08 it returned on the cloud's acceptance, and the record was gone while GKE still showed the cluster `STOPPING` — and billing.)*
6. **Destroy the registry** — delete the instance's image repository and everything in it ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)), *waiting* for the deletion to actually run (unlike the cluster's, it takes seconds). The cluster goes first because it is the expensive resource. Nothing sovereign is lost — every image in the repository is derivable from Git — while keeping it would leave billable storage nobody is watching. Deleting an absent repository succeeds, and a provider with no registry capability has nothing to delete.
7. **Retire a keeper on this machine** — a keeper installed here for this instance, whose CA is this instance's, has its bundle and leaf key wiped, and a request pending beside them; its ledger and record stay, because the ledger is the evidence an audit reads (`keeper status` shows it as wiped). A directory holding only a pending request is left and reported `untouched` — no certificate came back to prove which instance it was for — with `farcast keeper uninstall <instance>` to discard it. Keepers enrolled on other devices are named, with `farcast keeper uninstall <instance>` to run on each: release cannot reach them, and each still holds key material for an instance that no longer exists.
8. **Clean up local state** — remove the instance directory, only after both deletes have completed.

### Command surface

```
farcast release <instance> [flags]
```

| Flag | Meaning |
|---|---|
| `<instance>` | The instance name to release (positional, required). |
| `-y`, `--yes` | Skip the destructive confirmation; required when non-interactive. |

Global flags (`--output`, `--verbose`, `--config`) apply. With `--output json` the command prints one JSON result and never prompts. Release takes **no** cloud flags — provider, project, region, and credentials all come from the recorded instance.

### The confirmation

Destruction is irreversible, so the bar is higher than install's. Interactively, release prints a summary (instance, provider, region, cluster, and — when one is recorded — the image registry and every image in it) and asks the operator to **retype the instance name** to confirm; anything else aborts. `--yes` skips the prompt (and is required when stdin is not a terminal). This mirrors the "type the name to delete" pattern operators expect from destructive tooling.

### Order & idempotency

The danger in teardown is the inverse of install's: removing the local record before the cloud resources are gone would strand something **billable and now unfindable**. So release **initiates the cloud deletes first, then removes local state**:

1. Set `status: deleting` in `metadata.yaml`.
2. `DeleteCluster`. On error, **keep** the local record (status stays `deleting`), report the failure, and exit non-zero — the operator can re-run `release`.
3. `DeleteRegistry`, under the same discipline: on error the record is kept — the message says the cluster is destroyed and the registry is not — so a re-run has something to converge on.
4. On success, remove the instance directory.

Both deletes are idempotent (neither an absent cluster nor an absent repository is an error), so a `release` re-run after a partial failure — cluster already deleted, registry or local cleanup interrupted — simply succeeds and removes the lingering record. The registry is identified from the recorded repository name, falling back to the instance name and region, so an instance whose record predates registries still has the (idempotent) delete attempted against the right name. A `release` is therefore always safe to repeat, which is exactly what cleans up the orphaned *record* a failed `install` can leave behind (status `provisioning`/`error`). `DeleteCluster` waits for the delete to complete, so the record outlives the cluster rather than the other way round; a delete that fails after acceptance leaves the record, and the next `release` converges on it.

### Local cleanup & output

On success the instance directory (`metadata.yaml`, `credentials.yaml`, `kubeconfig.yaml`) is removed wholesale. For phase 1.4 there is no persistent storage to consider — the cluster is empty compute; data lifecycle arrives with DataSphere (phase 3).

Human:

```
✓ instance "prod" released
  provider:    gke
  cluster:     farcast-prod (deleted)
  registry:    farcast-prod (deleted)
  cloud logs:  kept by the provider; release cannot remove them — its audit log of this instance's
               API writes until about 2027-12-15, its system logs and events until about 2026-12-10 (default retention),
               its metrics about the instance's Pods (names, states, resource use) until about 2028-11-10
  state:       removed
```

JSON (`--output json`):

```json
{"name":"prod","provider":"gke","cluster":"farcast-prod","registry":"farcast-prod","cloud_logs":{"audit_log_until":"2027-12-15","system_logs_until":"2026-12-10","metrics_until":"2028-11-10","workload_logs":false},"status":"released"}
```

The `cloud logs` line is what outlives the instance in the provider's own logging and monitoring ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md)). Release reports it and deletes nothing there, because those records belong to the project, not to the instance. The dates are approximate. Audit entries expire 400 days after each write, and the system-log date assumes the project's default 30-day retention. Metric points expire 24 months after each sample, and only deleting the project guarantees they go sooner. The metrics cover Pod and container names, states (phase, readiness, waiting reasons) and resource use, and they are kept whatever the logging config was. An instance not recorded as `cloud_logging: system`, one installed before ADR 0019, also says its applications' output may be among the logs. In the JSON, `workload_logs: false` means only that the instance was recorded at install as *configured* to send the provider's logging system logs only, by the provider's own read-back. That is unwalked on Autopilot and is not an observation that no application output reached the provider ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md), Context); `true` means the instance was never recorded as configured that way.

The `registry` line and field name only what the instance was recorded as owning: the delete is still attempted for an instance whose record predates registries, but the report claims only what it knows.

The `reader` line appears only for an instance that records a reader identity (`farcast reader`, [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.3). Release deletes `reader.key` with the instance directory, but the account, its uploaded keys and its project-level `roles/container.clusterViewer` binding stay in Google. So the confirmation names the account, and the result prints the two Cloud Shell commands that delete it. The binding's removal comes first, because a binding to a deleted account is expected to stay in the project's policy; that is not verified. Every value in those commands is rebuilt from the record's checked name and project, never copied from the record, and single-quoted. When the record fails that check, the confirmation and the result say instead that the account `cannot be printed safely`, and name only `farcast-reader-` and 8 hex characters; release goes on. *(2026-11-16: `reader init` records the reader's email before any account exists, so `release` prints the two commands even when the Cloud Shell paste never created the account. It did so on the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md), where key upload was blocked. Run then, they are expected to fail with `not found`, which is harmless; running them was not recorded.)* In the JSON the field is `"reader":{"email":…,"cloud_shell":[…,…]}`, or `"reader":{"unprintable":…}` for a record that fails the check.

## `farcast connect` — open a FatLine tunnel (Phase 2.3)

`farcast connect <instance>` is where the operator's machine stops being a point of presence and the *instance* becomes one. It establishes the [FatLine](../../fatline/README.md) mutually-authenticated tunnel into a running instance, reports the boundary's status, and persists the operator's data-plane identity so every later command (`run`, `ps`, `logs`, …, phase 4.3) routes its instance traffic through FatLine rather than the public internet.

Unlike `install`/`release`, which drive the *control plane* (the Kubernetes API, over Google IAM), `connect` drives the *data plane*: FatLine, authenticated by FarCast's **own per-instance CA**, never Google IAM ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)). The two planes stay separate by design ([ADR 0004](../../docs/adr/0004-private-control-plane.md)).

The first `connect` to a fresh instance does a one-time **bootstrap**: mint the instance's mTLS identity, put FatLine's image into the registry the instance owns, deploy FatLine into the cluster, and provision its public point of presence. Subsequent connects reuse all of it and simply re-dial. Every step is idempotent, so an interrupted bootstrap is resumed, not duplicated.

### What it carries — the carrier ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md))

The default carrier is a **single public, mTLS-gated L4 passthrough load balancer** per instance (a GKE `Service{type: LoadBalancer}` fronting the FatLine Pod). Google forwards raw TCP and never terminates TLS, so the cloud carries **ciphertext + SNI only**; the entire boundary is FatLine's `RequireAndVerifyClientCert` — an unauthenticated peer with the IP gets a TCP connect and a `ClientHello`, then is dropped at certificate verification, before any byte is routed. It is a locked door on a public street.

That load balancer is a **standing ~$18/mo cost** (a real 30–50% bump on the ~$37–51/mo Autopilot baseline). Because cost control is a non-negotiable pillar, `connect` surfaces it and **requires confirmation** before provisioning — the same "last step before money is spent" gate as `install`. The carrier sits behind a thin, swappable seam (ADR 0005 invariant #4); the documented control-plane-port-forward fallback (A2) is a later binding against that seam, not a rewrite — `connect`'s mTLS identity and core are carrier-independent.

### Where FatLine's image comes from ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md))

A Deployment needs an image, and FarCast's answer to "from where" is **the registry the instance owns** — never one Sofmon publishes. What goes there, since [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M1 (built 2026-11-13; walked 2026-11-14), is the image **this farcast carries**: a release farcast holds the four components' layers and, compiled into it, the digest of every image they assemble into. Shrike, TechnoCore and the keyholder follow exactly the same rules below; only the flag names differ.

There is no central fallback: the `ghcr.io/sofmon/farcast/fatline` default of the earlier 2.3 cut is **deleted, not deprecated**. It made every instance's network boundary depend on an artifact feed a third party controls — a standing central dependency and a supply-chain injection point aimed at FatLine itself. Nothing is fetched from Sofmon at run time either: the layers are inside the executable the operator chose to run.

**The version tag holds only the carried image.** `connect` looks up `<prefix>/system/fatline:<version>` (e.g. `us-central1-docker.pkg.dev/<project>/farcast-prod/system/fatline:v0.1.0`):

- **It holds exactly the digest this farcast carries** → reused, with no push and no base pull, and deployed as `…/system/fatline@sha256:…`, **pinned by digest**. A Deployment that names a *tag* can be redirected by anyone who can write that tag; a digest cannot.
- **It is missing** → the carried image is pushed, with **no build confirmation**: it is part of the executable the operator chose to run, and pushing it changes nothing that is running. Before any upload the image is assembled from the carried layer on the pinned base and its manifest digest compared with the compiled-in one; the registry's echoed digest is compared again after.
- **It holds any other digest** → never deployed. A warning on stderr — always, `--output json` included — names both digests, and the carried image is pushed over the tag. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: under `connect --plan` and `redeploy --plan` the warning is a notice in the plan, and nothing is printed on stderr.)*

Only a literal miss counts as missing: a permission or network failure stops with the registry's own words attached.

**A farcast that must not push what it carries is refused before anything is asked or called.** A version of `dev`, one carrying `+dirty`, one built from a modified tree, components assembled against another base, or components built at another commit than the farcast that carries them (the digest table records the revision, and farcast's own build info records its) — each is refused before any prompt, before the registry is ensured and, except in `connect`, which has to read whether it will deploy at all, before the instance's record is read. A reconnect and `--status` deploy nothing and are never refused for it. `--source` deploys nothing carried, and so does `--technocore-image` or `--datasphered-image` on its own command, so none of them is refused for it. `--fatline-image` is: on `connect` and `redeploy` it names FatLine's image alone, and Shrike's would still come from the carried components, so such a farcast is refused there too, even when the registry is the thing that is broken. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: on `connect` and `redeploy` the refusal comes before any plan is made, under `--plan` too, with the same text and kind, `internal`; no plan is printed.)*

**Where an image came from is recorded.** `metadata.yaml` gains `system_images`, one entry per component: the digest-pinned image, its origin (`embedded`, `operator`, `development` or `named`), the Go that compiled it, the farcast version that pushed, built or named it, and for a build its time and checkout directory. It is valid only while it names the image the deploy record names, and an `embedded`, `operator` or `development` entry only when it is in this instance's registry — one naming another host is ignored, and said, so a local record can never send the registry credential elsewhere. An older farcast rewriting the record drops the field; the next command then deploys the carried image and says it does not know what it replaced.

**A release farcast replaces another farcast version's image only with `--embedded`** ([ADR 0021](../../docs/adr/0021-farsight-native-client.md) decision 6's version-skew guard, which ADR 0023 decision 4 keeps). When the record says another farcast version deployed a different carried or named image, a farcast that carries components refuses with kind `version_skew`, naming both farcast versions and both Go versions, and says when the replacement would put back an older Go. The same image from another version is no skew; its record is rewritten with this version. Every other replacement it makes is said on stderr: a development image, a named image, or one whose origin this machine does not record. A farcast built from source has no carried image to guard, so neither the guard nor `--embedded` applies to it ([below](#where-fatlines-image-comes-from-adr-0007)). *(Since ADR 0023 M2.6, built 2026-11-17, not walked: `connect` and `redeploy` decide both images before they ask anything, and refuse with `version_skew` then, before any question; `connect` used to refuse after its cost question. Their plans bind the replacement instead of refusing it, as the image fact's `replaces_other_version`, so a `--confirm` of a plan that lists it replaces the image, with or without `--embedded` ([plans and confirmation](#plans-and-confirmation)). `--yes` still never implies `--embedded`. Since M2.6c (built 2026-11-17, not walked) `kernel deploy` and `storage deploy` do the same: they decide their image before the cost question, and their plans bind the replacement (`TestConfirmCoversTheReplacementItsPlanListed`).)*

**`--source <dir>` is the operator's own patch path** (ADR 0023 decision 6). It compiles the image from that checkout with this machine's Go, pushes it under its own tag, `source-<first 12 hex of its manifest digest>`, so it never overwrites the version tag, and records it as `operator`-built with its Go, its time and the checkout. Later commands keep it — checking first that it is still in the registry, and naming both Go versions — until `--embedded` replaces it with the carried image, or `--source` builds again. A recorded operator build that has gone from the registry is an error naming `--source`, and on a release farcast `--embedded` as well.

**A farcast built from source** carries nothing. With no `--source`, and no operator or development build recorded for the instance to keep, it compiles the image from the checkout it finds (walking up from the working directory to the `go.mod` declaring `github.com/sofmon/farcast`, *past* `sdk/go`) and deploys it, whatever is deployed now (a release's image included), after its build confirmation, which `--yes` answers. It records the image as `development`, which only a source-built farcast keeps; a release farcast replaces it and says so. The version-skew guard and `--embedded` apply only to a farcast that carries components. Its version never names an image, so it looks no version tag up.

**Nothing in either path is a container engine.** Each image is a static Go binary on a digest-pinned distroless base with no `RUN` steps to execute: the binary packed into a deterministic tar layer, that layer appended to the base image pulled anonymously from gcr.io **by digest**, and the result pushed to the instance's registry. No docker, no podman, no daemon, no VM, and no credential left in any tool's store — the push credential is a ~60-minute access token minted in-process from the stored service-account key, used for the one command and dropped. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: deciding each image that its flag does not name mints one, used by its lookups (an explicit `--source` build looks nothing up but still mints it), and a push or a build mints its own when it runs, on every command that deploys a system image. A decision holds no secret, and a push can come after a question has waited longer than a token lives. So a command mints one more token than before for each image it pushes or builds.)* The independent check of the carried images is the release tool's rebuild ([Module & build](#module--build)); `fatline/Containerfile` is retired.

**What a build needs is `--source`'s, or a source build's:** a Go at or above go.mod's `toolchain` line on `PATH` and a farcast checkout. The compile runs `<GOROOT>/bin/go` with an environment built from an allowlist and refuses a binary not built by the recipe. A release farcast needs neither. With an image to build and no checkout, the command fails naming what it could not find, and that a release farcast would need none. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: that Go is asked for its path and version (`go env`, with `GOTOOLCHAIN=local`) when the image is decided, before any question, so under `--yes` too, on every command that builds a system image. Before, only the interactive build question asked it. A Go that cannot be asked is no refusal: the interactive question says so, as before, and a plan binds an empty Go.)*

**`--fatline-image` must be digest-pinned** (`repository@sha256:<64 hex>`), as `--technocore-image` and `--datasphered-image` already had to be. It is deployed exactly as given, with no lookup and no registry access, so the break-glass path still works when the registry is what is broken *(since ADR 0023 M2.6, built 2026-11-17, not walked: when the registry cannot be had at all, outside `--plan` and `--confirm`; a registry that is read but fails its ensure after consent refuses the command, [below](#the-bootstrap-flow))*; a tag is refused before anything is loaded, because the builder's push grant covers the whole instance repository and an application build could otherwise move a tag under `system/` that an operator had named. So is a value that is not a canonical `host/repository@sha256:…` reference — no host, no repository, or any whitespace — because it is written into the workload's YAML as given. It is recorded as `named`.

**`--fatline-image` names FatLine's image alone, so `--embedded` beside it governs Shrike's.** On `connect` and `redeploy` the pair is accepted: FatLine is deployed as given and never pushed, and Shrike's image is resolved by the rules above with `--embedded` given — the image this farcast carries, replacing an operator build or one another farcast version deployed, and said. Without `--embedded`, a Shrike that another farcast version deployed is refused with `version_skew`, naming Shrike, as it would be without `--fatline-image`. `--embedded` beside it needs the registry, which Shrike's image comes from: when the registry cannot be ensured the pair is refused before anything is applied or pushed, and the refusal says to drop `--embedded` to deploy FatLine alone. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: that refusal, and FatLine deployed alone without `--embedded`, hold when the registry cannot be had before consent: none recorded and its ensure failing, the installer's key refused, or the provider not opened. A recorded registry whose ensure fails after consent refuses the command with or without `--embedded`, `…; nothing was pushed or deployed`, and dropping `--embedded` does not deploy FatLine alone.)* On `kernel deploy` and `storage deploy` the image flag names the command's only component, so `--embedded` beside it is a usage error.

**The image flags apply to the first connect only.** A reconnect re-dials what is
already running; it renders and applies nothing. So `--fatline-image`,
`--source` or `--embedded` on an already-connected instance is refused with a usage error rather
than silently ignored — reporting success while the previous image kept serving
is the worst possible answer when the flag is being used to roll out a FatLine
fix. Changing what a connected instance runs is
[`farcast redeploy`](#farcast-redeploy--replace-a-connected-instances-fatline-workload-phase-23)'s
job, and the refusal names it: `connect` opens the tunnel, `redeploy` changes
what runs inside it.

**A registry failure stops only a connect that needs the registry.** `--status` does no registry work whatsoever — a health probe must not depend on it. A reconnect to an instance already running FatLine, or a connect carrying an explicit `--fatline-image` without `--embedded`, degrades a failed ensure to a stderr warning and carries on (the first connect then deploys FatLine without Shrike, and says so); that is what keeps an instance installed before ADR 0007 — whose stored installer credential predates `roles/artifactregistry.admin` — reconnectable. *(Since ADR 0023 M2.6, built 2026-11-17, not walked, a first connect takes the registry its record names, with the installer's key, before it asks anything, and ensures it only after consent ([the bootstrap flow](#the-bootstrap-flow)). So FatLine deploys alone, outside `--plan` and `--confirm` only, when the registry cannot be had that way: the key refused, the provider not opened, or, for a record that names no registry, the ensure made first failing. A token or a lookup that fails while Shrike's image is decided is an error, as it was. A plan that read the registry and decided Shrike's image is never cut down to FatLine alone: an ensure that fails after consent refuses the connect, `…; nothing was pushed or deployed`, in every mode. No plan deploys FatLine without Shrike. With `--fatline-image` and no `--embedded`, `--plan` and `--confirm` refuse when the registry cannot be read, with the failure's own kind: `--plan and --confirm never deploy FatLine without its Shrike monitor, and instance "<name>"'s image registry could not be read (<why>); deploying FatLine alone is a break-glass step: run the command without --plan or --confirm, interactively or with --yes`. A reconnect's plan is the ensure alone; under `--confirm`, an ensure that fails still prints the warning and the status, and then fails the command (*Its plan*, below).)*

### The bootstrap flow

*(Reordered by ADR 0023 M2.6, built 2026-11-17, not walked.)* A first connect decides everything before it asks anything, and writes only after: steps 2 to 4 read and decide, step 5 is the consent, and steps 6 to 12 do what was decided. *(2026-11-17: in an interactive or `--yes` run, the one write before the consent is step 3's ensure of a record that names no registry, which comes after step 2 has decided the identity.)* Until then the CA was minted and the registry ensured before the cost question, and the images were looked up and pushed after it. Under `--plan` the connect stops after step 4 and prints what it decided. Under `--confirm` it decides again, compares the result with the digest given, and goes on from step 6, asking nothing (*Its plan*, below).

1. **Resolve the instance** — load `metadata.yaml`, `credentials.yaml`, `kubeconfig.yaml`. An instance that was never `install`ed, or is not `running`, is an error directing the operator to `install` first.
   - **Open the writer and read once** *(since ADR 0023 M2.5, built 2026-11-15, not walked)*. The instance's writer opens from `credentials.yaml`, sending nothing. This machine is checked for what the applies below still need until M2.7, `kubectl` on its `PATH` and the instance's `kubeconfig.yaml`, running nothing. Then `farcast-system`'s uid is read in-process as the installer service account, a token mint and one read. All of this comes before the CA is minted or loaded, the registry ensured, the cost asked, or anything pushed or applied, so a refusal here changes nothing. A reconnect and `--status` skip it. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: `--plan` never opens the writer, and `--confirm` opens it, and reads, right after the comparison, before step 6.)* *(2026-11-16: the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md) sent this read as the installer's key. GKE's DNS endpoint answered 401 to farcast's token, scoped to `userinfo.email` alone, and 200 with `cloud-platform`. So at 2482810 this read is refused against GKE, and `connect` would stop here having changed nothing (inferred: `connect` itself was not run). The fix, built later that day, mints with `cloud-platform` and `userinfo.email`, exactly the pair the walk's read was answered 200 for; farcast's own read with it is not walked. A leaked writer token then works for every Google API the installer's IAM allows, not only the cluster.)*
2. **Decide the data-plane identity** — whether this connect mints the instance's identity (on first connect, when this machine holds none) or loads the one it holds. Deciding reads whether the material exists and, when it does, the CA certificate alone, never a key. It refuses a CA certificate it cannot read, and a CA whose key is not ECDSA P-256 — an instance made before [ADR 0020](../../docs/adr/0020-instance-pki-ecdsa-p256.md): there is no CA rotation, so the remedy is `farcast release`, then `farcast install`. Material it would load must be whole: each of its six files, `ca.crt`, `ca.key`, `client.crt`, `client.key`, `server.crt` and `server.key` under `instances/<name>/fatline/`, is looked for without being opened, and the first that is missing, or is not a regular file, is refused with the `read <file>: …` error loading it would give, its cause naming stat since nothing is opened: `load identity for "<name>": read <file>: stat …`. *(2026-11-17: before step 3, as `redeploy` decides it and as `connect` did before M2.6, so a refused trust root comes before a record that names no registry is given one. Until ADR 0023 M2.6c, built 2026-11-17, not walked, a missing `ca.key` was found only at step 6, after the question and after a record that names no registry was given one; now it is refused here, in every mode, `--plan` included, before anything is asked, ensured or printed. A file removed after this check is still refused at step 6.)*
3. **Take the instance's registry** — the one its record names. The installer's key is read from `credentials.yaml` and the provider opened; nothing is created, recorded or sent. A key that is blank, an install with Application Default Credentials, is refused with `credential_missing` before the provider opens. A record that names no registry is first given one outside a plan, by install's idempotent ensure ([above](#the-instances-registry)), as every connect did before, so an instance created before it had a registry converges here instead of failing later as an unexplained `ImagePullBackOff` inside the cluster. A plan never ensures, and refuses such a record: `instance "<name>" has no image registry recorded; run 'farcast connect <name>' interactively or with --yes, which ensures it`. Skipped entirely under `--status`.
4. **Decide FatLine's and Shrike's images** — the version tag holding the carried image is reused, a missing one is pushed, a foreign one is warned about and pushed over; `--source`, and a farcast built from source, compile and push from a checkout instead ([above](#where-fatlines-image-comes-from-adr-0007)). Deciding mints the registry token and looks up what the version tags, or a kept build, hold, and for a build finds the checkout and asks its Go (`go env`). It pushes and builds nothing. What it says, a foreign tag's warning and the notes on a kept or replaced image, prints once on stderr after this step, before anything is asked; the note on a replaced image used to come after the push. *(2026-11-17: each line Go-quoted when it holds a character that would act on the terminal, as a plan shows it. An interactive or `--yes` run that refuses a replacement with `version_skew` (step 5) refuses before the lines of the image it refuses, so it never announces a replacement, or a push over a foreign tag, that it does not make.)*
5. **Consent: the skew guard, the cost gate, then the build gate** — first, a component another farcast version deployed is refused with `version_skew` unless `--embedded` was given, before anything is asked. Then, if FatLine is not yet deployed, show the standing LB cost, counted against the instance's cost limit, and require a yes. *(Since ADR 0023 M2.6, built 2026-11-17, not walked, it is asked from the plan's cost fact, in exact cents: `~$18.25/month` for the load balancer where it said `~$18/month`, and the instance's limit in exact cents too, `USD 50.00/monthly` for the example instance.)* A resume, which finishes a bootstrap that deployed FatLine and was stopped before its carrier was recorded, asks no cost question. `--yes` skips it; it is required when non-interactive, and that refusal, in exact cents too, ends `pass --yes to confirm, or --plan and then --confirm <digest>`. *This is the point where money starts.* Only a build then has a **second, separate confirmation** — a consent gate, not a cost gate — naming the checkout and the Go step 4 found, which `--yes` also covers. Without a terminal it is refused the same way, with the plan route named. Pushing the carried image asks nothing more. Nothing is minted, pushed or built, and nothing is ensured beyond step 3's, until every answer is in, so a declined question leaves no CA behind.
6. **Mint or load the data-plane identity** — on first connect, mint a fresh **per-instance CA** and from it an **operator client leaf** (URI SAN `farcast://<instance>/operator`) and a **FatLine server leaf** (DNS SAN `<instance>.fatline.farcast`, the pinned server name). Persist all of it under the instance dir at `0600` (see [Local identity store](#local-identity-store)). On later connects, load it, and check the CA for P-256 again. This runs before anything is pushed or applied, for `redeploy` too. Material that appeared after step 2 decided to mint is never minted over: `instance "<name>"'s mTLS material appeared after the plan was made, and its plan would mint over it; nothing was written`, `plan_changed` under `--confirm` and `internal` otherwise. **The CA private key never leaves the operator's machine** — only the CA *certificate* and the server leaf+key are pushed to the cluster, so a compromise of the in-cluster Secret reads a rotatable leaf, never the power to mint identities.
7. **Ensure the instance's registry** — re-run install's idempotent ensure ([above](#the-instances-registry)), a Google write, not cost-gated: the registry is cents at most, unlike the load balancer. An ensure that fails refuses the connect, `…; nothing was pushed or deployed`, and never drops Shrike from what was decided. So does an ensure that answers with another registry than step 3 took: `instance "<name>"'s image registry is now <prefix>, not the <prefix> this command planned with; the registry was ensured, and nothing was pushed or deployed`, `plan_changed` under `--confirm` and `internal` otherwise. When step 3 took no registry, so that FatLine deploys alone, nothing is ensured.
8. **Push or build the images** — as step 4 decided them, with nothing looked up again. What comes out either way is a digest, and where it came from is recorded with the deploy in step 10.
9. **Deploy FatLine** — render FatLine's Autopilot-compliant workload ([`fatline/deploy`](#supporting-modules)) — `Namespace`, the mTLS `Secret` (CA cert + server leaf+key; **not** the CA key), `Deployment` (its container image the digest from step 8), and the `Service{type: LoadBalancer}` — and apply it through **kubectl over the stored kubeconfig** (no vendored Kubernetes client — see [Decisions](#decisions)). Idempotent (`kubectl apply`). Requires `kubectl` **and** `gke-gcloud-auth-plugin` on the operator's `PATH` — the stored kubeconfig authenticates through the plugin's exec hook (Decision 8).
10. **Await the point of presence** — record the now-existing (billable) load balancer and the exact image the cluster was told to run *before* waiting, then wait for the Deployment to roll out and the Service to be assigned its external IP (the LB ingress), with progress on stderr.
11. **Dial & verify** — `tunnel.Connect(ctx, "https://<lb-ip>:8443", ClientIdentity{client leaf, per-instance CA, pinned server name})`. `Connect` performs the mTLS handshake and probes FatLine's status endpoint, so a bad cert or unreachable instance fails *here*, not on first use.
12. **Record & report** — persist the carrier (endpoint, server name, type) and `fatline_deployed: true` into `metadata.yaml`; print the connection status.

A reconnect deploys nothing. It loads the identity, refusing material that is missing or a CA that is not P-256, and re-ensures the registry. A failed ensure is a warning, and the reconnect goes on, except under `--confirm` (*Its plan*, below). It then dials and prints the status as step 11 does, without the warm-up wait, and records nothing. It opens no writer and runs no kubectl. *(Since ADR 0023 M2.6c, built 2026-11-17, not walked: the ensure reads the installer's key first, as the writer reads it, and opens the provider only with a key. On an instance installed with Application Default Credentials, or whose `credentials.yaml` is missing, cannot be read or does not parse, it is refused, `credential_missing`, before the provider opens, so a reconnect never ensures a registry as this machine's ADC. That refusal is the warning, `Warning: <the refusal>` (for an ADC install, `Warning: instance "<name>" was installed without a service-account key (Application Default Credentials), …`); the reconnect goes on, prints the status and exits `0`, and under `--confirm` exits `1` with that kind. Until then it opened the provider with the blank key, which the provider took for this machine's ADC.)*

**Its plan** *(since ADR 0023 M2.6, built 2026-11-17, not walked)*. `connect <instance> --plan` binds `--carrier`, `--embedded`, `--fatline-image`, `--source` and `--status`, each as its parsed value; `--status` beside `--plan` or `--confirm` is a usage error, `--status only dials the bound carrier and reports; it writes nothing, so it has no plan to print or confirm`. A first deploy's facts are, in order:
- its cost: the load balancer and FatLine's replicas, standing, against the cost limit, with the instance's floor and whether the limit is below it;
- FatLine's and Shrike's images, each with its action (named, kept, reused, pushed, pushed over a foreign tag, or built from source), the image it deploys, the image the record says runs today, and whether it replaces a component another farcast version deployed; a build also binds its checkout's directory and the Go that compiles it;
- the CA, FatLine's server leaf and the operator's client leaf it mints, when this machine holds no material;
- the registry's cloud facts: the ensure, as the repository and the cluster's pull grant on it, then a push for each image that goes into the registry;
- one write for each of the six documents of FatLine's workload, rendered over placeholder leaves (below);
- its notices: what step 4 says, and for a build `the build compiles whatever <dir> holds when --confirm runs; this plan binds the directory, not its content`, once per checkout.

A resume has the same facts without the cost, and with a restart of FatLine when it mints over the one deployed. A reconnect's plan is the registry ensure alone, its two cloud facts.

The plan reads the record and the CA certificate, never `ca.key` or a leaf's key. It reads the installer's key from `credentials.yaml` only for the registry: to mint the token deciding the images uses. A source build's plan also finds the checkout and asks this machine's Go (`go env`). It reads no cluster, opens no writer, runs no kubectl, and ensures, pushes and builds nothing. A reconnect's plan reads neither the key nor the registry. With `--fatline-image` and no `--embedded`, a registry that cannot be read refuses `--plan` and `--confirm` ([above](#where-fatlines-image-comes-from-adr-0007)): no plan deploys FatLine without Shrike.

`--confirm <digest>` decides again and compares, prints what step 4 said, then opens the writer and goes on from step 6, asking nothing. It deploys the images it compared: after the comparison nothing is looked up again. Its plan is the consent to the cost, to each build, and to replacing a component another farcast version deployed, with or without `--embedded` ([plans and confirmation](#plans-and-confirmation)). Another Go found when it runs changes a source build's plan, which is then refused before anything is built. A reconnect's `--confirm` re-ensures the registry and prints the status; when that ensure fails, the command then fails, exit 1: `the registry ensure this plan bound did not succeed: <why>; the connection status above was read, and nothing else was written`, with the ensure's kind. A reconnect's plan reads no key, so on an instance installed with Application Default Credentials it is made, and its `--confirm` then fails this way, `credential_missing`, the provider never opened *(M2.6c, built 2026-11-17, not walked)*.

These changed for every first connect *(2026-11-17, ADR 0023 M2.6, built, not walked)*, in the order of the flow above:
- the registry token is minted and the version tags are looked up before the cost question, and the ensure, a Google write, comes after it; a record that names no registry is ensured before it too, as before, and again after;
- the CA is minted after the questions, where it was minted before them;
- a component another farcast version deployed is refused before the cost question, where it was refused after it;
- a source build's Go is asked before any question, so under `--yes` too;
- what the image decisions say prints once, before any question;
- FatLine's six documents are rendered and checked as a plan checks them (the stream check, `kube.SplitStream`) before any question, where they were rendered after the questions; no value the command line can give is known to trip that check;
- the cost question, and its refusal without a terminal, state exact cents;
- each refusal without a terminal names the plan route;
- a push or a build mints a registry token of its own ([above](#where-fatlines-image-comes-from-adr-0007)).

### Command surface

```
farcast connect <instance> [flags]
```

| Flag | Meaning |
|---|---|
| `<instance>` | The instance to connect to (positional, required). |
| `--carrier <nlb>` | Data-plane carrier (default `nlb`, the public mTLS load balancer). The seam reserves `cp-forward` (control-plane fallback) for a later phase. |
| `--status` | Don't bootstrap or provision anything — just dial the already-bound carrier and report status (re-connect / health probe). Does **no registry work at all**. Fails if the instance was never connected. It writes nothing, so it has no plan: beside `--plan` or `--confirm` it is a usage error *(since ADR 0023 M2.6)*. |
| `--yes`, `-y` | Skip the LB-cost confirmation **and**, for `--source` or a source build, the build-and-push confirmation; required when non-interactive, unless `--plan` and then `--confirm` are used. Never implies `--embedded`. |
| `--fatline-image <ref>` | FatLine image to deploy, **digest-pinned** (`repository@sha256:…`). Default: the image this farcast carries, pushed to the instance registry's `system/fatline`. An explicit ref is deployed exactly as given, with no lookup and no registry access, and recorded as `named`. First connect only: refused on a reconnect, which deploys nothing — use `farcast redeploy --fatline-image` to change what a connected instance runs. |
| `--source <dir>` | A farcast checkout to build FatLine's and Shrike's images from with this machine's Go (a release farcast needs none); pushed under `source-…` and recorded as operator-built ([why it always builds](#why---source-forces-a-rebuild)). Likewise refused on a reconnect (`farcast redeploy --source` is what rebuilds for a connected instance). |
| `--embedded` | Deploy the images this farcast carries, replacing an operator-built image or one another farcast version deployed. Never implied by `--yes`. Beside `--fatline-image` it governs Shrike's image alone: FatLine's is deployed as given and never pushed, and Shrike's needs the registry, so a failed ensure refuses the pair. Refused with `--source`, on a farcast that carries nothing, and on a reconnect. |
| `--plan` | *(Since ADR 0023 M2.6, built 2026-11-17, not walked.)* Print what this connect would do, and change nothing (*Its plan*, above). It needs the registry recorded, and never plans FatLine without Shrike. |
| `--confirm <digest>` | *(Since ADR 0023 M2.6, built 2026-11-17, not walked.)* Do exactly the plan with that digest, asking nothing. A plan that has changed since is refused with `plan_changed` before anything is written, and so is one whose identity or registry turns out changed when it comes to them, before anything is pushed or applied (steps 6 and 7; [plans and confirmation](#plans-and-confirmation)). |

Global flags (`--output`, `--verbose`, `--config`) apply. With `--output json` the command prints one JSON result and never prompts (so the cost gate must be pre-answered with `--yes`, or with `--plan` and then `--confirm <digest>`; under `--plan` the JSON is the plan document).

```
  relayed by:  the FatLine replica on gk3-farcast-prod-pool-1-…
  registry:    us-central1-docker.pkg.dev/<project>/farcast-prod
  image:       us-central1-docker.pkg.dev/<project>/farcast-prod/system/fatline@sha256:…
  cost:        load balancer ~$18/mo + FatLine and Shrike ~$11/mo + registry ~$0/mo (limit: USD 50/monthly)
```

The `image` line is a **digest, not a tag** — it is the reference the cluster was actually told to run. Both it and `registry` are omitted for an instance that has neither recorded.

`relayed by` names the node of the FatLine replica that answered this connection (`node` in JSON). The load balancer hands a connection to one replica, so it says nothing about where the other runs; it is omitted when FatLine does not report it (a workload deployed before it did). `farcast storage state` uses the same answer to say when that replica shares a node with the keyholder replicas ([ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md)).

JSON (`--output json`):

```json
{"name":"prod","connected":true,"carrier":"nlb","endpoint":"34.120.0.5:8443","identity":"farcast://prod/operator","active":0,"registry":"us-central1-docker.pkg.dev/<project>/farcast-prod","image":"…/farcast-prod/system/fatline@sha256:…"}
```

### "All subsequent commands route through FatLine"

The CLI is stateless between invocations — there is no daemon. `connect` makes routing possible by **persisting the operator's identity and the carrier endpoint**; each later command (`run`/`ps`/`logs`/`costs`, phase 4.3) re-loads them and re-dials the tunnel for its duration via the same `fatline/tunnel` library, using `Conn.HTTPClient()` for its instance API calls. So 2.3 delivers the mechanism and the status surface; the commands that consume it land in 4.3. (With the public-NLB carrier the endpoint is a stable IP, so each re-dial is direct and stateless — no port-forward to keep alive.)

### Local identity store

`connect` extends the [instance store](#configuration--credential-storage) with the data-plane mTLS material, under the same `0700`/`0600` rules:

```
instances/<instance-name>/
├── metadata.yaml        (0600)  + carrier {type, endpoint, server_name}, fatline_deployed
│                                + registry {prefix, repository, location, puller,
│                                  fatline_digest} — the instance's own image registry
│                                  and the digest-pinned ref last deployed from it
├── credentials.yaml     (0600)  (unchanged — cloud credential)
├── kubeconfig.yaml      (0600)  (unchanged — control-plane access)
└── fatline/             (0700)  data-plane mTLS identity
    ├── ca.crt           (0600)  per-instance CA certificate
    ├── ca.key           (0600)  per-instance CA private key — the crown jewel, NEVER pushed to the cluster
    ├── client.crt       (0600)  operator client leaf (SAN farcast://<instance>/operator)
    ├── client.key       (0600)
    ├── server.crt       (0600)  FatLine server leaf (SAN <instance>.fatline.farcast) — pushed to the cluster Secret
    └── server.key       (0600)
```

The CA key's locality is the security crux: it is what keeps the data-plane trust root sovereign and off the cloud. The metadata/credentials/identity split means `instances` and `world` never open the CA key. `usage`'s network half, which dials the same tunnel, still loads it with FatLine's server key, as `storage state` does ([below](#who-the-cluster-reads-run-as)).

### Supporting modules

`connect` is an orchestrator; the reusable capability lives in five small, testable seams:

- **[`fatline/identity`](../../fatline/README.md)** *(new, public)* — the operator-side mint/load surface wrapping FatLine's `internal/crypto` (which stays internal): mint a per-instance CA, issue the operator client + FatLine server leaves, and assemble a `tunnel.ClientIdentity` from stored PEMs. This is what lets the CLI handle mTLS material without importing FatLine internals.
- **[`fatline/deploy`](../../fatline/README.md)** *(new, public)* — renders FatLine's own Kubernetes workload (Namespace, Secret, Deployment, Service) as an Autopilot-compliant apply stream. FatLine owns the shape of how it is deployed; this is the one-off precursor to Planck's general manifest translator (4.2).
- **`farsight/cli/internal/cluster`** *(new)* — a minimal **kubectl-subprocess** wrapper (apply via stdin, await rollout, read the Service external IP) over the stored kubeconfig. The exec boundary is injectable, so the orchestration is unit-tested with a fake runner; the real cloud path is integration-gated. Since [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M0 (built 2026-11-13) kubectl no longer inherits this process's environment: it gets one built from an allowlist (`PATH` without relative or empty entries, an absolute `HOME` and `TMPDIR`, `LANG` and `LC_*`, the two variables that choose the gcloud configuration, and `GORACE`), with `KUBERC=off`, and the parent's `KUBECONFIG`, which reaches only the auth plugin, since kubectl is always given `--kubeconfig`. *(Until ADR 0023 M2.4 `world` alone set `KUBECONFIG` to the instance's kubeconfig. No kubectl call does since.)* What an operator notices: a proxy in the shell no longer reaches kubectl, `CLOUDSDK_CORE_ACCOUNT` and `CLOUDSDK_PYTHON` no longer reach gcloud through the plugin, and `~/.kube/kuberc` is never read. Who a kubectl call runs as is unchanged: the active gcloud configuration. Since ADR 0023 M2.3 (built 2026-11-14) the package also has `Open`, which builds the instance's [reader](#farcast-reader--the-reader-identity-adr-0023-m23) in-process and starts no program. Since M2.4 (built 2026-11-15) a reader answers every read in-process — workloads, ConfigMaps, namespaces, a rollout, a Service's IP, a Job, its logs and an application's logs — and the access review. It refuses `Apply`, `CreateConfigMap` and `ReplaceConfigMap` before anything is sent: `cluster: a reader client never writes`. The cluster reads of `world`, `ps`, `costs`, `usage` and `logs` use it, and so do `reader grant`'s verifying read and reviews. Since M2.5 (built 2026-11-15) `Open` also builds the instance's writer, from the installer's key in `credentials.yaml`, and `New` is gone: every client farcast builds is built by `Open`. A writer answers the same reads in-process, and `NamespaceUID`. It creates and replaces the storage key pin in-process too: a `POST`, and a `PUT` carrying the `resourceVersion` the pin was read at. Only its `Apply` still runs kubectl, over the stored kubeconfig, as the active gcloud configuration, until M2.7. That is the one kubectl call left, `reader grant`'s apply included ([who the writing commands run as](#who-the-writing-commands-run-as)).
- **`farsight/cli/internal/oci`** *(new, 2.3 + [ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md))* — a standard-library-only **OCI distribution client**: reference parsing, per-host authentication (anonymous, Basic, and the Bearer-challenge token dance), pull with index platform selection, deterministic tar layer building, layer append, and push. It knows nothing about FarCast — it is pure wire protocol — and it treats registries as untrusted transport: every manifest and every blob is verified against the digest that addressed it, credentials are never logged, never put in a URL, and never sent to a non-loopback host over plaintext HTTP.
- **`farsight/cli/internal/image`** *(new, 2.3 + [ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md); rewritten for [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M0 and M1)* — the FarCast-shaped decisions above that protocol: which base (`BaseImage`, the digest-pinned distroless, whose three documents are committed under `image/base/` and embedded, so manifest digests are computed offline; `PinnedBase` checks them against `BaseImage`, and a missing one fails to compile), which platform (`ComponentPlatform`, linux/amd64), and the one recipe for a component: `BuildFlags`, `FindToolchain`, `BuildEnviron` and `CheckBinary` for the compile, `ComponentLayer` and `Assemble` for the image. `PushEmbedded` pushes a carried component, comparing the assembled manifest digest with the compiled-in one before any upload; `BuildAndPush` is `--source` and the development fallback, pushing under `SourceTag`; `Resolve` is a HEAD by tag or digest; `FindSource` locates a checkout.
- **`farsight/cli/internal/components`** *(new, ADR 0023 M1)* — the four components' identities, and, behind the build tag `farcast_embedded`, the layers and digest table a release carries. Untagged it carries nothing, so a plain `go build ./...` compiles.
- **`farsight/cli/internal/release`** and **`farsight/cli/cmd/farcast-release`** *(new, ADR 0023 M1)* — the release tool: `build`, `layers`, `notices`, `base -write` (the one networked step, for a base bump) and `execsites` (the exec gate's listing, `internal/execgate`). A development tool, never linked into farcast.

### Testing

Mirrors `install`/`release` and [Planck's strategy](../../planck/README.md): the orchestration — identity mint/persist, the registry ensure, the image preflight and the build-or-decline decision, manifest rendering, the cost gate, the kubectl call sequence, status rendering, the record-before-provision ordering — is unit-tested against a **fake cluster runner**, a **fake registry provider**, a **fake image builder** and an **in-process mTLS FatLine** (the same `httptest`-over-mTLS harness FatLine's `tunnel` e2e test uses), with `t.TempDir()` state and asserted `0600` perms — **no real cloud, no LB cost, nothing compiled, no registry contacted**. The end-to-end public-NLB path sits behind `//go:build integration` and is **never run by `./check.sh`** (cost pillar), exactly like Planck's create/delete tests.

The two image packages are tested a layer down. `oci` runs against an `httptest` registry: the Bearer and Basic challenge flows, the refusal to offer a credential before being challenged or to fetch a token over plaintext, index platform selection, layer determinism, a cross-registry round trip, and the rejection of a tampered blob or a manifest that breaks its own pin. Wire-protocol correctness is the price of owning this code, so a pull, a tag resolve and a miss are also exercised against the **real gcr.io** behind `//go:build integration` — that one costs nothing, but it is opt-in like every other network-touching test here. `image` drives `BuildAndPush` end to end with an injected compiler, asserting among other things that the target registry's credentials are never offered to the public base's host.

## `farcast redeploy` — replace a connected instance's FatLine workload (Phase 2.3)

`farcast redeploy <instance>` re-renders and re-applies FatLine's workload for an instance that is **already connected**. It is how a fix to the network boundary reaches a running instance — a new image, a changed manifest, or both — without touching the carrier, the mTLS identity, or anything else the instance is.

It exists because the alternative was destroying the instance. The first live Phase 2 Part B deploy crash-looped: FatLine's mTLS `Secret` was mounted root-only and the non-root container could not read its own key (fixed in `e4c066e`). Rolling that fix out took hand-editing `fatline_deployed: false` into the instance's `metadata.yaml` to trick `connect` into bootstrapping again, because `connect` skips its bootstrap entirely once the instance is deployed and bound. The only supported alternative was `release` plus a reinstall — destroying an entire instance to patch the thing guarding it. That is the wrong price to attach to a security fix, because it is the price that makes an operator postpone one.

The division of labour is the point: **`connect` opens the tunnel, `redeploy` changes what runs inside it.** Redeploy never provisions a carrier and never mints a CA, so nothing it does is billable-new and the instance's public endpoint and trust root are exactly what they were.

### Flow

*(Reordered by ADR 0023 M2.6, built 2026-11-17, not walked.)* A redeploy decides both images before it asks, and ensures the registry, pushes and builds only after the answer: steps 2 to 4 read and decide, step 5 is the consent, and steps 6 to 11 do what was decided. Until then the registry was ensured and the images pushed or built before the change question, which was then asked with the pushed digest in hand. Under `--plan` it stops after step 4 and prints what it decided; under `--confirm` it decides again, compares, and goes on from step 6, asking nothing (*Its plan*, below).

1. **Resolve the instance** — load `metadata.yaml` (its `credentials.yaml` and `kubeconfig.yaml` are read by the steps below that need them). An instance being released is refused, as it is by `connect`. An instance that was never connected — no `fatline_deployed`, no carrier — is refused too, directed at `farcast connect <instance>`: redeploy replaces a workload, it does not create one, and inventing a carrier here would duplicate connect's bootstrap (billable half included) behind a verb that promises not to.
   - **Open the writer and read once** *(since ADR 0023 M2.5, built 2026-11-15, not walked)*, as `connect`'s bootstrap does: the writer opens from `credentials.yaml`, this machine is checked for `kubectl` and the instance's `kubeconfig.yaml`, and `farcast-system`'s uid is read in-process as the installer service account, all before the identity is loaded, the registry ensured, anything pushed or asked. A refusal here changes nothing. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: `--plan` never opens the writer, and `--confirm` opens it, and reads, right after the comparison, before step 6.)* *(2026-11-16: at 2482810 this read is refused against GKE, as `connect`'s is: the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md) found that GKE's DNS endpoint refuses farcast's token scoped to `userinfo.email` alone. The fix, built later that day and not walked, mints with `cloud-platform` and `userinfo.email`, so a leaked writer token works for every Google API the installer's IAM allows, not only the cluster.)*
2. **Decide the data-plane identity** — the per-instance CA and FatLine's server leaf are to be **loaded, never minted**. FatLine is already running and already trusts a CA; a fresh one would only produce certificates it must reject, and would overwrite the record of what it actually trusts. Missing material is therefore reported as unrecoverable (the same message `connect` gives a deployed instance), never replaced. Deciding reads whether the material exists and the CA certificate alone, and refuses a CA that is not ECDSA P-256, before the registry is read or ensured. *(Since ADR 0023 M2.6c, built 2026-11-17, not walked.)* It also looks for each of the material's six files, `ca.crt`, `ca.key`, `client.crt`, `client.key`, `server.crt` and `server.key`, without opening one, and refuses the first that is missing, or is not a regular file, with the `read <file>: …` error loading it would give, its cause naming stat since nothing is opened (`load identity for "<name>": read <file>: stat …`), as `connect` does. Until then a missing key was found only at step 6, after the question and after a record that names no registry was given one.
3. **Take the instance's registry** — the one its record names, as `connect` takes it: the installer's key read from `credentials.yaml` and the provider opened, with nothing created, recorded or sent. A record that names none is first given one outside a plan, by the same idempotent ensure `install` and `connect` run ([above](#the-instances-registry)); a plan refuses it, naming `connect`. When the registry cannot be had this way, a redeploy that needs it stops. With an explicit `--fatline-image` and no `--embedded`, FatLine's image is neither looked up nor pushed, so outside `--plan` and `--confirm` the failure degrades to a stderr warning, and Shrike, with no registry to come from, is not deployed: FatLine deploys alone, and the command says so. Under `--plan` and `--confirm` it is refused instead, with the failure's own kind: no plan deploys FatLine without Shrike ([above](#where-fatlines-image-comes-from-adr-0007)). `--embedded` beside `--fatline-image` asks for Shrike's carried image, which needs the registry, so there the failure stops the redeploy before anything is applied, and says to drop `--embedded` to deploy FatLine alone.
4. **Decide FatLine's and Shrike's images** — *identical* to connect's, from the same code ([above](#where-fatlines-image-comes-from-adr-0007)): a recorded operator build is kept until `--embedded` or `--source`; otherwise, in a release farcast, the image it carries, reused when the version tag holds exactly it and pushed when it does not, and refused with `version_skew` (at step 5) when another farcast version deployed a different one and `--embedded` was not given (a farcast built from source compiles instead, after its build confirmation); an explicit `--fatline-image` is deployed exactly as given, with `--embedded` beside it governing Shrike's image alone, and an explicit `--source` always builds ([below](#why---source-forces-a-rebuild)). Deciding mints the registry token and looks up what the version tags, or a kept build, hold, and for a build finds the checkout and asks its Go (`go env`); it pushes and builds nothing, and what it says prints once on stderr after this step, before anything is asked, as on `connect` *(2026-11-17: Go-quoted where a line would act on the terminal, and not said for an image whose replacement step 5 refuses with `version_skew`)*. Every deploy is pinned by digest, and where the image came from is recorded once the rollout succeeds. The two commands share one implementation rather than two copies, because that path is the supply chain for the instance's network boundary and a second, subtly different copy of those rules is how an unpinned deploy eventually arrives.
5. **Confirm the change** — a component another farcast version deployed is refused first, as on `connect`; then each build's question, then show what will change and ask *(2026-11-17: the images and the checkout it names are Go-quoted where they would act on the terminal; the six documents have been rendered and checked as a plan checks them before this step, where they were rendered after the questions)* ([below](#the-consent-gate-and-why-there-is-no-cost-gate)). `--yes` skips both; non-interactive without `--yes` is a usage error, which since ADR 0023 M2.6 names the plan route too: `…; pass --yes to confirm, or --plan and then --confirm <digest>`. Nothing is pushed, built or ensured beyond step 3's until every answer is in.
6. **Load the data-plane identity** — the material step 2 decided on, checked for P-256 again.
7. **Ensure the instance's registry** — the ensure, a Google write. One that fails stops the redeploy, `…; nothing was pushed or deployed`, and so does one that answers with another registry than step 3 took (`plan_changed` under `--confirm`, `internal` otherwise), as on `connect`. When step 3 took no registry, so that FatLine deploys alone, nothing is ensured.
8. **Push or build the images** — as step 4 decided them, with nothing looked up again.
9. **Render & apply** — render the workload for the carrier the instance is **already bound to**, never a default, and apply it through the same kubectl seam `connect` uses. Re-rendering a bound instance with a different Service type would tear down the point of presence the operator reaches it through and, for the load balancer, replace a standing billable resource and its public IP as a side effect of a workload change nobody asked to be one.
10. **Wait, then record** — wait for the rollout, and write the deployed digest into `metadata.yaml` **only once that rollout has succeeded**. This is the one ordering redeploy deliberately inverts from `connect`, which records before waiting because it is racing to record a billable load balancer; nothing here becomes billable. FatLine runs two replicas, and at two the default rolling strategy adds a new pod before it removes an old one (maxUnavailable rounds to 0, maxSurge to 1), so a rollout that never goes ready leaves the *previous* image serving traffic — recording early would name an image that never served a byte, on the exact path this command exists for. A failed rollout leaves the record alone and — when local state records what was there — names the image still serving and the `kubectl describe pod` that explains why the new one is not.
11. **Report** — old digest → new digest, the fact that the digest did not change, or just the image when local state had nothing to compare against.

**Its plan** *(since ADR 0023 M2.6, built 2026-11-17, not walked)*. `redeploy <instance> --plan` binds `--embedded`, `--fatline-image` and `--source`, each as its parsed value. Its facts are, in order: FatLine's and Shrike's images, as on `connect`; the registry's cloud facts, the ensure and then a push for each image that goes into the registry; one write for each of the six documents of FatLine's workload, rendered for the carrier the instance is bound to, over placeholder leaves and the instance's own CA certificate; and its notices, what step 4 says and a source build's notice. A source build's plan binds the checkout's directory and Go, not what the checkout holds when `--confirm` runs, and says so. It mints nothing and restarts nothing: it only loads. It reads what `connect`'s plan reads: the record, the CA certificate (never `ca.key` or a leaf's key), the installer's key for the registry alone, and for a source build the checkout and this machine's `go env`. It reads no cluster, opens no writer, runs no kubectl, and ensures, pushes and builds nothing. `--confirm <digest>` decides again and compares, prints what step 4 said, then opens the writer and goes on from step 6, asking nothing. It deploys the images it compared, and its plan is the consent to each build, to the change, and to replacing a component another farcast version deployed, with or without `--embedded` ([plans and confirmation](#plans-and-confirmation)).

### Command surface

```
farcast redeploy <instance> [flags]
```

| Flag | Meaning |
|---|---|
| `<instance>` | The instance to redeploy (positional, required). Must already be connected. |
| `--yes`, `-y` | Skip the change confirmation **and**, for `--source` or a source build, the build-and-push confirmation; required when non-interactive, unless `--plan` and then `--confirm` are used. Never implies `--embedded`. |
| `--fatline-image <ref>` | FatLine image to deploy, **digest-pinned** (`repository@sha256:…`). Default: the image this farcast carries, pushed to the instance registry's `system/fatline`. An explicit ref is deployed exactly as given, with no lookup, and recorded as `named`. |
| `--source <dir>` | A farcast checkout to build FatLine's and Shrike's images from with this machine's Go (a release farcast needs none). It **always** builds, pushes under `source-…` and records the images as operator-built ([below](#why---source-forces-a-rebuild)). |
| `--embedded` | Deploy the images this farcast carries, replacing an operator-built image or one another farcast version deployed. Never implied by `--yes`. Beside `--fatline-image` it governs Shrike's image alone: FatLine's is deployed as given and never pushed, so a Shrike another farcast version deployed does not block the break-glass redeploy; Shrike's image needs the registry, so a failed ensure refuses the pair (drop `--embedded` to deploy FatLine alone). *(Since ADR 0023 M2.6, built 2026-11-17, not walked: dropping `--embedded` deploys FatLine alone only when the registry cannot be had before the change is confirmed; a recorded registry whose ensure fails after it refuses the redeploy either way, with nothing pushed or deployed.)* Refused with `--source` and on a farcast that carries nothing. |
| `--plan` | *(Since ADR 0023 M2.6, built 2026-11-17, not walked.)* Print what this redeploy would do, and change nothing (*Its plan*, above). It needs the registry recorded, and never plans FatLine without Shrike. |
| `--confirm <digest>` | *(Since ADR 0023 M2.6, built 2026-11-17, not walked.)* Do exactly the plan with that digest, asking nothing. A plan that has changed since is refused with `plan_changed` before anything is written, and so is a registry that turns out changed at step 7, before anything is pushed or applied ([plans and confirmation](#plans-and-confirmation)). |

Global flags (`--output`, `--verbose`, `--config`) apply. With `--output json` the command prints one JSON result and never prompts (so the change gate must be pre-answered with `--yes`, or with `--plan` and then `--confirm <digest>`; under `--plan` the JSON is the plan document). There is deliberately **no `--carrier` flag**: the carrier is whatever the instance is already bound to, and changing it is `connect`'s business, not a workload update's.

### Why `--source` forces a rebuild

`--source <dir>` is read as a request to *build*: the checkout is compiled and pushed with nothing looked up first. *(Since ADR 0023 M1, 2026-11-13, for a new reason.)* An operator build is its own image, under its own `source-…` tag and its own `operator` record, and the version tag holds only the image this farcast carries — so looking anything up would only find an image other than the operator's fix. `--source` therefore always builds, and nothing else does in a release farcast (a farcast built from source compiles whenever nothing recorded is kept); the build is then kept by later commands until `--embedded` or `--source` again.

That makes the image flags opposed intents — "deploy exactly this", "build from here and deploy that" and "deploy what this farcast carries" — so passing two for the same image is a usage error rather than a silent choice between them. `--fatline-image` with `--embedded` is not such a pair: the first names FatLine's image, and the second then governs Shrike's.

### The consent gate, and why there is no cost gate

Redeploy asks before it applies, and what it asks about is the *change*, not the money:

```
this replaces the image "prod" runs: …/system/fatline@sha256:9f2c… → …/system/fatline@sha256:41ab….
Re-apply FatLine's workload now? [y/N]:
```

There is **no ~$18/mo confirmation** here, and that is a deliberate protection of the gate that matters. The load balancer already exists and a redeploy makes nothing new billable, so re-asking the cost question would attach the cost prompt to an operation whose honest answer is always "nothing changes" — which is how a gate that guards real money ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)) gets trained into a reflex. One prompt, one meaning.

Building an image from source — `--source`, or a farcast built from source with an image missing — keeps its own separate confirmation (the one `connect` uses), and it is asked *first*, because a push changes nothing about what the instance is running. Pushing the image a release farcast carries asks nothing of its own. Only the apply does — so the operator is asked about the apply with the resulting digest in hand rather than in the abstract. `--yes` covers both. *(Since ADR 0023 M2.6, built 2026-11-17, not walked: the build's question is still asked first, but nothing is pushed or built until both are answered, because a push is a write to the one place the instance runs code from. The carried image's digest is known before it is pushed, from the digest this farcast carries, so the change question still names it. A build's digest exists only once it is built, so for a build the question names the checkout instead: `this replaces the image "prod" runs: …/system/fatline@sha256:9f2c… → a source build of <dir>, pushed once it is built`, or, with nothing recorded, `this redeploys "prod" with a source build of <dir>; local state does not record what it runs today`.)*

**An unchanged digest still re-applies.** The failure this command was built for was a workload-*template* defect with the image byte-identical, so a redeploy that no-opped on a matching digest would be useless for exactly the case it exists for. It says so rather than pretending something moved:

```
"prod" already runs …/system/fatline@sha256:41ab… — image unchanged; re-applying the workload template.
Re-apply FatLine's workload now? [y/N]:
```

### Output

Human:

```
✓ redeployed FatLine to "prod"
  carrier:     public mTLS NLB  34.120.0.5:8443 (unchanged)
  registry:    us-central1-docker.pkg.dev/<project>/farcast-prod
  previous:    us-central1-docker.pkg.dev/<project>/farcast-prod/system/fatline@sha256:9f2c…
  image:       us-central1-docker.pkg.dev/<project>/farcast-prod/system/fatline@sha256:41ab…
  rollout:     complete
```

The image lines report exactly as much as local state supports — three cases, never one dressed as another:

- **The digest moved** → `previous:` then `image:`, as above.
- **Nothing recorded to compare against** → `image:` alone, with no `previous:` line and no "unchanged" claim: local state does not know what the instance was running, so calling it unchanged would be a guess dressed as a fact.
- **The digest did not move** → the two lines collapse into one that says what actually happened:

```
  image:       us-central1-docker.pkg.dev/<project>/farcast-prod/system/fatline@sha256:41ab… (unchanged; the workload template was re-applied)
```

`rollout: complete` is a fact the command waited for, not a hope: it is printed only after the Deployment reports its new Pods ready, so a crash-looping FatLine fails the command instead of being reported as a success — and, because the digest is recorded only after that wait, local state keeps naming the image that is still serving.

JSON (`--output json`):

```json
{"name":"prod","carrier":"nlb","endpoint":"34.120.0.5:8443","registry":"us-central1-docker.pkg.dev/<project>/farcast-prod","previous_image":"…/system/fatline@sha256:9f2c…","image":"…/system/fatline@sha256:41ab…","image_changed":true,"status":"redeployed"}
```

`previous_image` is omitted for an instance whose local state does not record what it was running — the redeploy still proceeds, and says so. `image_changed` is `false` both there and when the digest did not move, so it answers "did the image move?" and never stands in for "did anything happen?" — the workload was re-applied either way.

## `farcast storage` — the instance's encrypted disk (Phase 3.3)

`farcast storage` is how an operator puts data into an instance and gets it back out. Everything it writes is encrypted before the cloud sees it and stored under an opaque name, by [DataSphere](../../datasphere/README.md) — the CLI does not get a say in that, because the encrypting `Store` is the only path there is.

Two things make this group unlike the rest of the CLI. It is the first command family that touches **data that derives from nothing** — a cluster is re-provisionable and every registry image rebuilds from Git, but a deleted object is gone, and soft delete is disabled on the bucket by design. And it depends on a local file, `keys.yaml`, whose loss is the permanent loss of everything in the bucket. Both facts shape every decision below.

**It needs no cluster and no tunnel.** Storage runs entirely on the operator's machine: the recorded bucket, the stored cloud credentials, and the local keyring. `farcast storage` therefore works on an instance that has never been `connect`ed, and it is why Phase 3.3 is not blocked on 3.2's in-cluster key-delivery ADR.

### Addressing: `<instance>:<key>`, scp-style

```
prod:app/reports/q3.csv     one object
prod:app/reports/           a /-aligned prefix
prod:                       the whole bucket
./q3.csv    -               a local file; stdin/stdout
```

An operand is **remote** iff its first `:` falls before any `/`, the text before it is a valid instance name, and that instance exists in local state. Everything else is local. If both readings are genuinely available — an instance `prod` exists *and* a local file named `prod:x` exists — it is a **usage error** telling the operator to write `./prod:x`. Guessing here either uploads the wrong bytes or overwrites the wrong file, and neither is recoverable.

### The verb tree

Two levels for the data verbs, as [Decisions](#decisions) 1 reserved; **three only for `key`**.

```
farcast storage ls    <instance>[:prefix]   [-l|--long] [--tokens]
farcast storage cp    <src> <dst>           [-r] [--force|--skip-existing]
farcast storage rm    <instance>:<key>…     [-r] [-y]
farcast storage usage <instance>

farcast storage key list   <instance>
farcast storage key export <instance> --out <path> --passphrase-file <path>
farcast storage key import <instance> <file>       --passphrase-file <path>
farcast storage key rotate <instance>       [-y] [--plan | --confirm <digest>]
farcast storage key rekey  <instance>       [--dry-run] [-y]
farcast storage key pin    <instance>       [--replace] [-y] [--plan | --confirm <digest>]
```

`key` earns the third level because **the noun changes**: `ls`/`cp`/`rm`/`usage` address objects in a bucket; `export`/`import`/`rotate`/`rekey` address the file whose loss destroys all of them. Flattening them would put a keyring verb in the same tab-completion neighbourhood as `storage rm`, and `storage rotate` reads as though it rotates data. The cost is one dispatcher instantiated twice.

No command in the group takes cloud flags. Provider, project, region and credentials all come from the recorded instance, exactly as `release`, `connect` and `redeploy` take none, and there is no `--bucket`: the record is the sole authority.

### `cp`, and the two ways it can lose data

`cp` streams in both directions through DataSphere's v2 chunked format, so file size is not a consideration in either direction. Exactly one operand may be remote; two remote or two local operands are a usage error rather than a guess.

- **It never overwrites silently**, in either direction. An existing destination — a local file or a remote key — stops the copy and names what is there; `--force` replaces, `--skip-existing` skips. This is stricter than `cp(1)` on purpose: the remote side has no undelete.
- **A failed download leaves nothing at the destination.** Downloads land in a temporary file alongside the target and are renamed only after the final frame authenticates. This is load-bearing rather than tidy: v2 authenticates per frame, so a truncated or tampered object is detected only when the reader reaches the damage, and a partial file that looks plausible is worse than no file.
- **Local files it creates are `0600`**, matching the credential store's discipline — decrypted plaintext is not something to leave world-readable.
- **A recursive download must not be a path-traversal primitive.** A logical key is any non-normalized UTF-8 byte string and may contain `..`, a leading `/`, or bytes illegal in the local filesystem — and, after 3.2, may have been written by an application inside the instance. `cp -r prod: ./out` refuses any key that does not map to a safe relative path under the destination, names it, and continues with the rest. It never mangles silently and never writes outside the destination root.

### `rm`, and `release`'s new gate

`rm` on an exact key is unceremonious. `rm -r` on a prefix shows what will go and requires confirmation, and says plainly that deletes are immediate and final because soft delete is disabled on the bucket.

`farcast release` gains one flag, `--delete-data`, and one gate:

**`release` refuses while the instance bucket still holds data.** The gate is **data-triggered, not configuration-triggered** — a bucket with zero objects produces no gate, no flag and no extra prompt, so a test instance that installed, connected and released without writing anything behaves exactly as it does today. With data present, `release` names the object count and stored bytes and stops, pointing at `storage cp`; `--delete-data` is what proceeds.

`--delete-data` is a **scope** flag, not a consent flag. `--yes` says "don't ask me" and never implies it: the confirmation an operator clicks through daily must not be able to destroy the one thing that derives from nothing.

The count comes from `datasphere.BucketUsage` over the `Provider` — **never through the `Store`, and with no keyring**. An operator who has lost `keys.yaml` still needs to be able to stop paying, and a gate built on what the keyring can *name* would report an empty bucket while billable ciphertext sat in it.

Ordering inside `release` follows the shipped discipline, with the data last: probe and gate **before anything is destroyed**, then cluster → registry → bucket → local state. A failure part-way leaves the data intact and the record in place, so a re-run converges.

### The keyring, and when it is minted

The keyring lives at `<instance>/datasphere/keys.yaml` (`0700` directory, `0600` file), beside the mTLS CA key — the two crown jewels in one directory, so the backup gesture is one gesture.

It is minted at **first storage use**, not at `install`: the install flow is shipped and validated, and an instance that never stores anything never needs one. The mint is a deliberate step rather than a side effect, and it prints DataSphere's mandated sentence verbatim — *loss of `keys.yaml` is permanent, unrecoverable loss of all stored data — FarCast keeps no copy anywhere, by design* — naming the instance directory as the thing to back up.

- **`key export`** writes a passphrase-armored copy (stdlib `crypto/pbkdf2` + AES-256-GCM, versioned format). The passphrase is read from a terminal, never a flag.
- **`key import` is merge-only** — it adds entries the live keyring lacks and never overwrites or drops one, refusing outright if an id appears on both sides with different material, or if a scope appears on both sides with no name key in common — minted twice, independently, so merging would leave one side's objects unlistable. This is `datasphere.Keyring.Merge`'s semantics surfaced as a command, and it is a security control: a blob's key ID is cloud-writable, so a tampering cloud can make any object demand a key the keyring lacks, and the natural overwrite-restore would destroy every key added since the backup. The output says `removed: nothing — import is merge-only, by design`, in every mode, to teach the invariant to whoever is about to look for a `--force` that does not exist.
- **`key rotate`** prepends a new KEK to the instance's own key space **and to every application's scope** — since ADR 0018 decision 5 every application object lives under a scope, so a rotation that reached only the master rotated nothing an application wrote. A serving keyholder is handed the new keys in two steps: every serving replica first holds them with the old ones still active, and only when each has confirmed — and still holds them when asked again — are they made active. A new key active on one replica and absent from another would leave the second unable to read what the first writes. This machine's keyring follows the same rule, because this machine writes to storage too (`secret set`, `storage cp`): it is saved with the new keys held first, and saved with them active only at the moment every replica holds them. While the new keys are held, the key kept in use is one a serving replica already writes under — never a held key an earlier, unfinished rotation gave to some replicas only. If a replica misses the first step, or every replica is sealed (with none serving, nothing would stop a keeper re-seeding the old keys), nothing changes for any application and running it again once every replica is serving and answers finishes a rotation with fresh keys (the unused ones stay held). It succeeds only when some replica took the push that puts the keys in use (one that reached none puts this machine's keyring back), and exits non-zero naming what finishes it — `storage unseal` and then another `rotate` when every replica is sealed, `storage unseal` when only some replicas use the keys, another `rotate` otherwise, and nothing on this machine when a replica serves another machine's copy of a scope minted twice. A push whose answer was lost is confirmed by asking the replica before anything is undone. Every write of `keys.yaml` — by `rotate`, `run` or `key import`, the first one included — is atomic, runs under a lock every farcast process takes, replaces only the file its writer read (or, the first time, none), and refuses a `keys.yaml` that is a symlink or hard link. A sealed replica is left sealed and receives them on the next `storage unseal`. It names every keeper that must be re-enrolled, because each one's bundle now predates the rotation. Its output must state the scope in DataSphere's mandated terms: everything the cloud already saw **stays exposed** to whoever captured it, future data is protected once the cloud credentials are rotated too, and names stay exposed until name-key rotation exists. Rotation is nonce hygiene and keyring retirement, **not** compromise recovery, and an operator who believes otherwise has been actively misled. *(2026-11-17, ADR 0023 M2.6c, built, not walked: an interactive or `--yes` run reads the pin before it warns and asks, so a keyring that lacks a key the pin requires is refused before the question; it still rotates without a pin it cannot reach. `key rotate --plan` needs the instance's record. It prints the keys it would mint, one for the instance's key space and one for each application's scope, each named by what it is (`new key 1 of <scope>`), since an id is drawn only when a key is minted; with a keyholder deployed and at least one application scope it also prints the two pins and their writes: the hold, at the version read, which requires the new keys and retires nothing new, and the final pin, a replace at the version the hold produces, which retires every older key. With a keyholder it reads the pin and the cluster as the instance's reader, which `reader grant` must have verified; without one it reads no cluster. A keyring behind the pin is a block. `--confirm <digest>` opens the writer only after the comparison and refuses unless its cluster is the one the plan read; with an application scope it also refuses unless the pin is where the plan read it, and waits at most a second for this machine's clock to pass the newest key; then it mints. It writes each pin once, and only as the plan listed it. Another writer that moves the pin before the hold is written is `plan_changed`, with the new keys held by every replica and in use on none, as is a hold that is not the one the plan listed; a hold write that fails otherwise (a 500, say) keeps its own kind, the keys held and unused, and the result says the pin was not written. One that moves the pin after the hold, while the keys are being put in use or once they are, is `plan_changed` with the keys in use and the pin left at the hold (or at the other writer's): the result's pin line names `farcast storage key pin`, which writes the final one, then `storage key rekey`. A hand-over that ends where the plan did not say — the replicas never took the held keys, a replica refused them, or this machine was put back on its old keys — writes no further pin and fails unfinished, as an interactive run does. A record whose keyholder changed while it ran is `plan_changed`, once the new keys are saved and before anything is handed over. Its refusal without a terminal now ends `or --plan and then --confirm <digest>`.)*
- **`key rekey`** sweeps objects, rewriting each header's key ID and wrap fields under the active KEK **of the key space the object lives in** without touching a body — possible because the data AAD excludes the key ID. It accepts a bare `<instance>` as well as `<instance>:<prefix>`. It refuses to move any application's objects while this machine's keyring holds a key newer than the one it uses (a rotation that did not finish — run `rotate` again), and until every keyholder replica is serving and holds and uses exactly that application's current keys, because a replica without it could read nothing rekey moved; `--dry-run` reports that verdict too, and `storage unseal` is what brings every replica up to the current keys. `storage unseal` uses the same hand-over as `rotate` and `run`: it asks every replica what it holds first, never pushes one that did not answer, and while one is silent leaves a sealed replica sealed too — the silent one may serve keys this keyring lacks — unless `--unchecked` says this keyring is known to be current, **refuses** to push a keyring that is behind what a serving replica holds (keys or a scope it lacks, or an older key active — another machine rotated, or this keyring was restored or imported from before; pushing it would take those keys away), holds back any key a serving replica lacks until every replica holds it, pushes one generation above what every replica reports, and counts a replica unsealed only if it reports exactly the keys it was sent. When no replica ends up writing under this machine's newest keys, the summary line says which case it is, and the error after it says why. If none took them, it reads `No replica took this machine's keys; the reason follows.` If some hold them but missed the push that puts them in use, it reads `No replica writes under this machine's newest keys yet; N hold them. The reason follows.` *(Since 2026-11-10. Before, the first line also covered the second case, contradicting the rows above it.)* The JSON result counts those replicas as `held_only`, omitted when 0, beside `loaded` and `total`. `storage state` says how each serving replica's keys differ from this machine's keyring — a key or scope it lacks, a half-finished hand-over (harmless: it reads everything), or a keyring here that is behind — and names a keyholder image too old to report its keys, which `storage deploy` updates. It is resumable, reports a cursor when interrupted, and every object stays readable throughout because old keys remain in `keys.yaml`. It is also the most expensive command in the CLI: a full read and write of every object. `--dry-run` prints the cost first.
- **The keyholder refuses what the CLI refuses, itself.** *(Since 2026-10-08.)* A serving replica refuses a push lacking a key or scope it holds (`would-drop`) — so another machine pushing between this machine's read and its push is refused rather than caught by the next read; `storage seal` then `storage unseal` is the deliberate way past it. And every replica enforces the **key pin** ([ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md#the-in-cluster-key-pin-and-a-keeper-bound-to-its-bundle)): the KEK IDs every bundle must hold and those no scope may write under, written to a ConfigMap by `storage deploy`, `run` and `key rotate` (which therefore now needs `kubectl` and the instance's credentials) and handed to running replicas live. *(Since ADR 0023 M2.5, built 2026-11-15: the pin is read, created and replaced in-process as the instance's installer service account, with the key `install --credentials` stored. So `key rotate` and `key pin` need no `kubectl`, auth plugin or gcloud, for an instance installed with `--credentials` where service-account keys are allowed. Not yet walked against Google.)* A keyring the pin refuses is behind the instance even when nothing serves to show it, and `unseal` refuses it before pushing anything, naming what fixes it — an import for a keyring that lacks keys, and, for one that holds them all but writes under a key the pin retired — what an import leaves — `key rotate` while a replica serves the current key, or `key pin --replace` with every replica sealed and the machine that rotated gone; `storage unseal --below-pin` is the way past a pin no keyring can meet — the keys it requires are gone everywhere — and needs no cloud access. `storage state` reports each replica's pin against this keyring: current, behind (`key pin` raises it), refusing this keyring, absent, unreadable, or serving keys it would refuse.
- **`key pin`** writes the pin from this keyring and hands it to every replica, and reports any replica still enforcing a pin above this keyring rather than claiming it took this one. It only ever raises it; a keyring behind it is refused, and `--replace` lowers it after confirmation, saying what it lowers — on every replica whose live pin differs, even once the ConfigMap itself is no longer above this keyring. It is for when a command could not write the pin, or the ConfigMap was deleted. *(2026-11-17, ADR 0023 M2.6c, built, not walked: `key pin --plan` prints the pin it would write, what `--replace` lowers, and the ConfigMap write, reading the pin and the cluster as the instance's reader, which `reader grant` must have verified; a keyring behind the pin is a block without `--replace`. `--confirm <digest>` writes that pin once, at the version the plan read, after the writer's uid and pin reads agree with the plan, and with `--replace` lowers the pin and any replica found enforcing another without asking: the plan is the consent. Its refusal to lower without a terminal now ends `or --plan and then --confirm <digest>`. An interactive or `--yes` run is unchanged.)*

### `usage`, and surfacing spend honestly

Object count and stored bytes cannot tell an operator what storage costs, so `usage` reports the object count, the stored bytes the provider actually bills, the window over which they were written, and a monthly estimate. It deliberately takes **no prefix**: scoping to one would mean mapping stored names back to logical ones, which needs the keyring — and the whole point of `usage` is that it still works for the operator who has lost theirs. A silently ignored operand would be worse than an unsupported one, so a prefix is refused with that reason.

Two further figures are specified but **not yet implemented**, and both are worth having: the **envelope overhead** FarCast itself adds (~131 bytes plus a padded sealed name per object — a real, permanent, billed cost of the privacy pillar that no other tool can compute), and the report's own cost in list operations.

A third — **incomplete uploads** left by an interrupted `cp` — was specified and is **not implementable on GCS**, which the [Phase 3 validation run](../../docs/runbooks/phase-3-validation.md) settled. An unfinalized resumable session is invisible to a listing, reports zero bytes, exposes no enumeration endpoint (GCS has no equivalent of S3's `ListMultipartUploads`), and does not block bucket deletion. The failure it was meant to warn about — an interrupted upload stranding a teardown — cannot happen here, so the line has nothing to report and is dropped rather than left as a to-do.

Every figure carries its price basis: estimates are prefixed `~` and the output names the built-in price table's `as_of` date with a pointer to live pricing. A stale price presented as fact is worse than no price. `usage` also states its own cost in list operations, and runs without a keyring, so the operator who lost `keys.yaml` can still see what they are paying.

Cost is **surfaced, never gated**, per [ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md) decision 8: gating cents trains an operator to click through the ~$18/mo carrier gate that guards real money.

### The `storage:` record, and the ensure path

`InstanceMetadata` gains a pointer-typed `storage:` block mirroring `registry:` — `bucket`, `location`, `provider`, `recorded_at`, `created_at` — so pre-3.3 metadata still loads and converges on the next storage command.

The bucket is ensured **lazily, at first storage use**, never at `install`: an empty bucket costs $0.00 and serves nothing, and the registry's defensive-ensure precedent already proves lazy convergence. The record is written **before** the create call, because the name's 32 bits of entropy exist nowhere else and the name is deliberately not re-derivable from the instance (its instance segment may have been truncated to fit GCS's 63-character cap).

The mint/record/retry loop belongs here, in the record-owning caller, never in the adapter — which mints nothing. On `ErrNotOwned` it mints a new suffix, updates the record and retries, bounded at 3 attempts. **With one hard exception:** if `created_at` is set, the bucket was ensured successfully before, and `ErrNotOwned` now means something changed rather than a name collision — auto-minting past it would abandon the operator's data under a name nothing points at any more. That case stops and asks the operator to look. Any other error keeps the record and fails, so a re-run converges.

### `farcast storage deploy` — where the keyholder's image comes from

`farcast storage deploy <instance>` puts the keyholder's image into the instance's own registry ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)) by connect's rules (*Where FatLine's image comes from*, above; [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M1). By default it is the image this farcast carries, reused when the version tag under `system/datasphered` already holds exactly it and pushed otherwise. `--source <dir>` builds one from that checkout with this machine's Go, pushes it under `source-<12 hex>` and records it as operator-built; later deploys keep it until `--embedded` or `--source`. `--embedded` replaces an operator build, or an image another farcast version deployed, with the carried one; without it the latter is refused with kind `version_skew`. `--datasphered-image` deploys an image exactly as given, with no registry lookup, and must be digest-pinned (`repository@sha256:<64 hex>`). Each of these is a usage error before anything is loaded: `--datasphered-image` with `--source`; `--embedded` with `--source`; `--embedded` with `--datasphered-image`; `--embedded` on a farcast that carries no components; and a `--datasphered-image` that is not digest-pinned. A farcast that must not push what it carries is refused before the record is read. The keyholder then comes up sealed, and stays sealed until `farcast storage unseal`.

*(2026-11-17, [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.6c, built, not walked.)* **What it decides before it asks.** It reads the key pin, then decides the pin it writes, checks the instance's mTLS material (all six files there, `ca.key` among them, opening none but the CA certificate), reads the recorded registry with the installer's key and decides the image, all before the cost question; the bucket and keyring are minted, the registry ensured and the image pushed or built only once the deploy is agreed. A keyring the pin is above is refused there, before anything is minted, a first deploy's included (before, a first deploy found it only after creating the bucket). The cost question and its refusal without a terminal give the keyholder's cost in exact cents, the refusal ending `or --plan and then --confirm <digest>`. On an instance that records no registry an interactive or `--yes` run ensures it before reading it, once the pin, the uid and the mTLS material have been checked, as `kernel deploy` does after the namespaces; a run with no terminal and no `--yes` ensures nothing, and is refused, `instance "<name>" has no image registry recorded; …`, with nothing written. *(Until ADR 0023 M2.6c, built 2026-11-17, not walked, such a run was refused at the cost question, the registry ensured only after it.)*

**Its plan.** `--plan` prints the keyholder's standing cost and its figure on a cluster without bursting support, against the cost limit and the instance's floor; the image; the registry's ensure and push, and on a first deploy the bucket it creates, as `farcast-placeholder:bucket:<instance>`; the keyholder's leaf, and on a first deploy with no keyring here the keyring, as mints; a restart of a deployed keyholder's replicas, whose leaf is new; the pin it writes and its create or replace at the version read; each document it applies, over a placeholder leaf, the CA certificate and the planned bucket; and the bucket grant. A source build's plan binds its checkout's directory and Go, not what the checkout holds when `--confirm` runs, and says so in a notice. It reads the pin and the cluster as the instance's reader, which `reader grant` must have verified (there is no fallback), and opens no writer and no private key. A keyring behind the pin, or a pin the keyring itself would fail or no replica could read, is a block. `--confirm <digest>` recomputes it as the reader and, after the comparison, opens the writer, which must reach the cluster the plan read, and reads the pin, which must be where the plan read it, before anything is minted; after minting a first deploy's storage it reads the record again, and refuses, `plan_changed`, a keyholder, bucket, storage provider or location other than the plan's, having written only the bucket and keyring; it writes the pin once, at the version read. Its plan is the consent to replacing an image another farcast version deployed.

## `farcast secret` — the values an application must not carry in its image (Phase 5.3)

`farcast secret` provisions database passwords, API tokens and signing keys for the applications an instance runs. An application reads them through the SDK with [`farcast.Secrets()`](../../sdk/go/README.md#secrets--farcastsecrets); it cannot write or delete one.

Like `farcast storage`, it runs **entirely on the operator's machine** — the recorded bucket, the stored cloud credentials, the local keyring — so it needs no tunnel and no running cluster.

```
farcast secret set <instance> <namespace>/<app> <NAME> [--from-file PATH] [--raw] [--force]
farcast secret ls  <instance> [<namespace>/<app>]
farcast secret rm  <instance> <namespace>/<app> <NAME> [-y]
```

### Why an application is named `<namespace>/<app>`

Because both halves are real. An application is one entry in a manifest's `apps:` list; the namespace is the manifest's top-level `name`, overridable with `--namespace` and not derived from the repository. The same manifest deployed under two namespaces is two sets of applications with **two sets of keys**, and a secret set for one is not a secret for the other — so a bare application name would be a guess about which one you meant.

### Where a secret goes, and what that protects

Each secret is an ordinary object under `app/<namespace>/<app>/secrets/<name>` — inside that application's **own scope**, with its own name key and KEK — written with this instance's keys. The cloud provider holds ciphertext under a tokenized name, and **nothing is ever placed in a Kubernetes Secret**, which is base64 in etcd encrypted under a key the provider holds.

**The boundary is the application.** A neighbour's keys cannot compute the stored name of this secret, let alone open it, and its leaf does not reach this scope to ask ([ADR 0018](../../docs/adr/0018-thin-device-storage.md) decisions 1 and 5). That was not true before: [ADR 0017](../../docs/adr/0017-application-secrets.md) records the boundary as the *instance*, which is what it was when every application shared one scope.

What is enforced on top: the keyholder refuses application writes and deletes under the subtree, so a secret is created and removed by you and by nobody else — including by the application it belongs to.

An application's scope is minted when `farcast run` deploys it — and handed to the keyholder there, so the application does not start into one that has never heard of it. A `secret set` for an application that was never deployed is refused rather than stored somewhere nothing will look.

`run` will not unseal a **sealed** keyholder to do it. Pushing a bundle to a sealed keyholder is an unseal, and a deploy performing one would hide a seal you have not seen — or clear a hold you placed. It deploys anyway, says the scopes are waiting, and names `farcast storage unseal`.

### There is no `--value`, and there is no `get`

The value is read from stdin, or from a file with `--from-file`:

```bash
printf '%s' "$PASSWORD" | farcast secret set prod api DB_PASSWORD
farcast secret set prod api TLS_KEY --from-file ./key.pem
```

A value on the command line is visible to every process on the machine while the command runs, and it lands in shell history — so there is no flag that takes one. And there is no read-back verb: a secret printed to a terminal is in scrollback, in a screen share, and in whatever recorded the session. That is a guard rail rather than a lock — the keyring is the operator's, so `farcast storage cp` can always recover the bytes deliberately, with the key in hand.

**A trailing newline is removed, and the removal is reported.** `echo x |` appends a byte that is the shell's and not the operator's, and a credential one byte longer than the one in the provider's console is a long afternoon. `--raw` keeps it. Acting and saying so beats both silent choices.

`set` refuses an empty value (use `rm`), refuses to replace an existing secret without `--force`, and caps a secret at 64 KiB — something larger is a file, and files belong in `storage cp` where they stream.

### Applications deployed before ADR 0018 need `farcast run` again

Since [ADR 0018](../../docs/adr/0018-thin-device-storage.md) decision 1 the keyholder's data path admits only callers that present a leaf from the instance CA. `farcast run` mints one per application and delivers it beside the egress credential; the SDK presents it. An application deployed **before** its instance's keyholder was upgraded holds no leaf and is refused the moment the new keyholder starts — reported by the SDK as `ErrStorageUnavailable`, not as a seal. `farcast storage deploy` says so when it upgrades, and `farcast run` again is the remedy. There is deliberately no mode in which the keyholder waits for stragglers: that would be the fail-open the decision forbids.

### The one thing that would fail silently

The operator writes a key that an application reads, and the two are computed in different packages: the CLI from the keyring, the application from the `FARCAST_SECRETS_PREFIX` Planck rendered from the recorded scope prefix. A divergence would not fail loudly — it would store a secret nothing ever fetches.

So `secret` resolves the prefix from the **keyring**, which is the material that actually encrypts the object, and a test renders Planck's ConfigMap and asserts the two agree character for character.

## `farcast keeper` — unattended recovery on your own hardware (Phase 5.4)

[ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md) concedes something plainly: key material lives only in the keyholder's memory, so after a 03:00 node upgrade applications get `ErrStorageSealed` until a human runs `storage unseal`. Nothing is lost and nothing is corrupted — and storage is down for hours.

A **keeper** is the lawful automation of that human. The theorem in that ADR leaves exactly one option: an external party supplying an input the cloud does not hold. A keeper is an operator-owned device doing precisely that, and **running FarCast as a server wants at least two of them** — one device is one power cut away from the window this exists to close.

```
farcast keeper request <instance> --out <path> [--replace] [--accept-backup-risk]
farcast keeper enroll  <instance> <device> --request <path> [--key-sha256 <hex>] --out <path> --passphrase-file <path>
farcast keeper install <packet> --passphrase-file <path> [--accept-backup-risk]
farcast keeper run     <instance> [--interval <duration>] [--once]
farcast keeper status  [instance]
farcast keeper revoke  <instance> <device> [-y]
farcast keeper uninstall <instance>
```

**Enrolment is by request** ([ADR 0020](../../docs/adr/0020-instance-pki-ecdsa-p256.md) decision 3, built 2026-11-13). A device's private key is made on the device, and FarCast never sends it anywhere: no request, packet or command carries it. On a desktop it is a 0600 file under the keeper directory's rules, not bound to hardware ([ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md) finding 2), and with `--accept-backup-risk` a backup may still copy it:
1. **`keeper request`, on the device**, makes a P-256 key in the device's keeper directory, under the rules `install` applies (a synced folder is refused, the backup exclusion is read back, 0700/0600), writes a PKCS#10 request carrying only the public half, and prints the key's fingerprint as two lines of eight groups. The request holds no secret. One request is pending per instance; `--replace` discards it, and a packet issued for the discarded one is then refused.
2. **`keeper enroll --request`, on the operator's machine**, checks the request (a P-256 key, signed with ECDSA-SHA256, and nothing else in it honoured) and issues only once the fingerprint is confirmed against the device's screen: `--key-sha256` with the 64 characters, or, at a terminal, typed when asked — all 16 groups or at least the last 8. Nothing of the fingerprint is shown before it matches, so it cannot be copied off this screen; it is printed once confirmed. From this machine's records, enroll refuses a key already certified for another device or instance, one certified before a revoke (kept in `revoked_key_sha256`, which nothing clears), and a device's older key; it re-issues only to a device's newest key while the device is not revoked. A released instance's records are gone, so its keys are no longer remembered, and an instance enrolled from another machine was never seen here; the fingerprint confirmation still stands in front of them. The packet carries a certificate and the bundle, and no private key.
3. **`keeper install`, on the device**, writes the certificate and the bundle beside the key `request` made there and moves the key into place. A certificate for any other key is refused **as a security event**, with nothing written: either the packet is another device's, or the request was replaced on its way and someone else's key was certified under this device's name — the message names both fingerprints and the remedy (revoke, rotate, enrol again from a new request). The certificate must also chain to the packet's CA as a client certificate, checked at the later of now and its start, so a device whose clock lags the operator's still installs.

`enroll` and `revoke` run on the machine holding the CA key. `request`, `install`, `run` and `uninstall` run on the device — `uninstall` wipes its bundle and leaf key, and a pending request's key, and keeps its ledger and record; on a directory holding only a pending request it discards that. `farcast release` does the same to a keeper installed on the releasing machine, a pending renewal included, and reports a directory holding only a pending request as untouched, since nothing proves which instance it was for. `status` runs on either and reads whatever ledgers that machine has. On the machine that enrolled the fleet it also lists each device with its expiry and budget, and totals the budgets of the devices that can still push, per window: two devices at 8 a month admit 16 re-seeds a month, which no one device's status shows. That is a total of limits — what each device has used is in its own ledger, on that device. (Since 2026-11-09; a device enrolled before then has no window recorded, and status says to re-enrol it to count it.)

**The packet in transit.** `enroll` writes a packet carrying the bundle and the device's certificate, and no private key *(since 2026-11-13, [ADR 0020](../../docs/adr/0020-instance-pki-ecdsa-p256.md); before then it carried the leaf's key and, with its passphrase, was the device)*. Anyone holding the packet and its passphrase can read what is stored under the keys its bundle carries, and `revoke` does not retire the bundle — rotating does (see *What `revoke` does not do*). It cannot re-seed through the tunnel, provided the fingerprint was confirmed: the leaf it carries certifies a key the packet does not carry. Losing it loses nothing; make a new request and enrol again. So write the packet and the passphrase file outside every directory a desktop indexer or sync client reads — not directly in `~`, nor `~/Documents`, `~/Desktop` or `~/Downloads`, but under a directory such as `~/.config/farcast/` — and delete both once `install` has run. (The 2026-11-10 walk left both directly in `~` on a Linux device, where GNOME's file indexer made their names searchable; the keeper directory under `~/.config` was not indexed.) The same handling applies to the request file: it holds no secret, but a request substituted on its way is what the fingerprint confirmation guards against, and a file nobody is reading is one nobody substitutes.

### What a pass exits with

`keeper run --once` is for a timer, and a timer reads the exit status. *(Since 2026-11-10; before then every refusal exited `0`, so a keeper that could no longer keep looked like one that had.)*

| Code | The pass found |
|---|---|
| `0` | **kept** — every replica is serving, was just re-seeded, or is held on purpose by the operator. A hold is still reported on stderr every pass; it is the state the operator asked for, and alarming on it would teach the alarm to be ignored. |
| `3` | **cannot keep, a person must act** — a stale bundle (including one the fleet has moved past while every replica is still serving), a replica that cannot read its key pin, a spent budget, or a leaf that does not bind its bundle or has expired. The last two are checked on the device before it dials. |
| `4` | **incomplete** — a replica or the tunnel did not answer, a re-seed could not be checked beside a replica that did not, or another keeper pass on this device was running. The next pass retries. |
| `1` | a fault on this device: its store, ledger or bundle could not be read, or its ledger would not take a write. |

**A re-seed is recorded before it is pushed, and is not pushed when that write fails.** *(Since 2026-11-10.)* The keeper appends a `pending` entry, makes the push, then appends the outcome (`ok`, `refused-after-send` or `refused`), which settles it. Both entries carry the same random push id, and only that push's outcome settles that `pending` entry. When the `pending` write fails, the replica is reported as `ledger-unwritable` and nothing is pushed. Until then the entry was written only after the push, and the budget is read back from the ledger on every pass, so a ledger that read but no longer wrote — mode 0400 after a restore, a read-only remount, a full disk — let every pass push and counted none of it: a cluster that restarted its replicas between passes was re-seeded without limit. A `pending` entry that nothing settles is a push whose outcome was lost. The budget counts it as a re-seed that succeeded, and so does the audit, which cannot rule out that key material moved; `keeper status` names it `unconfirmed`. A keeper killed between the two writes leaves one too. That spends a budget slot on a push that may not have happened, which is the safe direction. It can also raise the audit's alarm: when the killed push never landed, the next pass re-seeds the same still-sealed process, and `keeper status` lists that process as re-seeded twice, with `1 unconfirmed` on its row. A solicitation looks the same, so the row stays; the note says which reading it could have. A write that failed part-way (a full disk, a crash) leaves a fragment at the end of the ledger. The next entry starts on a line of its own, so the fragment is skipped and the entry is not lost with it.

**A refusal after the bundle was sent counts.** *(Since 2026-11-10.)* The bundle is sealed to the key in the challenge, and the challenge comes from whatever answered. [ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md) finding 1's solicitor holds the keyholder's server leaf, so it can answer, read the bundle, and refuse it. So a refusal that arrives after the request was written (`already-serving`, `below-pin`, `keeper-bundle`, `pin-unreadable`, or any other error after that point) is recorded as `refused-after-send`. The budget counts it, and so does the audit, against the process it names. Only a push that sent nothing (no dial, no handshake, no challenge) is a plain `refused`, and only that one costs nothing. Before this, a solicitor that refused every push spent none of the budget and left the audit clean. A push that loses a race to another pusher, such as the operator's `storage unseal` or another device's keeper, now spends a slot. That is the safe direction. A `refused` line written before 2026-11-10 could be either kind and is not counted.

**One pass at a time on a device.** *(Since 2026-11-10.)* A pass holds an exclusive lock (`pass.lock` in the keeper's directory) for as long as it runs. A second `keeper run` on the same device that finds the lock taken pushes nothing, writes nothing and exits `4`; in a loop it reports `check failed: another keeper pass on this device is running…` and checks again. Without the lock, a timer's `--once` and a manual one could both read a restarted replica as sealed and both push into it. The second push would be refused after sending, and one restart would spend two slots and read as a process re-seeded twice. The lock is `flock`, so it is released when its holder exits, however it exits. On platforms without `flock` there is no lock, and the push ids still keep each push's two entries paired.

A ledger that would not take a write outranks `3` and `4`, because the budget and an audit both read the ledger. That pass still reports every replica on stderr and exits `1`. Its error says which write failed — `this device's ledger did not take the entry a re-seed is recorded in before it is pushed, so none was: <cause>`, or `the outcome of a re-seed was not recorded in this device's ledger, so the budget counts it as done and an audit reads it as unconfirmed: <cause>` — followed by `(the pass also found: <reason>)` when the pass would otherwise have exited `3` or `4`.

What each replica got is on stderr either way; the exit status is the summary. Without `--once`, `keeper run` never exits on any of these — it reports and checks again (a fault prints `check failed: …`), because a keeper that exited on a refusal or a dead tunnel would be absent for the next restart, which is what it is for. Under systemd, `SuccessExitStatus=4` is the deliberate opt-out for transient failures on a timer unit; nothing makes `3` quiet, because it does not go away on its own.

### What a keeper holds, and what it therefore cannot do

A derived **scope bundle** and its **own device leaf**, whose key it made itself — nothing else. That bundle is exactly what an unsealed keyholder already holds in RAM, which is the property that lets a device push one without widening what a compromised cluster can yield.

It does **not** hold the master keyring, so it cannot read names outside its scopes. It does **not** hold the instance CA key, so a stolen keeper can re-seed and **cannot enrol another keeper**. Losing a keeper is losing a device; losing the operator's machine is still losing the instance.

Each device gets `farcast://<instance>/keeper/<device>` as its identity, so one can be revoked without revoking the fleet, and a ledger entry can say which device produced it. Since 2026-10-08 the leaf also **names its bundle** — a second URI SAN carrying the digest of the exact bundle the device was given — and the keyholder refuses a keeper's push of any other bundle (`keeper-bundle`), so a stolen leaf cannot carry keys of its own making. A leaf enrolled before that names none and is refused outright; `keeper run` says so before it dials. Re-enrol every keeper from before 2026-10-08. FatLine's tunnel admits a keeper leaf to the keyholder's route and no other.

**Which device was that, answered on this machine only.** *(Since 2026-11-10, [ADR 0015](../../docs/adr/0015-what-the-boundary-can-measure.md) decision 7.)* FatLine and the keyholder log a tunnel peer by role and never by device, because their logs are provider-readable. FatLine's key is `peer_role` (`peer_role=keeper`), and the keyholder's is `role` (`role=keeper`), so a search of both needs both keys. Shrike's picture attributes each stream to an opaque token of the leaf that opened it (v2: over the leaf's signed body, [ADR 0020](../../docs/adr/0020-instance-pki-ecdsa-p256.md) decision 4), and `enroll` records the token of every leaf it issues to a device (`leaf_tokens`, oldest first, kept across re-enrolment and revocation, since an older leaf stays valid in the cluster to its own expiry). `farcast usage` turns tokens back into names in its **Tunnel** section — `operator`, `keeper <device>` marked revoked, expired or an earlier leaf, or `keeper (leaf not enrolled from this machine)`. A device enrolled before 2026-11-10 shows as that last one until it is re-enrolled from here: the machine never kept the leaf, so its token cannot be backfilled.

### The four refusals

A keeper is an automaton holding key material, so the question it answers each cycle is *"is there any reason not to"* — and re-seeding is what is left when there is not.

1. **An operator hold is never a keeper's to clear.** "Sealed because it restarted" and "sealed because you said so" are different states. The keeper refuses locally, before dialling; the keyholder refuses again if it is asked. Two checks, because the local one can be modified and the in-cluster one cannot.
2. **Beyond its budget it refuses** — 8 reseeds per 30 days by default, which is well above what Autopilot actually does to two replicas. The refusal *is* the alarm. Widening the budget is not the fix for it.
3. **A bundle the fleet has moved past is stale**, and it says to re-enrol rather than pushing retired keys: a serving replica holding a key or scope the bundle lacks, or writing under a newer one — and, since 2026-10-08, the instance's **key pin** refusing the bundle, which is the reference that remains when every replica has restarted. The keyholder enforces the same pin itself, so a keeper modified to skip this check is refused there (`below-pin`). That verdict is the fleet's, not one replica's, so a pass prints it once (`this device: stale-bundle — …`) and each replica it stops points to that line. And it is printed whether or not anything is sealed: since 2026-11-10 a keeper learns it is stale at the rotation, while every replica still serves, rather than at the next restart — the outage it exists for.
4. **A synced folder is refused outright**, and that one cannot be overridden. A backup is a periodic copy; a synced directory is a continuous upload, and installing a bundle into one puts it in somebody's cloud before anyone looks.

One more refusal is not about the device at all. A replica that cannot read its own key pin refuses every re-seed whatever the bundle, and the keeper reports it as `pin-unreadable` — the keyholder's own refusal code — and leaves that replica alone, while still re-seeding another whose pin is sound. The operator's `farcast storage key pin` repairs it; re-enrolling the device changes nothing. (Until 2026-11-10 it was reported as `stale-bundle`, which asked for exactly the re-enrolment that would not help.)

### The ledger, and why the budget is not the control

The budget is a **tripwire, not a barrier** — a patient adversary simply stays under it. What actually catches a solicited push is reading the ledger, and `keeper status` is what reads it.

The question it asks is not *"how often did we re-seed"* but **"how many distinct keyholder processes did we re-seed"**. `datasphered` mints a random boot label per process and serves it only on the mutually-authenticated control surface; a keeper records which process it seeded. A process is sealed once per restart, so:

- one reseed per process is a cluster restarting and a keeper doing its job;
- **two pushes into the same process** means something asked for key material a live process already held.

A keeper writes two entries per push, `pending` before it and the outcome after, both carrying the push's id, and the audit reads each push through its outcome. One whose outcome was lost counts as a re-seed into the process its `pending` entry names, and status lists it as `unconfirmed`. One refused after the bundle was sent counts as a re-seed too, listed as `after send` (see *What a pass exits with*). A process re-seeded more than once that includes either kind says so on its row. Such a row can be read more gently, as a killed keeper or a lost race, but it cannot be told apart from a solicitation. In `--output json`, `refused` counts only the pushes that sent nothing, and `refused_after_send` counts the others, which are in `reseeds` too.

That is detection by audit, and it is named as such: it runs when you run it, it is not a live alert, and against a cloud that reads the keyholder's memory directly it says nothing at all. Read it anyway — it is what is left after the tripwire.

### What `revoke` does not do

It marks the device withdrawn in your records. It does **not** reach the cluster, and the device's certificate stays cryptographically valid. What retires a lost device's *bundle* is rotating the keys it holds — `farcast storage key rotate`, then `farcast storage key rekey`, then re-enrolling every keeper you keep — and the command prints that sequence rather than implying it happened. It used to print `farcast storage rekey`, which was never a command, for a pair that reached none of a bundle's keys; a test now resolves every command the CLI advises against the real command tree. Rotation bounds the damage forward, not backward: anything that device already read, it already read; and names stay computable, because a scope's name key cannot rotate. Once the rotation has moved the instance's key pin, a replica that restarts refuses the device's bundle — the one its leaf binds, the only one it can push — whether or not anything is still serving to compare with (`below-pin`); rekey is for the ciphertext already stored, not for this. The pin protects only while a replica has loaded it: one that starts without it checks nothing, `farcast storage state` reports that as "none loaded", and `farcast storage key pin` restores it. Until the rotation writes the pin, the device can re-seed a replica that restarts, with the keys it holds — which are today's keys; a replica already serving refuses a re-seed, and `storage state` flags any replica serving keys other than this machine's keyring. Until its certificate expires it can still reach the keyholder and read each replica's state; it cannot release an operator's hold. The generation is no sign of it: anything holding a bundle can push one at whatever generation it chooses.

There is one automatic bound, which was already there: keeper leaves carry the CA's ordinary **90-day validity**, so an un-renewed device stops keeping on its own. `keeper status` warns before that arrives rather than after a keeper has silently stopped.

### At rest on the device, stated without softening

The material comes to rest **unarmored**, and that is what a keeper is: a device that re-seeds at 03:00 cannot hold a passphrase behind a human. What protects it is mode 0600 inside a 0700 directory, marked excluded from the platform's backup pipeline with the exclusion **read back** — a setter nobody checked is an intention, not a guarantee.

On macOS that check is real. On other platforms there is no single pipeline to exclude from, so `install` **refuses** unless you pass `--accept-backup-risk`, and the device's own record then says you did.

What is **not** delivered is hardware binding. On a desktop the bundle is a file that anything running as you can read. Binding it to machine identifiers was considered and rejected as obfuscation — those identifiers are readable by whatever can read the file. The hardware-backed class waits for the mobile keeper in 7.5.

## `farcast build` — build an image inside the instance (Phase 4.2)

`farcast build <instance> --repo <url> --app <name>` runs the application's Containerfile as a one-shot Job **in the instance**, not on this machine. [ADR 0010](../../docs/adr/0010-application-image-builds.md) chose that so running and updating software is not tied to one prepared laptop: the instance clones the repository itself, and this machine never needs the source, a container engine, or the repository's credentials.

### The builder image must be pinned, and the command helps you pin it

A builder runs arbitrary build steps while holding a credential that can write to your registry — the single worst place in FarCast to accept a floating tag. So `--builder-image` must be digest-pinned.

Pass a tag and the command **resolves it, reports the digest, and then refuses**. That is deliberate: resolving on every build would be trust-on-first-use rather than pinning, and the next build would silently run whatever the tag points at then. The refusal is how you obtain a value to record.

There is no default. Kaniko was archived by Google in June 2025, and the fork ADR 0010 chose (`cgr.dev/chainguard/kaniko`) stopped answering anonymous pullers; [ADR 0011](../../docs/adr/0011-build-toolchain-mirroring.md) decision 4 settles on the archived `gcr.io/kaniko-project/executor:v1.23.2` as a named stopgap, and the refusal names it. Shipping a digest nobody in this project has verified would be worse than asking for one.

### How the digest comes back

Kaniko writes the digest it pushed to `/dev/termination-log`, which Kubernetes surfaces in the Pod's status — so the CLI reads it from the API server with no log parsing and no shared volume. It is validated as a *complete* sha256 digest before use: a truncated one would build a reference that looks pinned and names nothing, and the image may well have been pushed by then.

### What it prints, and why it cannot do it for you

The builder pushes under its own cloud identity, so the `farcast-builder` ServiceAccount needs `roles/artifactregistry.writer` on the instance's repository through Workload Identity. The command prints that grant rather than applying it — granting it needs permission to change a repository's IAM, which this CLI's credential is not required to carry. Same reasoning, and same shape, as the keyholder's bucket grant ([ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md) decision 8). Without it the build fails on a 403 at push.

A failed build prints the build's **own** output before failing, and says how to read more — the Job survives an hour so `kubectl logs job/…` still works. Repeating "the build failed" would help nobody; the Containerfile already said why.

### Its plan

*(Since [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.6, built 2026-11-17, not walked.)* `build <instance> --repo <url> --app <name> --plan` binds the eight flags that shape the build, `--app`, `--builder-image`, `--containerfile`, `--context`, `--git-secret`, `--ref`, `--repo` and `--tag`, each as given, an empty one as empty. Its facts are, in order:
- the build: the repository, ref, app, Containerfile and context as given, and the tag and the destination it pushes to;
- its cost: one Job, at the CPU, memory and deadline it is rendered with, against the cost limit, with nothing standing, and the instance's floor and whether the limit is below it;
- the builder image, `named` by `--builder-image` or `recorded` by the instance, with the one recorded, if any;
- one write for each of the three documents it applies: its ServiceAccount, its NetworkPolicy and the Job.

It reads the record alone: no cluster and no `credentials.yaml`. A builder given by tag is looked up anonymously at its own registry, as without `--plan`, only to be refused with the digest to pin; that is a usage error, and no plan is printed. An instance with no kernel or no registry recorded is refused before any plan, as it is without `--plan`. A flag value that is not UTF-8 is refused while the plan is made, and never quoted. `--confirm <digest>` computes the plan again and compares it, and only then opens the writer, checks this machine for kubectl, reads `farcast-system` once as the writer, applies exactly the three documents the plan bound, and waits for the Job, asking nothing ([plans and confirmation](#plans-and-confirmation)).

Two things changed for every run with it *(2026-11-17, ADR 0023 M2.6, built, not walked)*. Without a terminal and without `--yes`, the refusal names the plan route, `building runs a 1 vCPU / 2048 MiB Job in the instance until it finishes or its deadline expires; pass --yes to confirm, or --plan and then --confirm <digest>`. And the documents are checked as a plan checks them (the stream check, `kube.SplitStream`) before the question, so a value that check refuses, such as a `--builder-image` that is not UTF-8, is refused in every mode, never quoted, where it used to reach kubectl. The order of an interactive or `--yes` run is as before: the writer opened and read, the builder resolved, the documents rendered, the question asked.

At 4.3 `farcast run` reads the manifest and calls this for each app. Today the app and its Containerfile are given explicitly.

## `farcast kernel` — the in-cluster kernel (Phase 4.1)

`farcast kernel deploy <instance>` puts TechnoCore's image into the instance's own registry ([ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)) by connect's rules — the image this farcast carries, `--source <dir>` to build one with this machine's Go (recorded as operator-built), `--embedded` to replace an operator build or another farcast version's image, and `--technocore-image`, which must be digest-pinned, to deploy one as given; `--technocore-image` with `--source` is a usage error ([ADR 0023](../../docs/adr/0023-one-download-farcast.md) M1) — then applies its workload: a ServiceAccount, a ClusterRole bound per-namespace, a Role pinned to one ConfigMap, and a single-replica Deployment.

### What it deploys, and what that costs

One replica at 100m/128Mi — about $4/month, derived from [`technocore/deploy`](../../technocore/deploy/)'s own declared requests so the figure in the prompt cannot drift from the manifest applied. The gate names that, names what the kernel will do once running, and — when the instance's limit is below its floor — prints the breakdown, says which lines the kernel meters (every Pod, and since 2026-10-08 the load-balancer carrier) and which it cannot (the modelled cluster line), and says what that means: below the metered part, a shutdown cannot close the gap; between it and the modelled total, the bill can pass the limit with nothing the kernel counts and nothing it can stop.

**Nothing is fetched, built or run without a kernel.** *(Since 2026-10-08.)* `farcast run` and `farcast build` refuse, before fetching or building anything, on an instance with no kernel whose deploy applied — a namespace the kernel does not meter has no `expected` spend and cannot be stopped by a cost shutdown, so a workload there is outside the limit entirely. There is no override; the kernel is a few dollars a month. `kernel deploy` always meters `farcast-system`, where every fetch and build Job runs. What it does not cover, stated: FatLine, the carrier and the keyholder bill from `connect` and `storage deploy` until the kernel is deployed, and the kernel does not back-bill that time; a namespace whose metering fails after its workloads apply runs unmetered, and `run` says so (`NOT METERED`, with the fix); and the lines `farcast costs` lists as *Not metered* are caught only by `confirmed`.

**Its tuning is recorded.** `--adapt` (ADR 0016), `--adapt-cooldown` (default 6h, 1m–720h) and `--interval` (default 30s, 5s–5m) are rendered as visible arguments, refused outside their bounds before anything is built, recorded in `metadata.yaml`, and carried forward by every later `kernel deploy` that does not name them. `--adapt=false` turns adapting off and `=0` restores a duration's default. Before this a routine redeploy — an image bump, a changed limit — silently switched adapting off; it also dropped the record of confirmed costs, which `kernel confirm` then overwrote in the cluster, and both are kept now.

*(Reordered by ADR 0023 M2.6c, built 2026-11-17, not walked.)* A deploy reads the namespaces the instance has, then decides the image, and only then asks: it reads the registry the record names with the installer's key, mints its token and looks the version tag up before the cost question, and ensures the registry, pushes or builds only after the answers, the build question last. Until then the registry was ensured and the image pushed after the cost question, and the build question came after the ensure. What it prints while it decides (a metered namespace dropped, the knobs' notes, an image kept or replaced, a foreign tag, the warning when no reader binding can be added) prints once, before the question; the note that an image was replaced still prints once the new one is in the registry, and a version skew is refused before the image's own lines. An interactive or `--yes` run on a record that names no registry ensures one first, after the namespaces are read, so a namespace that does not exist is still refused before any Google write; a run with no terminal and no `--yes`, which the cost question would refuse, ensures nothing, and is refused, `instance "<name>" has no image registry recorded; …`, with nothing written. *(Until ADR 0023 M2.6c, built 2026-11-17, not walked, it was refused at the cost question, the registry ensured only after it.)* The question and its refusals without a terminal state the cost in exact cents (`~$3.70/month`, where they said `~$4`), and those refusals end `, or --plan and then --confirm <digest>`. The knobs' bounds are checked from the flags and the record before anything is opened. *(Since ADR 0023 M2.6c, built 2026-11-17, not walked: `--interval` and `--adapt-cooldown` take whole seconds, as the plan states them; another value, `--interval 5.5s` say, is a usage error in every mode. A plan refuses a recorded knob that is not whole seconds, which an earlier farcast could record, `internal`, naming the knob and the flag that replaces it, rather than show it other than it is applied; an interactive or `--yes` run deploys it as recorded.)*

**Its plan** *(since ADR 0023 M2.6c, built 2026-11-17, not walked)*. `kernel deploy <instance> --plan` binds `--adapt`, `--adapt-cooldown`, `--embedded`, `--interval`, `--namespaces`, `--source` and `--technocore-image`, each as given, and the three knobs as empty when not given: what the kernel runs with is its own fact. Its facts are, in order: the cost (the kernel's replica, the cost limit, the instance's floor fully provisioned, and whether the limit is below it, which is a fact confirming consents to, as `--yes` deploys past it, never a block); TechnoCore's image, as on `connect`; the kernel's settings (adapting, the cooldown and the interval as recorded, the namespaces it meters, and the reader bound in them); the registry's cloud facts, the ensure and then a push when the image goes into the registry; one write for each document of the stream it applies, the reader's RoleBindings among them; and its notices. A source build's plan binds its checkout's directory and Go, not what the checkout holds when `--confirm` runs, and says so in a notice. It reads the cluster as the instance's reader: the namespaces the instance has, and `farcast-system`'s uid, which it binds as its target. So it needs a reader `reader grant` has verified, with no fallback to the installer's account: without one, `--plan` and `--confirm` are refused, `credential_missing`, `'farcast kernel deploy --plan' reads the cluster as instance "<name>"'s reader, whose state is <state>; <what to do>, or run the command in a terminal` (`--confirm` in place of `--plan` under `--confirm`), before the reader opens and before `credentials.yaml` is read. It reads the registry, in every plan and with `--technocore-image` too, with the installer's key, which an install with Application Default Credentials is refused for before the provider opens. A namespace `--namespaces` names that the instance lacks blocks the plan, `internal`, with `cannot meter <names>: no such namespace in this instance.` as its first line, and nothing more is read. It opens no writer, runs no kubectl, ensures, pushes and builds nothing, and records nothing. `--confirm <digest>` computes the plan again as the reader and compares; prints what the plan says; opens the writer, checks this machine can apply, and reads `farcast-system`'s uid as the writer, which must be the one the plan read, or it is refused, `plan_changed`: `instance "<name>"'s cluster is not the one its plan read: farcast-system's uid is <uid>, not <uid>; nothing was written; run the same command with --plan instead of --confirm`; then ensures the registry, pushes or builds the image it compared, asking nothing, and records and applies as before.

### The limit it enforces is the instance's own

The cost limit reaches the container as arguments rendered from `metadata.yaml`, so a kernel can never be deployed enforcing a number the operator never chose. What was deployed is recorded back into `metadata.yaml` **before** the apply, like every other billable thing this CLI creates: a workload the local state does not know about is one nobody will think to tear down. The record includes the limit the *deployed* kernel is enforcing, which is not necessarily the instance's current limit — when they diverge, the cluster is still acting on the old one until the next deploy.

### It refuses more than it accepts

- An instance that is **not connected** — there is nothing to meter yet, and a cost enforcer with nothing to enforce against is a standing charge for nothing.
- An instance with **no recorded cost limit** — the kernel would meter it and never act, which is the one configuration that looks like cost control and is not.
- Anything the manifest itself refuses: an image that is not digest-pinned, a zero limit, a metered namespace under `kube-*` ([ADR 0003](../../docs/adr/0003-gke-autopilot.md) puts the managed namespaces out of bounds).

### `farcast kernel confirm` — the confirmed half of the two-signal model

The kernel meters continuously from declared resource requests. That figure is **`expected`**, and it is what protective action fires on. `farcast kernel confirm <instance> --amount <n>` supplies **`confirmed`**: the provider's own number for a window that has closed, which arrives late, never drives an action, and exists to correct the estimate and calibrate the model behind it.

This is [ADR 0009](../../docs/adr/0009-technocore-kernel-and-cost-metering.md)'s channel B1 — the operator's machine already holds the cloud credential, so it reads the bill and pushes the number. No billing credential ever enters the cluster: reading billing in-cluster would need a grant scoped to a *billing account*, which spans every project the operator owns.

**Windows must not overlap, and the default continues from where the last push ended** — with no `--from` it starts at the end of the last window pushed this period, and with no `--to` it ends at today's UTC midnight. Running it daily therefore appends one window per day with no bookkeeping. A second run on the same day has an empty window and says so rather than failing, because a cron job doing exactly the right thing should not be noisy.

An overlap is refused *here*, not left to the kernel: the kernel's only recourse would be to skip the window in silence, which looks identical to a confirmation that worked. Refusing at the point of entry means the operator finds out while they still have the invoice open. The push is recorded locally before it is applied, and rolled back if the apply fails — a confirmation the cluster never received would be skipped by the next push and the window would go unconfirmed forever.

**Zero is a real answer.** An idle window genuinely cost nothing, so `--amount 0` is accepted and is distinct from omitting the flag — the same distinction the kernel keeps between "no confirmation yet" and "confirmed zero", carried through to the command line.

**Its plan** *(since ADR 0023 M2.6, built 2026-11-16, not walked)*. `kernel confirm <instance> --amount <n> --plan` binds `--amount` as the number it parsed, and `--from` and `--to` as the days they resolve to. Its facts are the confirmation (the window, its amount in cents, the UTC day it is dated, and every window the record holds after it) and the one ConfigMap it would apply, `technocore-confirmed`. It reads the record alone: no cluster, no Google API, no `credentials.yaml`. An empty window is a plan too, with its `Nothing to confirm` line as a notice and no write, and under `--confirm` it is compared before it says anything. A missing `--amount`, a window outside the period and an overlap stay usage errors in every mode, raised before any digest is compared. Because the plan binds the UTC day, as the window's default end and as the confirmation's date, a plan made on one day does not confirm on the next: it is made again ([plans and confirmation](#plans-and-confirmation)).

Four things changed for every run with it *(2026-11-16, ADR 0023 M2.6, built, not walked)*. A confirmation is dated the UTC day it is made, where it held the instant. A non-finite `--amount` (NaN or an infinity) is refused before anything is recorded: `--amount must be a finite number, got …`, a usage error. So is an `--amount` of 10000000000000 or more, whose cents a plan could not state exactly: `--amount must be less than 10000000000000, got …`. A window the record already holds at such an amount, or at one that is not finite, is refused as the record's fault, naming the window, with nothing written. And the ConfigMap is rendered before the record is saved, where a render failure used to come after the save, with nothing rolled back.

### `farcast kernel meter` — making a namespace count

Two things have to happen before an application's spending is counted, and doing only one is worse than doing neither: the kernel needs a **RoleBinding** to list pods in that namespace, and it needs to be **told the namespace exists**. A namespace with a binding and no listing is invisible to the meter; one listed without a binding makes every reconcile report an unreachable namespace.

`farcast kernel meter <instance> <namespace>…` does both in a single apply, so a failure between them cannot leave exactly one. With no namespace it reports what is currently metered.

**It never restarts the kernel.** The kernel is a single replica with a `Recreate` strategy, so re-rendering its workload with a longer `--namespaces` argument would stop the cost meter at precisely the moment new spending starts. Instead it re-reads a `technocore-namespaces` ConfigMap on every reconcile, and this command rewrites it. `kernel deploy` seeds the same list its own bindings cover, so the two views never begin out of step.

`--remove` stops metering a namespace and says plainly that the kernel's RoleBinding stays: this command does not delete cluster objects, the kernel's grant reads nothing once the listing is gone, and deleting the namespace removes it. If `reader grant` bound the reader there, its `farcast-reader` RoleBinding stays too, and still lets the reader read that namespace's workloads, pods and logs until the namespace is deleted; on an instance that records a reader, the result says so. `farcast-system` cannot be un-metered — the instance's own components live there, and dropping them is the under-reporting the whole component exists to prevent.

Once `reader grant` has recorded its scope, each namespace `kernel meter` starts metering also gets a `farcast-reader` RoleBinding, and the result names it, in JSON as `reader` and `reader_bindings_created`; `kernel deploy` and `run` do the same ([the reader identity](#farcast-reader--the-reader-identity-adr-0023-m23), "Later namespaces").

**Its plan** *(since ADR 0023 M2.6, built 2026-11-16, not walked)*. `kernel meter <instance> <namespace>… --plan` binds `--remove`. Its facts are, in order:
- the meter fact: the namespaces to add or remove, as given; the kernel bindings it creates; under `--remove`, the namespaces whose kernel binding stays; the reader and the reader bindings it creates; and the metered list after;
- one write for each document of its stream;
- its notices. Under `--remove` there are two: that the cost guard stops counting those namespaces against the instance's cost limit, and, on an instance that records a reader, the result's three lines saying that the reader's binding there stays. When namespaces are added and no reader binding can be added, there is the warning that says so.

A request that changes nothing has the meter fact and one notice, `Already metering …`, and no write; under `--confirm` it is compared before it says anything. Only an add can be such a request: removing a namespace that is not metered writes the list again. The plan reads only files on this machine, never `credentials.yaml`: no cluster and no Google API. With no namespaces the command only reports, so there `--plan` and `--confirm` are a usage error: `kernel meter --plan and --confirm need namespaces to add or remove; with none it only reports what is metered`. Outside a plan the command prints what it printed before, once. It does not print the `--remove` notices there, because its result says the same ([plans and confirmation](#plans-and-confirmation)).

### What the kernel may do once it is running

Stop **applications** and nothing else. `datasphered` and FatLine carry `farcast.sofmon.com/tier: system` and are classified last-to-die: stopping them would make storage impossible to unseal while the instance kept billing ([ADR 0008](../../docs/adr/0008-in-cluster-key-delivery.md)). A workload carrying no tier label is protected rather than stopped, and counted in the report — the two mistakes are not equally bad, so the tie goes to not stopping.

**What its checkpoint holds** *(version 2, since 2026-11-12)*. The `technocore-ledger` ConfigMap carries the ledger, the last observation, and two records:

- **Spending by namespace and name.** The ledger keys each application's accrual `<namespace>/<app>`, so two namespaces' `web` are two figures. A kernel restoring a version 1 checkpoint keeps every figure exactly — totals, `confirmed`, `expected`, overhead, calibration — and keeps its bare-named entries as they were, never re-keyed to a namespace it would have to guess; they read as *accrued before the kernel recorded namespaces* until the period ends. The usage profiles are keyed the same way (their document is version 2; a version 1 one is discarded at restore and said so). `farcast usage` names each profile `<namespace>/<app>` in both its tables, the profiles and the right-sizing advice; its JSON `apps[]` carries `namespace` beside `app`, which is now the bare name. It still reads a version 1 profiles document, from a kernel not yet updated, and names each profile as it was written, with no namespace and the note *profiled before the kernel recorded namespaces*.
- **The stops.** Each workload a cost shutdown scaled to zero: namespace, Deployment, when, why (`cost_guard`, the only reason the kernel has) and the hourly figure it was saving. A record ends when the kernel next sees the workload with replicas above zero (someone brought it back), sees its namespace without it (it is gone), or no longer meters its namespace (`kernel meter --remove`: the kernel would never list it again, so the record would otherwise outlive the namespace). A metered namespace the kernel cannot read keeps its records. Nothing is written on the Deployment itself.
- **The floor.** When every application is stopped and spending is still over ([ADR 0009](../../docs/adr/0009-technocore-kernel-and-cost-metering.md) decision 8): since when, what still burns an hour, and the levers left — `drop_carrier` while the carrier is billed, and `release_instance` — which the kernel names and never takes. Cleared on the first tick that is no longer there.

A stop, or the floor newly reached, is written at once rather than on the five-minute schedule — the ledger's ConfigMap alone, and tried again on every tick until a write succeeds — so a kernel that crashes right after stopping an application still says why it is stopped. The usage profiles wait for the schedule, and the schedule does not move. None of it tells the provider anything it does not already hold ([ADR 0009](../../docs/adr/0009-technocore-kernel-and-cost-metering.md) decision 2's test): each stop is a write to the Deployment's scale, which by the documented audit policy the provider keeps in Admin Activity with its full body for 400 days — very likely, per [ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md), and not yet seen in a walk — and the saving is the price of requests it holds and bills. The ConfigMap's writes are logged at Metadata level, without their content. The off-schedule write of `technocore-ledger` after a stop dates the stop a second time, and adds nothing to the first; the one when the floor is first reached has no scale-down of its own beside it, but its time follows from what the provider already holds — the scale-downs, the limit in the kernel's Deployment arguments, and its own bill crossing it.

**The upgrade is one way.** A kernel image built before 2026-11-12 reads only version 1 and refuses a version 2 checkpoint, so rolling the kernel back past this change (`farcast kernel deploy --technocore-image <older>`) leaves it failing to start on "restore the ledger", and the instance without cost enforcement until a kernel that reads version 2 is deployed again; `world` says so only as `checkpoint_stale`, after 15 minutes. Roll forward, not back.

### What `farcast costs` shows, and what it cannot

Both figures, the distance to the limit the kernel is enforcing, and spending by application from `expected` — each named `<namespace>/<app>`; a figure an older kernel accrued under a bare name is shown as it was kept, marked, with an empty `namespace` and a `note` in JSON. Then what the kernel has stopped to contain cost (`stops`: namespace, deployment, when, why, `saving_per_hour`), as it last recorded it — the human report lists under "Stopped by the cost guard" only records whose reason is `cost_guard`, as `world` labels only those, and shows any other with its reason — and whether it is at the instance floor (`floor`: `since`, `still_burning_per_hour`, `levers`). A checkpoint from a kernel that records neither says so (`records_stops: false`), rather than listing none. A checkpoint of a version this build does not read is refused with `version_skew`, as before; version 1 is read. Since 2026-10-08 the load-balancer carrier is metered too, and shown under **instance overhead** — never inside an application's share, because no application can be stopped to remove it; if the kernel could not read FatLine's Service it says it billed the carrier as present. And it always ends by naming what the kernel cannot see from inside the cluster — data through the carrier, bucket storage and operations, registry storage, and the cluster fee if the free credit is spent elsewhere — because a report that looks complete is the failure: `confirmed` is what catches those.

## `farcast reader` — the reader identity ([ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.3)

An instance's reader is a Google service account of its own, in the instance's project. Its ID is `farcast-reader-` and the first 8 hex characters of the SHA-256 of the instance name: 23 characters, and never the name itself. ADR 0023 decision 3 has cluster reads run as it, so that a read does not run as the installer, whose key can write. Since M2.3 (built 2026-11-14) the commands that set it up exist. **Since M2.4 (built 2026-11-15) the read commands read as it:** the cluster reads of `world`, `ps`, `costs`, `usage` and `logs` run in-process as the reader, and so does `reader grant`'s own check. Without a reader that `reader grant` has verified, they read nothing and say so ([who the cluster reads run as](#who-the-cluster-reads-run-as)). None of it has been walked against Google. *(2026-11-16: the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md) could not set a reader up, because its project's organization blocks key upload. It found that GKE's DNS endpoint refuses a token scoped to `userinfo.email` alone, the one scope farcast minted with at 2482810, so there these reads, and `reader grant`'s check, are refused against GKE. Since a fix later that day the reader's token carries `cloud-platform` and `userinfo.email`, so a leaked one works for every Google API the reader's IAM allows, not only the cluster. The fix is tested against a local API server only, and no reader has been walked with it.)*

### Setting it up

Four steps, one of them the human's:

1. **`farcast reader init <instance> [--days N]`**, on this machine. It makes an RSA-2048 key, `reader.key` (0600), and a self-signed certificate for it, `reader.crt`, whose subject is `CN=unused` and names no instance or account. It records the reader's email in `metadata.yaml`, prints a script, and names the script's SHA-256 on stderr. The script holds only the public certificate. With `-o json` it prints `{"instance","email","script","script_sha256","script_kind"}`. Run again before a key id is recorded, it prints the same script and makes no new key.
2. **The script, pasted into Cloud Shell by an Owner of the project.** It runs in a child shell (`sh -s`), so a failure leaves the Owner's shell as it was. It stops, changing nothing, if a key-upload constraint is enforced (below). Otherwise it creates the account unless it exists, grants it `roles/container.clusterViewer` on the project, uploads the certificate, and prints the key id. If the upload is refused, it prints the two lines that remove the account and its binding, and exits 1.
3. **`farcast reader record <instance> --key-id <id>`** records the id: 40 lowercase hex characters, the shape Google prints.
4. **`farcast reader grant <instance>`** applies the reader's Kubernetes RBAC, then checks as the reader that it can read and cannot write (below).

`metadata.yaml` then holds `reader: {email, key_id, granted_at, scope}`. farcast opens the reader only when the recorded email is the one it derives for the instance, a key id is recorded, and `reader grant` has verified it; `reader grant`'s own check is the one exception. A hand-edited email, such as one naming an account a certificate was uploaded to instead, is refused before anything is sent; a key id Google holds for another account is refused at Google's token endpoint.

Nothing farcast prints for Cloud Shell is copied from the record. The instance name, the project and any key id are checked first: the name by `install`'s rule, the project against Google's project-ID shape as farcast spells it (not yet walked; *2026-11-16: one real project passed it on the probe walk, where `reader init` printed its script and `release` its lines*), and the key id as 40 lowercase hex. The account is rebuilt from the name and project, and every value is single-quoted. The certificate is printed only after it parses as one certificate whose key is `reader.key`'s. A record that fails is refused, and nothing is rendered from it; `release` prints a safe fallback instead.

### What to know before relying on it

- **Its IAM role is project-wide.** `roles/container.clusterViewer` is granted on the project, so the reader can connect to and get every cluster in the project, not only this instance's. RBAC confines its reads to this cluster: only this cluster's RBAC binds it. Google lists the role's permissions, and none is on objects inside a cluster ([Google](https://docs.cloud.google.com/iam/docs/roles-permissions/container)).
- **Its key is an upload, and an organization can forbid that.** The managed constraint `iam.managed.disableServiceAccountKeyUpload` and the legacy `iam.disableServiceAccountKeyUpload` can each forbid it. Google enforces the legacy one by default in organizations created on or after 2024-05-03 ([Google](https://docs.cloud.google.com/resource-manager/docs/organization-policy/restricting-service-accounts)). The installer's key is a download Google created, which neither constraint governs, so an instance whose installer works can still have no reader. The script checks both before it changes anything. *(2026-11-16: the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md)'s project was in such an organization, which enforces the legacy constraint. Key creation was allowed there. The script stopped at its first check with farcast's own refusal, and changed nothing. farcast cannot take a Google-created reader key today.)*
- **`iam.serviceAccountKeyExpiryHours` governs every key created after it is set,** the installer's download too, and an uploaded key must expire within it ([Google](https://docs.cloud.google.com/iam/docs/keys-upload)). `reader init --days` (365 by default, 1 to 3650) fits it only when it is `24h` or more: pass a `--days` no greater than its days, and at most 90. At `1h` or `8h` no reader key can be made, because `--days` counts whole days. The script cannot read the constraint, so pass `--days` wherever it is enforced.
- **The key expires with its certificate,** after `--days` days, and the reader is then expected to stop working. `reader init --rotate` is the remedy. It writes a new key and certificate as `reader.key.next` and `reader.crt.next`, and prints a script that only uploads the certificate: it creates nothing and grants nothing. The old key stays in use until `reader record` is given the new id. That moves the new key into place, keeps the grant, since the account is the same, and prints the Cloud Shell line that deletes the previous key, which works in Google until it is deleted. The line says to delete it once `farcast world` reads with the new key. *(2026-11-15: until M2.4 it named `reader grant`, run again, because no other command read as the reader.)*
- **`release` leaves the account in Google.** It deletes `reader.key` with the instance's directory, but the account, its uploaded keys and its project binding stay. Its confirmation names the account, and its result prints the two Cloud Shell lines that delete it, the binding first ([`release`](#local-cleanup--output)).
- **Not yet walked:** the output format the script reads the key id from (`keys upload … --format 'value(name.basename())'`), and the spelling and output of both policy checks (`org-policies describe … --effective`). If a check itself fails, it prints nothing, the script carries on, and the upload then fails with Google's own message. Whether an upload needs a key usage on the certificate is not walked either. *(2026-11-16, the probe walk: both checks' spellings work. Run unsilenced, the legacy one printed `True` and the managed one `False`, each with exit 0. The managed one needs the Org Policy API, `orgpolicy.googleapis.com`, on the project: where it is off, gcloud asks to enable it, and in the script, silenced and with no terminal, it prints nothing, which the script reads as "not enforced". That is the failing check above: an enforced managed constraint then fails at the upload with gcloud's message, not farcast's. The key id's format and the key usage are still not walked: the script stopped first.)*
- **What Google sees of it:** the account, its display name `FarCast reader for <instance>`, its project binding, and each uploaded certificate, which names nothing. Each command that reads as the reader mints its token, in memory, at Google's token endpoint, and the API server sees the reader as the caller ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md)). Since M2.4 that is every `world`, `ps`, `costs`, `usage` and `logs`, not only `reader grant`'s check ([what each read tells the provider](#what-each-read-tells-the-provider-and-the-network)).

### `farcast reader grant` — the RBAC, and the check

It writes to the cluster, and it is newly automated: nothing else in FarCast grants a Google identity Kubernetes RBAC. So `--yes` never covers it. It asks in a terminal, or takes its plan *(since ADR 0023 M2.6, built 2026-11-16, not walked)*. `--yes` is refused, a usage error: `reader grant cannot be run with --yes: it gives a Google identity read access to the cluster; confirm it in a terminal, or review 'farcast reader grant <instance> --plan' and pass --confirm <digest>`, naming the instance, or `<instance>` when the name given is not a valid one. So is a session with no terminal: `reader grant needs a terminal to confirm, or --plan and then --confirm <digest>`.

**Its plan.** `reader grant <instance> --plan` reads only files on this machine, never `credentials.yaml`: no cluster, no Google API, and no terminal, so it is the same plan in a terminal or not. It binds the reader (its email, the IAM role `roles/container.clusterViewer`, the scope `metered`, the namespaces it would bind, the resources and the ConfigMaps) and one write for each document of the RBAC below. A reader that is not recorded, whose key is not yet uploaded, or that is not the one farcast derives, blocks the plan with `credential_missing` and no facts: `--plan` prints it and exits 0, and its `--confirm` refuses. A record whose values farcast does not accept is refused before any plan, as before. `--confirm <digest>` computes the plan again and compares it first; only then does it open the reader and the writer, apply without asking, check as the reader as below, and record ([plans and confirmation](#plans-and-confirmation)).

**It needs the installer's key too** *(since ADR 0023 M2.5)*. Its apply runs through the instance's writer, which it opens before it asks anything, or under `--confirm` right after the comparison *(since ADR 0023 M2.6, built 2026-11-16, not walked)*; `--plan` opens none. So an instance whose `credentials.yaml` holds no usable installer key, such as one installed without `--credentials`, is refused with `credential_missing`, and nothing is sent. It makes no in-process call as the writer: the apply is kubectl's, and the read and the reviews below are the reader's.

It applies, through kubectl as the active gcloud configuration until M2.7:
- **`namespaces` (list), cluster-wide:** a ClusterRole and a ClusterRoleBinding, both named `farcast-reader-namespaces`. It is the one ClusterRoleBinding farcast renders, and the in-process client's table of kinds allows that name only (ADR 0023 decision 2).
- **In `farcast-system` and in every namespace the kernel meters,** a RoleBinding of the ClusterRole `farcast-reader`, which is never bound cluster-wide: `deployments` and `statefulsets` (get, list), `pods` (list), `pods/log` (get), `jobs` (get), and five ConfigMaps by name (get), `technocore-namespaces`, `technocore-ledger`, `technocore-profiles`, `fatline-egress-policy` and `datasphered-pin`. `TestReaderRoleNamesTheConfigMapsReadsUse` ties those names to the code that reads them.

It grants no Secret, Service, write verb or watch. It binds the reader only in `farcast-system` and in namespaces the kernel meters, so never in a `kube-*` namespace such as `kube-system`, which `kernel meter` refuses; a binding then outlives `kernel meter --remove` (below). GKE's other managed namespaces, such as `gke-managed-system` and `gmp-system`, are not refused: the reader is bound in one only if the operator meters it, as the kernel is. Its RoleBinding in `farcast-system` needs that namespace, which `connect` creates and `install` does not.

Then, as the reader and in-process, it checks:
- **One read:** the namespaces farcast manages. A 401 or 403 is retried for up to 8 minutes while IAM propagates; Google gives "typically 2 minutes, potentially 7 minutes or longer" ([Google](https://docs.cloud.google.com/iam/docs/access-change-propagation)). That a reader still propagating gets a 401 or 403 from the API server is not yet walked. A token Google's endpoint refuses is not retried. *(2026-11-16: still not walked for a reader. On the probe walk an account whose IAM role was not yet in force got the endpoint's 403, an HTML page, with `cloud-platform`. The tokens it sent scoped to `userinfo.email` alone, from an account with no role and from the installer, each got 401. So at 2482810 this read is refused against GKE whatever IAM holds. Since the fix later that day the reader's token carries `cloud-platform` and `userinfo.email`, with the trade-off that a leaked one works for every Google API the reader's IAM allows; a reader whose role is still propagating is then expected to get the endpoint's 403 (inferred, not walked).)*
- **Five access reviews,** each of which must answer no: may it create deployments in `farcast-system`, get secrets there, patch `deployments/scale` there, list secrets in any namespace, or list pods in `kube-system`, where no farcast RBAC binds it? GKE allows what either IAM or RBAC grants ([Google](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/role-based-access-control)). So an IAM role stronger than clusterViewer, edited into the paste, shows here if it can write a Deployment or its scale, read a Secret, or read pods beyond the reader's RBAC, and if GKE's reviews consult IAM as well as RBAC; that is not yet walked. *(2026-11-16: settled by the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md). An account holding `roles/container.developer` and no RBAC asked whether it may create deployments in `farcast-system`, and was allowed, with the reason "access granted by IAM permissions." So GKE's reviews consult IAM, and the inference holds. The reviews themselves were not run as a reader.)* The reviews sample: a role whose only extra powers are others, such as `pods/exec` or `serviceaccounts/token`, does not show.

A yes refuses, and records nothing. Run again on a reader verified before, a yes first withdraws that verification, so the reader is refused until a clean grant. A review that fails, or whose answer the API server could not fully evaluate, refuses too, records nothing, and leaves an earlier verification as it was. On success it records `granted_at` and `scope: metered`, and lists each namespace it bound.

**Later namespaces.** The prompt asks for "every namespace the kernel meters, now and later". With that scope recorded, `kernel meter`, `kernel deploy` and `run` add a `farcast-reader` RoleBinding beside the kernel's in each namespace they meter, before the metered list. Each binding is printed (`the reader … may now read <namespace>`), and the JSON result gains `reader` and `reader_bindings_created`. Without the scope they add none. A namespace metered before the grant is bound by the grant, and `reader grant` run again applies every binding again. A record the binding cannot be rendered from is a warning on stderr, and no binding is added. `kernel meter --remove` does not remove a binding, and `reader grant` run again removes none either: its prompt names only the namespaces metered today.

## `farcast instances` and `farcast world` — the Connected view's reads ([ADR 0021](../../docs/adr/0021-farsight-native-client.md) decision 9, amended 2026-11-12)

The FarCast app on macOS draws a live instance by running the operator's own `farcast` and nothing else: `farcast version`, `farcast instances` and `farcast world <instance>`, with fixed flags, the instance name being one `instances` returned. The listing, `farcast instances`, and `farcast world` are reads, and change nothing. Neither opens `ca.key` or `keys.yaml` — a test runs them against a config directory where both are mode 000, with the config package's read observer showing neither was opened. Since ADR 0023 M2.4, `world` never opens `credentials.yaml`, the installer's key, either (`TestWorldNeverOpensAWriterCredential`), and `instances` never opens `reader.key` (`TestInstancesNeverOpensTheReaderKey`).

### `farcast instances`

Every instance this machine holds, from each one's `metadata.yaml` alone. It opens no credential, kubeconfig, CA key, reader key or keyring, and touches no network, so the app runs it at launch. Whether `reader.key` is on this machine is told from the file's presence, by a stat, never by opening it.

```json
{"schema":2,"generated_at":"2026-11-15T10:00:00Z","farcast":{"version":"v0.1.0","commit":"0e54eb1"},
 "instances":[
  {"name":"atlas","provider":"gke","region":"europe-west4","status":"running",
   "cost_limit":{"cents":5000,"currency":"USD","period":"monthly"},"cloud_logging":"system_only",
   "components":{"fatline":true,"kernel":true,"keyholder":true},"keepers":1,"reader":"granted","migrated":false},
  {"name":"broken","error":{"kind":"record_unreadable","message":"instances/broken/metadata.yaml could not be parsed: a YAML syntax error at line 1, column 7"}}]}
```

- `status` is the record's, verbatim: `provisioning`, `running`, `unreachable`, `deleting` or `error`.
- `cloud_logging` is `system_only` when install read the provider's logging back as system logs only, `unverified` when the record has none (an instance from before ADR 0019), and `unknown` for anything else.
- `components` is what the record says was deployed, not what is running — `world` reads that.
- `keepers` counts enrolled keepers that are not revoked.
- `reader` *(since ADR 0023 M2.4)* is how far the instance's [reader](#farcast-reader--the-reader-identity-adr-0023-m23) is set up, checked in this order: `none` (no reader recorded: `reader init`), `key_missing` (recorded, and `reader.key` is not on this machine), `not_uploaded` (no key id recorded: the Cloud Shell script, then `reader record`), `not_granted` (not verified read-only: `reader grant`), or `granted` (the read commands read as it). The reader's account itself is never printed. A `reader.key` whose presence cannot be told makes the entry unreadable, as an unreadable record is.
- `migrated` *(since ADR 0023 M2.4)* is whether the record says the instance moved to server-side apply. Nothing writes that before `farcast migrate`, which arrives in ADR 0023 M2.7, so it is `false` for every instance until then.
- Project ids, cluster names, endpoints and addresses are never emitted. A record that cannot be read is its name and an error, nothing more; its path is relative to the config directory. A record that does not parse is described by the kind of fault and its line and column, never quoted: the YAML parser's own message prints the lines around the fault, and some of its messages quote a value, and a record holds the project, the endpoints and the reader's account. `world` says the same of a record it cannot parse; the file itself shows the rest.

The document is schema 2 since ADR 0023 M2.4, which dropped `gcloud_pinned` and added `reader` and `migrated`; `world`'s moved to schema 2 with it.

**`pin-gcloud` is retired** (ADR 0023 M2.4). `farcast instances pin-gcloud <instance> --account <email>`, in any of its forms, writes nothing and is a usage error (exit `2`): farcast reads each instance's cluster as the instance's own read-only service account, so there is no gcloud account to pin. A record's `gcloud_account`, written by an older farcast, is ignored, and dropped at the record's next save.

### `farcast world <instance>`

One instance, map-ready. The CLI does the grading, the staleness, the alerts and the spending arithmetic; the map draws what it is given and recomputes none of it. The document is built by a pure function of what was read plus the clock and the build stamp, so the in-instance read route can later serve the same document.

It reads in five **sections**, each on its own, each with its own deadline, under a ceiling of 60 seconds for the whole command:

| Section | Read | Through |
|---|---|---|
| `apps` | FarCast's own workloads in `farcast-system`, the namespaces labelled `app.kubernetes.io/managed-by=farcast`, each namespace's Deployments and StatefulSets, and the kernel's `technocore-namespaces` list | the cluster, in-process as the reader (`ps`'s workload read) |
| `spend` | the kernel's checkpoint | the cluster, in-process as the reader (`costs`' checkpoint read) |
| `policy` | the egress policy FatLine enforces | the cluster, in-process as the reader (`run`'s `readEgressPolicy`) |
| `network` | Shrike's whole picture: allowed rows, refusals, the tunnel table | the FatLine tunnel (`usage`'s `fetchNetwork`) |
| `seal` | each keyholder replica's phase, generation and hold — never its key ids, so no keyring is needed | the same tunnel |

`sections.<name>` is `{"read": true}`, `{"read": false, "error": {"kind", "message"}}`, or — the seal of an instance whose record has no keyholder — `{"read": false, "skipped": "not_deployed"}`. A failed section never fails the command: what it would have supplied is marked unknown (`null`, or the state `unknown`), never omitted as if absent. When `apps` fails, a group's `apps` list holds only the applications the policy or the monitor named, each `unknown` — not the namespace's whole content. When only the `technocore-namespaces` read fails, the section carries that error, the workloads it read stand, and `metered` is `null` wherever this machine's record does not say otherwise. The deadlines are 20 seconds for each cluster read, 15 for opening the tunnel and 15 for the monitor's picture, and 10 for each keyholder replica. The cluster reads and the tunnel reads run side by side, so a control plane that does not answer cannot spend the tunnel's share of the ceiling, nor a carrier that does not answer the cluster's. A failure every later cluster read would meet the same way — no usable reader (`credential_missing`), its key refused (`credential_refused`), an environment that would print a credential (`unsafe_environment`), an endpoint farcast does not accept (`endpoint_refused`), the token refused (`unauthorized`), a cluster that could not be reached (`cluster_unreachable`), a control plane that let one read run out its deadline, the ceiling reached — is reported for each cluster section without asking again, and a section that was not asked says "not asked". `forbidden` is not among them: RBAC answers per object, so each section says its own. None of these refuses the command: the reader is the cluster sections' only, and the tunnel sections still read (since ADR 0023 M2.4). A 403 adds what the reader needs, in `world`'s section and in the other read commands' errors alike: `run 'farcast reader grant <instance>'` when the API server's RBAC refused it, and otherwise that the endpoint refused the identity (IAM), that IAM changes can take 7 minutes or longer for a reader just set up, and to check the Cloud Shell step if not. Which 403 is which is told by whether its body is a Kubernetes Status; what GKE's IAM refusal looks like on the wire is not walked.

**A namespace the reader may not read** *(since ADR 0023 M2.4)*. `reader grant` binds the reader in `farcast-system` and the metered namespaces only. A namespace `world` also reads — one labelled as FarCast's, one the record names — that is not metered answers its workload list `forbidden`. That group's `apps_error` then carries `{kind, message}` and its `apps` holds no workload: an application a policy or monitor line names there is listed with state `unknown`. Every other group is read, and the `apps` section stays read. The group is still drawn, so its `unmetered_namespace` alert still fires. Any other failure, and any failure in `farcast-system` or of the namespace list, fails the `apps` section as before. `apps_error` is `null` for a group whose workloads were read. Metering the namespace (`farcast kernel meter`) binds the reader there, once `reader grant` has recorded its scope, and the mark's message names that remedy for a namespace this machine does not record as metered: `run 'farcast kernel meter <instance> <namespace>'`, never `reader grant`, which binds only the metered namespaces. A recorded namespace refused by RBAC lost or never got its binding, and its mark says to run `reader grant`, which applies every binding again; a 403 that is not RBAC's says what IAM needs, as everywhere. A tunnel the ceiling left no room to try says it was not attempted, which is not a carrier that did not answer. The network and seal reads ride **one** tunnel: two would double what the provider sees of a Refresh.

**Wire rules.** JSON, snake_case. Times are RFC 3339 UTC to the second (`2026-11-12T10:00:00Z`), never ages, never fractional. Money is integer cents, `math.Round(usd*100)`. Every array is sorted by a stable key and is `[]` when empty, never `null`. `farcast.version` and `farcast.commit` come from `buildinfo`. The document never carries a credential hash, the carrier's endpoint or address, the project, the cluster or the bucket; a section message that would name one says `<carrier>`, `<control plane>`, `<project>`, `<cluster>` or `<bucket>` instead. Nor does it carry an account: an API server's refusal names the caller, so anything shaped like an email address, the reader's own included, reads `<account>`. Nor a path on this machine: the config directory reads `<config>`, and the home directory `~`.

**`instance`** — `name`, `status` (verbatim), `cloud_logging`, `spend`, `network`, `components`, `hosts_omitted`, and `caveats` (what this document could not say: applications named by the policy or the monitor but not running, policy or monitor rows naming an application in `farcast-system` — which a manifest named `farcast-system` could put there before `run` refused such a manifest (2026-11-12), and which is never drawn as a group — tunnel peers not enrolled from this machine, namespaces whose storage wiring is unknown).

- **`spend`** is `{"read": false}` or: `currency`, `period` (the record's, verbatim), `period_start`, `period_end`, `total_cents` (what enforcement compares), `expected_cents`, `confirmed_cents` (`null` until the provider has confirmed anything — never a confirmed zero), `has_confirmation`, `confirmed_through`, `limit_cents` (the **kernel's**; `null`, with the caveat "the kernel published no limit", when it published none — the recorded limit is never substituted), `recorded_limit_cents` (this machine's), `level` (the kernel's own, never recomputed: `ok`, `warn50`, `warn75`, `warn90`, `reached`, or `unknown`), `observed_at`, `checkpoint_stale` (more than 15 minutes before `generated_at`), `at_floor` (whether the kernel records the instance floor; `null` when the kernel that wrote the checkpoint records no stops or floor), `floor` (`null`, or `{"since", "still_burning_month_cents", "levers"}`: when the kernel first found nothing left to stop, what still burns at 730 hours a month, and the levers it names — `drop_carrier`, `release_instance`), `not_metered` (the facts `costs` prints, as data) and `caveats` (discrepancies, unreadable namespaces, unclassified pods, an unobserved carrier, a kernel limit that differs from the recorded one, spending accrued before the kernel recorded namespaces, an application name such spending cannot be told apart by, a kernel that keeps no record of its stops).
- **`network`** is `{"read": false}` or `{"read": true, "replica", "since", "fatline_replicas"}`: every count is a floor, counted by that one FatLine replica since `since`.
- **`components`** — one each for `boundary` (FatLine), `kernel` (TechnoCore), `monitor` (Shrike, a container in FatLine's Pod) and `storage` (the keyholder, `datasphered`), sorted by role: `{"role", "name", "state", "ready", "desired", "version", "go"}`. `state` is `running`, `starting` (ready < desired), `stopped` (desired 0), `not_deployed` or `unknown`. `version` is `sha256:` and the first 12 hex characters of the image digest the cluster runs, when it is exactly the image the record says was deployed, and `null` otherwise; the monitor's is its container's digest, for which no deploy record exists. `go` is the Go release that compiled the image, from this machine's `system_images` record, set exactly when `version` is and that record names the same image (for the monitor, the image of FatLine's second container) and says which Go; `null` otherwise, never guessed. *(Since ADR 0023 M1, an additive field, so M1 kept schema 1; both documents are schema 2 since M2.4.)* The monitor is `running` whenever it answered through the tunnel, even when the workloads were not read: its answer is the evidence, and the `watch` line is drawn exactly then. When it did not answer, FatLine's workload says what it can — `not_deployed` when FatLine's Pod has no second container, `stopped` when it desires none — and otherwise the monitor is `unknown`, so `unknown` comes only with a failed network section. Its `ready` and `desired` are FatLine's, and `null` when the workloads were not read.

**`groups`** — one per FarCast-managed namespace, never `farcast-system`, discovered from the cluster's labelled namespaces, the kernel's metered list and this machine's record: `{"namespace", "metered", "provenance", "apps", "apps_error"}`, `apps_error` being `null` unless the reader may not read that namespace (above). `metered` is `true` when the kernel's list or the record names it, `false` when the list was read and neither does, and `null` when the list could not be read — by the same rule for a namespace only the policy or the monitor names. `provenance` is the record `run` wrote — `{"repository", "ref", "commit", "manifest_digest", "deployed_at", "storage_wired"}`, the repository never with a user name or credential in it — or `null`, which the map draws as "repository not recorded on this Mac". Each app is `{"name", "state", "ready", "desired", "stopped_by", "month_cents"}`. `stopped_by` is `"cost_guard"` only when the checkpoint records the kernel stopping that namespace's Deployment of that name **and** its desired replicas are 0 now — a record the operator has since undone never labels a running app — and `null` otherwise, including for every app when spending was not read. `month_cents` is the app's accrual this period under its `<namespace>/<app>` key (0 when the kernel has accrued nothing for it), or `null` when its namespace is not known to be metered or spending was not read. Spending an older kernel accrued under the bare name is added in where one namespace — `farcast-system` included — runs that name; where two do, it cannot be told apart, so neither app has a figure, and a caveat says so.

**`hosts`** — `{"name", "seen_as"}`. Two spellings are one host when they are equal lower-cased, trimmed and without a trailing dot — the rule Shrike and FatLine compare by; `name` is that key and `seen_as` the raw spellings that differ from it. At most 200, the strongest evidence first and then by name; the rest are counted in `instance.hosts_omitted`, raise an alert, and their lines are not drawn.

**`lines`** — one per (kind, from, to). Never app-to-app, and never `planned`: neither exists in a live world.

- `egress`: from `{"app": "<namespace>/<app>"}` to `{"host"}`, with `evidence` the strongest of its `ports` (observed > denied > declared), `stale`, `drift`, `last_seen` and `since`. A port entry is `{"port", "evidence", "count", "fails", "reason", "last_seen", "no_longer_declared"}`: **observed**, one per allowed row (`count` the allows, a floor); **denied**, one per refusal reason — Shrike keys refusals by reason and host and keeps only the last port, so `port` is that last port and `count` spans every port; **declared**, one per policy entry, `port` `null` and `reason` the manifest's. `stale` is true when the line was last observed more than an hour before `generated_at`, or never, for a counted line. `drift` is an allowed host the application's current policy does not declare, seen within the hour and after the namespace was last deployed from here; an older one is a host a redeploy removed — Shrike's tables live as long as its Pod — and is marked `no_longer_declared` with no alert. `drift` is `null` when the policy was not read.
- `tunnel`: the operator to the boundary, `label_hint: "read_now"`, present when the tunnel opened — that read is its evidence.
- `keeper`: a keeper device to storage, from that device's own tunnel rows, with `last_seen` and `stale`. A keeper line is stale when last seen more than 24 hours before `generated_at` — the window the keeper's health is judged by, not the egress hour: a keeper streams only when it re-seeds, and a healthy keeper drawn with a stale line would contradict itself.
- `watch`: the monitor to the boundary, present when Shrike answered.
- `storage`: each application to storage, `evidence: "declared"`, `label_hint: "wired_not_counted"`, for namespaces whose provenance says `run` wired storage, while the keyholder is deployed. The keyholder keeps no per-application counters, so these are never observed; a namespace with no provenance gets a caveat instead of a line.

**`devices`** — the operator, `{"id": "operator", "role": "operator"}`, and each keeper this machine enrolled, `{"id": "<instance>/<device>", "role": "keeper", "name", "health"}`. `health` is `revoked` or `expired` from the record first; `healthy` when one of the device's own tunnel rows was seen within 24 hours; `unseen` only when that absence means something — the picture covers a whole day, the device has a leaf token this machine recorded, and there is one FatLine replica, so the row cannot be in another replica's picture; `unknown` otherwise.

**`alerts`** — `{"id", "kind", "severity", "subject", "title"}`, critical first, then by id. `subject` is `{"app": "<namespace>/<app>"}`, `{"component": "<role>"}`, `{"device": "<id>"}` or `{"instance": true}`; `id` is the kind, the subject and, where one subject has several, a discriminator.

| Kind | Severity | Subject | When |
|---|---|---|---|
| `cost` | warning at `warn75`/`warn90`, critical at `reached` | instance | the kernel's level |
| `checkpoint_stale` | critical | `kernel` | the checkpoint is more than 15 minutes old |
| `at_floor` | critical | `kernel` | the checkpoint records the instance floor; the title names the levers left |
| `sealed` | critical | `storage` | a replica that answered is sealed or under an operator hold |
| `denied` | warning | the app | refusals seen within the hour, for an application on this map |
| `unattributed_denials` | warning | `boundary` | refusals within the hour that name no application on this map — none at all, or one in `farcast-system` |
| `not_ready` | warning | the app | ready < desired, desired > 0 |
| `keeper` | warning | the device | expired, revoked or unseen |
| `unmetered_namespace` | warning | `kernel` | a group whose `metered` is `false` |
| `logging_unverified` | warning | instance | `cloud_logging` is `unverified` |
| `release_incomplete` | critical | instance | status `deleting` — it may still be billing |
| `hosts_omitted` | warning | `boundary` | more than 200 hosts |
| `drift` | warning | the app | a drift line |

Every application, host, device and component a line or an alert names is in the document: an application the policy or the monitor names that the cluster does not run is added to its group as `not_deployed` (or `unknown`, when the workloads were not read), with a caveat.

The human rendering is brief — spending split into confirmed and expected (and whether the kernel is at the instance floor), the components, the groups with their repositories and how many apps the cost guard stopped, the counts of lines, what needs attention, and what was not read — with every name the instance chose quoted under [the rule above](#output-model). `-o json` is the whole document.

### Error kinds

Every JSON error envelope carries `kind` beside `message` and `code` — additive, so a reader of the two old fields reads them as before — and so does every section error. The set is closed and stable; a reader decodes a kind it does not know as unknown.

| Kind | Means |
|---|---|
| `record_unreadable` | this machine's record of the instance (or its operator identity) is there and cannot be read |
| `not_found` | no instance by that name on this machine — also for every command that loads an instance record that is not there |
| `not_connected` | no FatLine recorded, so no tunnel |
| `tunnel_unreachable` | the tunnel did not open, or what answered through it could not be read |
| `kernel_absent` | no kernel is recorded, so nothing meters the instance |
| `not_checkpointed` | the kernel's ledger is absent or empty: it has not written yet |
| `version_skew` | the checkpoint, the egress policy or the metered-namespace list is another version; or (`connect`, `redeploy`, `kernel deploy`, `storage deploy`, since ADR 0023 M1) a component another farcast version deployed would be replaced without `--embedded`; the message names both. *(Since ADR 0023 M2.6, not by `connect` or `redeploy`, and since M2.6c not by `kernel deploy` or `storage deploy`, under `--plan` or `--confirm`: the plan states the replacement as `replaces_other_version`, and its `--confirm` is the consent to it)* |
| `credential_missing` | the instance holds no usable stored credential for the identity the call needs: no installer key (an ADC install), no reader recorded or uploaded, a reader not yet verified read-only by `reader grant`, a reader email that is not the derived one, a missing `reader.key`, or a key file that is not a service-account key, or a reader record whose values farcast does not accept, or *(since ADR 0023 M2.6c, built 2026-11-17, not walked)* a plan that reads the cluster with no reader that `reader grant` has verified |
| `credential_refused` | Google's token endpoint refused to mint a token from the stored key: the key is deleted, disabled or expired (a reader key expires with its certificate), its recorded key id is wrong (Google may reject it), or the clock is far off |
| `unsafe_environment` | the process environment would make farcast print a credential; nothing was sent |
| `endpoint_refused` | the recorded cluster endpoint, its CA file and the credential do not pair (ADR 0023 decision 2's rule), or no endpoint is recorded; nothing was sent |
| `cluster_unreachable` | the cluster's API server, or the token endpoint the call needs first, did not answer: DNS, connection or TLS failure |
| `unauthorized` | the API server refused the token (401), after one fresh token. *(2026-11-16: GKE's DNS endpoint answers 401, an HTML page, to a token scoped to `userinfo.email` alone, which was every cluster token farcast minted at 2482810, so there every in-process cluster call is refused against GKE; the [probe walk](../../docs/runbooks/adr-0023-m2-probe-walk.md). Since a fix later that day the tokens carry `cloud-platform` and `userinfo.email`, so a 401 again means the identity was refused, not the scope (not walked), and a leaked token works for every Google API the account's IAM allows)* |
| `forbidden` | the API server refused the identity this read or write (403): by RBAC when the answer is a Kubernetes Status, otherwise at the endpoint. *(2026-11-16: the probe walk saw the endpoint's IAM 403 as an HTML page, not a Status, which holds this rule)* |
| `cluster_rejected` | the API server answered with any other error: a 4xx other than 401 and 403, a 5xx, or a 429 after retries; or an object did not come back as a write left it |
| `document_unreadable` | the cluster returned, or holds, a document that does not decode. This is the successor of `kubectl_failed`'s second meaning (the kernel's checkpoint, the egress policy and the metered-namespace list) |
| `rollout_stalled` | a Deployment reported that it exceeded its progress deadline (emitted since ADR 0023 M2.5, by `connect`'s and `redeploy`'s rollout waits only) |
| `not_migrated` | the instance was last written with client-side apply; run `farcast migrate`, which arrives in ADR 0023 M2.7 (nothing emits it before ADR 0023 M2.7) |
| `plan_changed` | a `--confirm` digest is not the plan's digest now, or something the plan bound changed before a write it covers, or the plan's inputs expired (emitted since ADR 0023 M2.6, by `--confirm`. *2026-11-16: so far the first case, by `kernel confirm`, `kernel meter` and `reader grant`. 2026-11-17: also by `connect`, `redeploy`, `build`, `kernel deploy`, `storage deploy`, `storage key pin` and `storage key rotate`, and the second by all of those but `build`: mTLS material that appeared where `connect`'s plan said mint, a registry ensure that answers with another registry than the plan's, a writer whose cluster's `farcast-system` uid is not the one the plan read as the reader, a key pin that moved from where the plan read it, a record that changed while a first `storage deploy` minted its storage or while `storage key rotate` ran, and a hold pin `storage key rotate` would write that, its new keys mapped back to their placeholders, is not the one its plan listed. Not the third*) |
| `timeout` | a read, or the whole command, ran out of time |
| `internal` | anything else |

There is no `usage` kind. A usage error, a flag that does not parse and an unknown command exit `2` with prose on stderr and no envelope, as they always have.

**The writing commands' envelopes** *(since ADR 0023 M2.5)*. A command that writes to the cluster carries the cluster kind of any failure of its in-process calls:
- opening the instance's writer: `credential_missing`, `unsafe_environment` or `endpoint_refused`;
- minting its token: `credential_refused`;
- its reads, its waits, and the storage key pin's create and replace: `cluster_unreachable`, `unauthorized`, `forbidden`, `cluster_rejected`, `document_unreadable`, `rollout_stalled` or `timeout`.

A `forbidden` one ends with one sentence: the cluster refused the instance's installer service account, by RBAC or at the endpoint (IAM), and the operator should check that it still holds `roles/container.admin` in the project. A failure of the kubectl apply the command still runs until M2.7 is `internal`, as before, and so is the refusal, right after the writer opens, of a machine with no `kubectl` or no kubeconfig for the instance, which is that apply's own refusal found early. Only a failure that reaches the envelope carries a kind. `run`'s and `kernel deploy`'s rollout waits and `run`'s pin raise only warn, and a failure of `build`'s log read is dropped. `storage key rotate` rotates without a pin it could not reach, and says so as an unfinished rotation, `internal`; under `--confirm` *(since ADR 0023 M2.6c, built 2026-11-17, not walked)* there is no going on without the pin, and a pin read or write that fails keeps its own kind, a conflict `plan_changed`. `TestWritingCommandsCarryClusterKinds` holds the kinds that reach an envelope.

**Retired kinds.** `kubectl_missing`, `kubectl_failed`, `gcloud_mismatch`, `gcloud_signed_out` and `auth_tool_missing` were shipped before ADR 0023 M2.4 moved the cluster reads in-process and retired the gcloud identity guard; nothing emits them any more, and no new kind ever takes one of their names.

### Who the cluster reads run as

Since ADR 0023 M2.4 (built 2026-11-15) the cluster reads of `world`, `ps`, `costs`, `usage` and `logs` run in-process as the instance's [reader](#farcast-reader--the-reader-identity-adr-0023-m23), and as nothing else. They start no kubectl, auth plugin or gcloud, and read no gcloud configuration. Each opens the cluster the same way (`openCluster`), and sends nothing until every check below has passed:

1. The record must name the instance the command was given. Otherwise `credential_missing`: every path is built from the recorded name.
2. The record must name a cluster endpoint. Otherwise `endpoint_refused`.
3. The instance name, the project and any key id must have the shapes `farcast reader` holds them to, before a path is built from them or any of them is printed. Otherwise `credential_missing`, with the value quoted.
4. The endpoint must pass ADR 0023 decision 2's rule: a name under `gke.goog` on port 443, trusted on the system roots alone, or a loopback IP literal trusted only on its own `cluster-ca.crt`, the rehearsal's. ### Plans and confirmation

*(Since [ADR 0023](../../docs/adr/0023-one-download-farcast.md) M2.6, begun 2026-11-16. Built and not walked.)* ADR 0023 decision 8 gives every command that writes to a cluster two answers beside its prompt and `--yes`. `--plan` prints everything the command would do, and changes nothing. `--confirm <digest>` computes it again from live state, and does it only if the result is the plan with that digest, asking nothing. What runs is then what the operator read, with no terminal and no `--yes`. Ten commands have them so far: `kernel confirm`, `kernel meter` and `reader grant`, and since 2026-11-17 `connect`, `redeploy`, `build`, `kernel deploy`, `storage deploy`, `storage key pin` and `storage key rotate` (each section above says what its plan binds). On every other command `--plan` and `--confirm` are unknown flags, a usage error: among those that write to a cluster, only `run` has no plan yet.

| Given | Result |
|---|---|
| two or three of `--plan`, `--confirm` and `--yes` (or `-y`) | Usage error, exit 2: `--plan, --confirm and --yes are three different answers; give one`. Values are counted, not flags, so `--yes=false --plan` is a plan. It is checked before the record is read. |
| `--confirm` with anything but `sha256:` and 64 lowercase hex characters, `--confirm=` included | Usage error, exit 2: `--confirm takes the digest a plan printed: sha256: and 64 lowercase hex characters`. |
| `--plan` | The plan is printed. Nothing is written or recorded, no key or certificate is minted, and nothing is asked. A plan that reads the image registry mints an access token for it, and one that reads the cluster the reader's token, each held in memory (below). Exit 0, for a blocked plan too. |
| `--confirm <digest>` | The plan is computed again. An error met while computing it is returned as it is, with nothing written. A plan whose digest is not the one given is refused with `plan_changed`, exit 1: `the plan for this command is now <digest>, not the <digest> given to --confirm: something it binds has changed since the plan was made; run it with --plan to review the new one. Nothing was written.` A blocked plan is refused with its first block's kind and message, exit 1. Otherwise the command does what the plan said, with no prompt, and prints its usual result. Something the plan relied on that has changed by the time the command comes to write it is refused with `plan_changed` too, before anything is pushed or applied except where a case below says what was already done, ending `run the same command with --plan instead of --confirm` (so far: mTLS material that appeared where `connect`'s plan said mint, a registry ensure on `connect`, `redeploy`, `kernel deploy` or `storage deploy` that answers with another registry than the plan read, and, since M2.6c, a writer whose cluster is not the one `kernel deploy`'s, `storage deploy`'s, `storage key pin`'s or `storage key rotate`'s plan read as the reader; a key pin that has moved from where `storage deploy`'s, `storage key pin`'s or `storage key rotate`'s plan read it, before or as it is written — as `storage deploy` writes it, its bucket and keyring are minted, the registry ensured and its image pushed or built, and as `storage key rotate` writes the hold, its new keys are minted, saved and held by the replicas, and as it writes the final pin they are in use; a record that a first `storage deploy`'s storage mint left other than its plan read, once that mint is done; a record whose keyholder changed while `storage key rotate` ran, once its new keys are saved; and a hold pin `storage key rotate` would write that, its new keys mapped back to their placeholders, is not the one its plan listed, the keys held and not in use). |
| neither | As before: `reader grant`, `connect`, `redeploy`, `build`, `kernel deploy`, `storage deploy` and `storage key rotate` ask in a terminal, `storage key pin` asks before `--replace` lowers the pin, and `kernel confirm` and `kernel meter` ask nothing. Without a terminal, the usage errors of the eight that ask now name the plan route, ending `or --plan and then --confirm <digest>`. |
| `--yes` alone | `reader grant` refuses it, and its refusal now names the plan route; the two kernel commands accept it unused, as before; `connect`, `redeploy`, `build`, `kernel deploy`, `storage deploy`, `storage key pin` and `storage key rotate` take it as before, and it never implies `--embedded`. |

**The document.** With `-o json`, `--plan` prints `{"schema":1,"kind":"plan","generated_at":…,"digest":"sha256:…","bound":{…}}`. `bound` is everything the plan binds:
- the protocol, `farcast-plan-1`;
- the farcast that computed it, its version and commit, so a farcast of another version or commit does not confirm it;
- the command, the instance's local name and its target (below);
- the stage, empty for the ten built so far;
- the options that change what the command does, each as its parsed value (`kernel confirm`'s `--from` and `--to` as the days they resolve to, given or not; `build`'s flags as given), sorted by flag;
- who the plan reads the cluster as (`cluster_identity`: `reader` for `kernel deploy`, `storage deploy`, `storage key pin`, and `storage key rotate` with a keyholder deployed; `none` for `storage key rotate` with none, and for the other six built so far);
- the facts, in the order the command presents them;
- the blocks, a kind and a message each, `[]` when nothing refuses it. A blocked plan has no facts.

Its encoding is canonical: compact JSON without HTML escaping, every field always present, no maps and no floating point (money is integer cents, and dates and times are UTC). A value that is not valid UTF-8, which a hand-edited record can hold, is refused rather than encoded, because JSON would write each bad byte as U+FFFD and two different values would share one digest: `plan: <where> is not valid UTF-8`, with nothing printed or written. So is such a value given on the command line, such as `connect`'s or `redeploy`'s `--source` *(since 2026-11-17)*; `build` refuses its own flags' values sooner, where it renders its documents, never quoting them. The digest is `sha256:` and the hex SHA-256 of `farcast-plan-1`, a newline, and `bound`'s bytes exactly as printed, so anyone can check a printed plan by hashing its `bound` member. `generated_at` is outside the digest.

**The target** is the instance as its record names it: provider, project, region, cluster, endpoint, and the record's creation time. It also holds `farcast-system`'s uid: the one a plan that reads the cluster read as the reader (`kernel deploy`'s, `storage deploy`'s, `storage key pin`'s, and `storage key rotate`'s with a keyholder, since M2.6c), and in the text `absent` when the cluster has none; and empty in a plan that reads no cluster, as the other six built so far, where the text says `not read`. A plan made against one record therefore does not confirm against a record of another cluster, or against the same name after a `release` and a new `install`.

**The text.** Without `-o json` the plan prints its blocks first, each `blocked (<kind>): <message>`. Then four lines name the instance and its target, the command, its stage and whom it reads the cluster as, the options, and this farcast and the protocol. Then the facts, one to three lines each, then `digest: sha256:…`, and last the line that confirms it: `To do exactly this: farcast … --confirm sha256:…`. That is the command line the plan was printed for, global flags included, with every `--plan` dropped and each word quoted where a POSIX shell, or zsh, would read it as more than itself: a word that begins with `=` is quoted too, since zsh reads it as a command's path. Where that line cannot be rebuilt, for a word that would not print as itself, it is `To do exactly this: run the same command with --confirm sha256:…`. A blocked plan ends with `blocked: --confirm would refuse this plan (<kind>)` instead. Every value in it passes through the rule `world`'s text uses, so a value with a control or bidi character prints Go-quoted and cannot act on the terminal that shows it.

**No file is kept.** A plan is printed, never saved; `--confirm` proves it fresh by computing it again. So a plan has no expiry of its own. A `kernel confirm` plan does not survive a UTC midnight, because it binds the day.

**What the plans read, and who acts under `--confirm`.**
- The plans of `kernel confirm`, `kernel meter` and `reader grant` read only files on this machine: the record, and for the reader's email the instance's `cluster-ca.crt`. They send nothing: no cluster read, no Google API, no token. They never open `credentials.yaml` or a writer, and run no kubectl (`TestPlansWriteNothing`, `TestPlansStillReadTheInstallerKeyForGoogle`).
- `build`'s plan reads the record alone, never `credentials.yaml`. A builder given by tag is looked up anonymously, only to be refused with the digest to pin.
- `connect`'s and `redeploy`'s plans read the record and the instance's CA certificate when there is one, never `ca.key` or a leaf's key. They read the instance's image registry, the one the record names, with the installer's key from `credentials.yaml`: the key mints an access token, held in memory, and the lookups ask what each version tag, or each kept image, holds. Until ADR 0023 M3b that key is what a plan reads Google with, and only for the registry. A source build's plan also finds its checkout and asks this machine's Go for its path and version (`go env`). They read no cluster, open no writer, run no kubectl, and ensure, push or build nothing; on an instance whose `credentials.yaml` is missing, cannot be read, does not parse or holds no key (an install with Application Default Credentials), they are refused with `credential_missing`, in the writer's words, before the provider opens. A reconnect's plan reads neither the key nor the registry (`TestPlansWriteNothing`, `TestPlansStillReadTheInstallerKeyForGoogle`).
- Under `--confirm` the plan is computed and compared first. Only then does the command open the writer, check this machine for kubectl and the instance's `kubeconfig.yaml`, and go on as an interactive run does (`TestKernelMeterAndConfirmOpenTheWriterOnlyAfterTheCompare`, `TestReaderGrantConfirmVerifiesAsTheReaderAfterTheCompare`, `TestBuildConfirmAppliesThePlannedJobAfterTheComparison`). `connect`, `redeploy` and `build` also read `farcast-system` once as the writer then. `connect` and `redeploy` then do what the plan said, `connect`'s mint, the registry ensure, the pushes and the builds, and deploy the images they compared, looking nothing up again (`TestConfirmExecutesWhatItCompared`). A reconnect opens no writer: after the comparison it ensures the registry and dials.
- `kernel deploy`'s plan *(since M2.6c)* reads the cluster as the instance's reader, which `reader grant` must have verified read-only: there is no fallback to the installer's account. Where no reader can be granted, such as a project whose organization blocks service-account key upload, `kernel deploy --plan` and `--confirm` are refused, `credential_missing`, and the command runs interactively or with `--yes` as before. It reads the registry as `connect`'s plan does. Under `--confirm` it computes the plan again as the reader, and the writer opens only after the comparison; the uid of `farcast-system` the writer then reads must be the one the plan bound, or nothing is written (`TestConfirmRecomputesAsThePlansIdentity`, `TestConfirmChecksTheWritersClusterIsThePlans`, `TestPlanWithoutAReaderIsRefused`, `TestPlansPresentOnlyTheReaderToken`). So under `--confirm` three identities act until M2.7: the reader, which plans; the installer's key, for the registry and the writer's reads; and kubectl's apply, as the active gcloud configuration.
- `storage deploy`'s and `storage key pin`'s plans *(since M2.6c)* read the key pin and `farcast-system`'s uid as the instance's reader, under the same rule, and the keyring's key ids, never a key. `storage deploy`'s reads the registry as `kernel deploy`'s does, and the instance's CA certificate, checking its other five files are there without opening them, never `ca.key`, and reads neither the bucket nor its IAM policy: the bucket grant it prints is a notice (below), not a fact checked against Google; `storage key pin`'s reads no Google and opens no keyholder. Under `--confirm` each computes the plan again as the reader, then opens the writer, whose preflight must read the plan's uid, and reads the pin as the writer, which must be where the plan read it: at the version its write binds, or, with no write, the pin the plan states. Only then does `storage deploy` mint the bucket and keyring, ensure the registry, push or build, issue the keyholder's leaf and write the pin, and `storage key pin` write it; each writes the pin once, at that version, never unioned or retried, a conflict refused `plan_changed` and a write that landed and lost its answer read back as written (`TestConfirmChecksTheWriterBeforeAnythingIrreversible`, `TestConfirmNeverWritesAPinThePlanDidNotList`, `TestConfirmPinThatLandedButLostItsAnswerSucceeds`, `TestConfirmPinNon409FailureKeepsItsKind`). `storage key pin --replace --confirm` lowers the pin, and any replica it finds enforcing another, without asking: the plan, which says so, is the consent (`TestKeyPinReplaceConfirmLowersReplicasWithoutAsking`). It applies nothing, so it needs no kubectl. So under `storage deploy --confirm` the same three identities act as under `kernel deploy`'s, and under `storage key pin --confirm` two: the reader and the installer's key.
- `storage key rotate`'s plan *(since M2.6c)* needs the instance's record, and reads the keyring's key ids and their times, never a key. With a keyholder deployed it reads the pin and `farcast-system`'s uid as the instance's reader, under the same rule; with none it reads no cluster and needs no reader. It reads no Google and opens no keyholder. Under `--confirm`, with a keyholder, it computes the plan again as the reader and opens the writer, whose preflight must read the plan's uid. With a keyholder and at least one application scope it then reads the pin, which must be at the version the plan read, and waits, at most a second, until this machine's clock is past the newest key of every scope, refusing a clock further behind; only then does it mint, save `keys.yaml` and open the keyholder. With a keyholder and no application scope it reads the pin and the uid in its plan, checks the writer's uid, and writes no pin. It reads its record again once the new keys are saved, and refuses `plan_changed` if the keyholder is not the one the plan read. It writes the hold once, at the version read, and the final pin once, at the version it reads back. Each is written only if, with its new keys mapped back to their placeholders, it is the pin the plan listed (`TestRotateConfirmWritesTheHoldPinThenTheFinalPin`, `TestRotateConfirmSurfacesPlanChanged`, `TestRotateConfirmPutBackWritesNoUnplannedPin`, `TestRotateWaitsForTheClockPastTheNewestKey`). It applies nothing, so it needs no kubectl.
- A `--plan` cannot tell whether this machine can apply, since the kubectl check comes after the comparison. On a machine with no kubectl, the plan prints, and its `--confirm` refuses after the comparison, having written nothing; a reconnect's `--confirm`, and `storage key pin`'s and `storage key rotate`'s, which apply nothing, do not.
- Until ADR 0023 M2.7 the apply is kubectl's, as the active gcloud configuration, and it writes to the cluster `kubeconfig.yaml` names, which `install` wrote for the same cluster. The plan binds the record's endpoint, and no code compares the two.
- `kernel confirm` and `kernel meter` make no in-process call and mint no token, under `--confirm` as in an interactive run. `reader grant --confirm` mints the reader's token for its check, after the apply, as an interactive run does. `connect --confirm`, when it deploys, `redeploy --confirm` and `build --confirm` mint the installer's cluster token for the writer's read; `connect` and `redeploy` also mint registry tokens from the same key, for the plan they compute again and for each push or build. `kernel deploy --plan` mints the reader's cluster token and, unless `--technocore-image` names the image, a registry token; its `--confirm` mints those again for the plan it computes again, the writer's cluster token after the comparison, and a registry token for each push or build, one reader and one writer opened. `storage deploy` does the same, with `--datasphered-image`; `storage key pin --plan` mints the reader's cluster token alone, and its `--confirm` that and the writer's, after the comparison; so does `storage key rotate` with a keyholder deployed, and with none it mints no token.

**What `--yes` never covers.** `reader grant`: it gives a Google identity read access to the cluster, so it is consented to in a terminal or through its plan, and `--yes` is refused. `kernel confirm` and `kernel meter` ask nothing. They keep an unused `--yes`, so scripts can pass it uniformly, except beside `--plan` or `--confirm`. And `--embedded`: `--yes` never implies it, so a `--yes` run of `connect`, `redeploy`, `kernel deploy` or `storage deploy` that would replace a component another farcast version deployed is refused with `version_skew`, before anything is asked.

**`--embedded` under `--confirm`.** A plan states whether each image replaces a component another farcast version deployed (`replaces_other_version`), and binds `--embedded` as an option. Its `--confirm` is the consent to that replacement, with or without `--embedded`: it is never refused for it. Where that is all `--embedded` changes, a plan made with it and one made without differ only in that option (`TestConfirmCoversTheReplacementItsPlanListed`, `TestYesNeverReplacesAnotherVersionWithoutEmbedded`). Over an operator build `--embedded` changes the action too, from keeping that build to deploying the carried image.

**Placeholders.** A plan opens no private key and cannot know a digest that exists only once an image is built, so it renders those parts over placeholders. FatLine's server leaf and key are `farcast-placeholder:fatline_leaf:<server name>:cert` and `:key`, whether the command mints them or loads them. A CA that `connect` would mint is `farcast-placeholder:instance_ca:<instance>:cert`, and an existing CA certificate is rendered as itself. An image built from source is its repository at `sha256:` and the hex SHA-256 of `farcast-placeholder:build:<component>`, in its image fact, its push and the Deployment. A key `storage key rotate` would mint has the id of the first eight bytes of the SHA-256 of `farcast-placeholder:key:<scope>:<n>`, created a second after the newest key of its scope, and its pins are decided over it; the text names it `new key <n> of <scope>`. A write fact binds each document's SHA-256 as the plan renders it. What `--confirm` applies may differ from those documents in a Secret's data, in the pod template's `farcast.sofmon.com/mtls-hash` annotation, for an image built from source in that image's digest, and in the key ids of a pin that requires or retires a key the command mints. `TestConfirmWritesThePlannedDocumentsExceptTheirSecrets` holds the rest equal byte for byte for FatLine's stream, from a first connect and from a redeploy of carried images, and for `build`'s three documents; no test yet compares a source build's applied stream with its plan.

**Notices.** A line a command prints while it works (`Already metering …`, `Nothing to confirm: …`, the warning when no reader binding can be added, and `connect`'s and `redeploy`'s notes as they decide an image: a kept build, a replaced image, a foreign version tag, a provenance record ignored, a development image built again) is a `notice` fact under `--plan`, shown only in the plan. Outside `--plan` it prints once, as before, and under `--confirm` right after the comparison. `connect` and `redeploy` now print theirs before anything is asked, which moves the note on a replaced image from after the push to before the questions. *(2026-11-17: outside `--plan` they print through the rule the plan's text uses, under `--confirm` too, so a line from a hand-edited record cannot act on the terminal, as `kernel meter`'s do; and an interactive or `--yes` run that refuses a replacement with `version_skew` refuses before the lines of the image it refuses, saying no replacement or push over a foreign tag that it does not make.)* `storage deploy`'s plan carries the bucket grant it prints as a notice too, but outside a plan that prints once the bucket exists, with its real name, as before. `storage key pin`'s carries, only in a plan, that which replicas are handed the pin is decided when it runs, and with `--replace` that a replica found enforcing another pin is handed this one in its place; the lines `--replace` prints before it lowers the pin are its notice. `storage key rotate`'s carries the scope warning it prints before it asks, and, with a keyholder deployed and at least one application scope, that which replicas take the new keys is decided when the rotation runs, which only a plan carries. A source build's plan adds one notice per checkout, which only a plan carries: `the build compiles whatever <dir> holds when --confirm runs; this plan binds the directory, not its content`. The two lines that say FatLine is deployed without Shrike print only outside plans, because no plan deploys it so.

**What a plan names.** A plan names the instance's project, cluster, endpoint, image registry, bucket and reader account. Handle a plan document like the instance's metadata.yaml. The values are printed as the record holds them, unscrubbed, in JSON and in text. Of the ten plans built so far, `connect`'s, `redeploy`'s, `build`'s, `kernel deploy`'s and `storage deploy`'s name the image registry, `kernel deploy`'s the reader account too, and `storage deploy`'s the bucket it serves (a first deploy's as the placeholder `farcast-placeholder:bucket:<instance>`, since its name is drawn only when it is created). A source build's plan also names the checkout's directory and the path of this machine's Go.

**Tested, not walked.** The plans and their confirmations are tested against fakes and a local API server (`kube/kubetest`) only. None of it has run against Google: no plan's registry token or lookup has been made against Artifact Registry, and no plan has read a GKE cluster as the reader. Each of the six commands of M2.6a and M2.6b has a plan among the golden vectors ([below](#golden-vectors)), and since 2026-11-17 so do `kernel deploy`, `storage deploy`, `storage key pin` and `storage key rotate`, read from a fixed fake cluster as the reader.

### What each read tells the provider and the network

- **Before the cluster reads** *(since ADR 0023 M2.4)*, `farcast` mints the reader's token at Google's token endpoint, `oauth2.googleapis.com`: that tells Google the reader's account, the time and the source address. The token is held in memory only, and each command is one process, so every `world`, `ps`, `costs`, `usage` and `logs` mints one. Google can therefore time each operator read, and records each key's last use (inferred, not walked). gcloud's auth plugin, which these reads used until M2.4, kept its token in a file and minted about once an hour (inferred). No gcloud runs, so no gcloud update check either. *(Since ADR 0023 M2.6c, built 2026-11-17, not walked: so does each plan that reads the cluster, `kernel deploy`'s, `storage deploy`'s, `storage key pin`'s, and `storage key rotate`'s with a keyholder deployed, under `--plan` and again under `--confirm`, for the plan it computes again. So Google can time each such plan too, by the reader's account (inferred).)*
- **Before a writing command's cluster calls** *(since ADR 0023 M2.5)*, `farcast` mints the installer's token the same way, one per process: that tells Google the installer's account, the time and the source address. Every writing command that reads the cluster or writes the storage key pin mints one: `connect` when it deploys, `redeploy`, `build`, `run`, `kernel deploy`, `storage deploy`, `storage key pin` and `rotate`. `kernel meter`, `kernel confirm` and `reader grant` make no in-process call as the writer, and mint none. Until M2.7 this comes on top of what gcloud's auth plugin mints for kubectl's applies. So one writing command can show Google two callers: the installer's service account for its reads (in Data Access audit, where that is on) and its pin writes, and the gcloud identity for its applies (not walked). *(2026-11-17, ADR 0023 M2.6, built, not walked: a plan reads no cluster, so `connect --plan`, `redeploy --plan` and `build --plan` mint no cluster token. `connect`'s and `redeploy`'s plans still mint registry tokens from the installer's key, one for each image not named by its flag, and look the images up in the instance's registry, so Google sees the installer's account and the time of each plan (inferred). Under `--confirm` they mint those again, for the plan they recompute, as well as the writer's.)* *(2026-11-17, ADR 0023 M2.6c, built, not walked: `kernel deploy --plan` and `storage deploy --plan` mint the reader's cluster token, not the installer's, and registry tokens from the installer's key as `connect`'s plan does; `storage key pin --plan` and `storage key rotate --plan` mint nothing from the installer's key. Each of the four mints the installer's cluster token only under `--confirm`, after the comparison, and `storage key rotate` only with a keyholder deployed.)*
- **The cluster reads** go to the provider's API server, which terminates TLS, with the reader's service account as the caller and `farcast` as the user agent (not yet walked). Data Access audit logging is off by default, but any parent folder or organisation can force it on; where it is on, it records each get and list — caller, object, namespace, source address, user agent and time ([ADR 0019](../../docs/adr/0019-what-the-cluster-tells-its-provider.md)). The objects read are in the provider's etcd already. The Mac's resolver sees the control plane's `*.gke.goog` name ([ADR 0004](../../docs/adr/0004-private-control-plane.md)), and `oauth2.googleapis.com`.
- **The tunnel reads** show the provider and the network the source address, the timing, the sizes and the SNI that names the instance — and are blind to content.
- `instances` and `version` read files on the Mac and tell nobody anything. That is why `world` runs only when the operator asks, and never on a timer.

### `run` records what it deployed, and keeps one repository per namespace

On success, after the workloads are applied and before the rollout wait, `run` records on this machine — never in the cluster — `deployments.<namespace>: {repository, ref, commit, manifest_digest, deployed_at, storage_wired}`, from what its in-instance read reported: the ref is `--ref`, or `refs/heads/main` when none is given (what the fetch resolves), `deployed_at` is UTC to the second, and `storage_wired` says whether this run gave its applications a storage identity. The write is a narrow read-modify-write of the record; a failure warns and does not fail the deploy.

A manifest's name is held to the same namespace rules as `--namespace` (2026-11-12): a DNS label, never a provider-managed `kube-` namespace, and never `farcast-system`, which holds the instance's own components. One named otherwise is refused after the read, before anything is built or deployed. A namespace this machine recorded under a different repository is refused, naming both, unless `--replace-repository` is given: two repositories in one namespace is the second replacing the first's egress entries and reusing its applications' storage scopes. Repositories are compared ignoring only a trailing `/` and `.git` (and a credential, should an older record hold one). A repository URL with a user name or credential in it is refused before anything is read — it would be written into the fetch Job and into this record, which every `world` prints — and the refusal names the URL without it; a private repository's read-only credential goes through `--git-secret`. With `--namespace` the refusal comes before anything is read; without it the namespace is the manifest's name, known only after the in-instance read — which has run and billed — so the refusal comes then, before anything is built, written to the egress policy, minted or applied, and says so. The record belongs to this machine: a deploy from another machine is not caught, and a namespace with no record here — every namespace deployed before this — is accepted by the first run from any repository.

### Golden vectors

Every JSON shape the app decodes has a vector under `internal/cli/testdata/`: `world/` (one per case — healthy, never connected, no kernel, tunnel down, a sealed replica, cost reached with stopped apps, a stop the kernel recorded beside one it did not, a stale stop record for an app running again, the instance floor, a checkpoint as a version 1 kernel wrote it, a stale checkpoint, an unmetered namespace, checkpoint version skew, two namespaces sharing an app name with bare-keyed spending and with namespaced spending, one host with mixed evidence, drift, an unattributed denial, a host name carrying a bidi override and a C1 control, the host cap exceeded, keepers healthy/expired/unseen, release incomplete, nothing read, a violation from a removed app, rows from `farcast-system`, section messages that name accounts, a connected instance with no reader, a namespace the reader may not read beside ones it read, and the `not_found` error envelope), `instances/` (an empty list, and a listing with unreadable records, one instance whose reader is granted and one with none), `version/` (`{version, commit}`, the two fields the app reads), `kinds/` (the closed set of error kinds, in order), and `app/` (`argv.json`, the app's three command lines, which a test runs against the CLI). Beside them, `plan/` *(since ADR 0023 M2.6, built 2026-11-16, not walked)* holds the plans of `kernel confirm`, `kernel meter` and `reader grant`, and the `plan_changed` error envelope; and, since 2026-11-17, `connect`'s first deploy (both carried images pushed, the identity minted), `redeploy`'s (with `--embedded`, over images an earlier farcast deployed) and `build`'s (a named builder); and, since ADR 0023 M2.6c (2026-11-17), `kernel deploy`'s, `storage deploy`'s over the recorded bucket, `storage key pin`'s (the pin created) and `storage key rotate`'s with the keyholder deployed (the hold and final pins over the new key's placeholder id). Those four read a fixed fake cluster as the reader, which holds the fixture's namespaces, a fixed `farcast-system` uid and no pin yet; the storage ones read a fixed keyring, whose key material is a counted test pattern trusted nowhere, and `TestPlanVectors` checks no vector holds any of its keys. The app decodes none of them yet. The commands make them themselves, against the world vectors' fixture record given a creation time, with the farcast stamp and the clock fixed. `connect`'s and `redeploy`'s are made by a release farcast at the vector stamp, carrying fake components, against fake registry answers and a stand-in installer key, the record edited for each; `redeploy`'s over a fixed P-256 CA certificate, public test data. No plan holds a key. They are produced in Go, and `./check.sh` does not copy them to FarSightKit until ADR 0021 step 7.1. The `world` and `instances` vectors are schema 2 since ADR 0023 M2.4, whose `gcloud_mismatch` envelope vector was deleted with its kind. World vectors come only from the pure builder fed literal inputs; the others from running the command against a written config directory. A test rebuilds each one and fails on any byte difference; `FARCAST_UPDATE_VECTORS=1 go test ./farsight/cli/internal/cli/ -run Vector` rewrites them, and the diff is then reviewed like code.

### The no-cost rehearsal

`farcast-rehearsal` is the instance the app reads from Finder before it reads a live one ([ADR 0021](../../docs/adr/0021-farsight-native-client.md) decision 9, "Walked before it is relied on", and Verification 5). It is `cmd/farcast-rehearsal`, built as `./bin/farcast-rehearsal`, and never part of `farcast`: a fake API server must never be in the product binary. It costs nothing, touches no cloud, and listens only on 127.0.0.1. *(Since ADR 0023 M2.4, built 2026-11-15, its cluster is a local API server and token endpoint. Until then it was three fake tools, `kubectl`, `gke-gcloud-auth-plugin` and `gcloud`; a directory one of those harnesses made is refused at start, with `start a new one in a new directory`.)*

- **What it runs.** A local Kubernetes API server and token endpoint (`kube/kubetest`), a real FatLine tunnel and a real Shrike behind it, and two keyholder replicas that answer `GET /v1/state` and refuse everything else. The tunnel and the keyholders are under the instance's own mutual TLS.
  - A state directory holds the instance's record, every name in it a `.invalid` placeholder. Its endpoint is the API server's `127.0.0.1:<port>`, and `cluster-ca.crt` is that server's CA, written at every start. It holds `reader.key` and `reader.crt`, with a reader recorded, uploaded and granted under the loopback name farcast derives (`farcast-reader-<8 hex>@rehearsal.invalid`), and `server_side_apply`. It also holds a writer's key in `credentials.yaml`, which a read must never use. `ca.key` and `keys.yaml` are mode 000.
  - The operator's own `farcast` reads it exactly as it reads a cluster since ADR 0023 M2.4: in-process as the instance's reader, with a token minted at the rehearsal's token endpoint, and the network and seal through the tunnel. The loopback endpoint is what makes that a test path: `farcast` sends a token to a loopback address only when that token was minted from a loopback endpoint, and trusts that address only on its own `cluster-ca.crt` (ADR 0023 decision 2's rule).
  - Its traffic: the shop's `api` reaching its payments host every minute, and the enrolled keeper reading storage's state through the tunnel every ten.
- **It never touches the real gcloud, kube or farcast directories.**
  - Before it writes anything, it refuses a directory that is, holds or sits inside `~/.config/gcloud`, `~/.kube`, this machine's default farcast configuration directory (protected whether or not `$FARCAST_CONFIG_HOME` is set), or a directory `$FARCAST_CONFIG_HOME`, `$CLOUDSDK_CONFIG` or `$KUBECONFIG` names.
  - Directories are compared by what they are on disk, not by how they are spelled. Both sides are resolved through their symlinks, and the parts that exist are matched by file identity, so `/var` and `/private/var`, a symlinked alias, and a macOS firmlink spelling (`/System/Volumes/Data/Users/…` for `/Users/…`) are each one directory. The parts not made yet are compared by name, ignoring case.
  - The one exception is a directory `$FARCAST_CONFIG_HOME`, `$CLOUDSDK_CONFIG` or `$KUBECONFIG` names *inside* a rehearsal that already exists, which is the rehearsal's own. The default farcast directory, `~/.kube` and `~/.config/gcloud` are never excepted.
  - Tests prove it against a fake home under `$TMPDIR`, through `/var`, a symlinked alias and, on macOS, the data volume's firmlink spelling, with the default farcast directory refused while `$FARCAST_CONFIG_HOME` points elsewhere.
- **The cluster answers only the reader, and only `world`'s reads.** A writer's token gets 403 whatever it asks for. The reader gets the reads `world` sends: the labelled namespaces, each namespace's Deployments and StatefulSets, and a ConfigMap in `farcast-system` by name, or a 404 for one it does not hold. Anything else gets 405: a write, a Secret, a log, a list across namespaces, a `continue` or any other query key.
  - Every request the API server and its token endpoint see is one line of `calls.log` in the state directory: `<time> cluster <METHOD> <path>[?<query>] as <reader|writer|none|unknown> | ok`, or `<time> token POST /token as <reader|writer|unknown> | ok`, or either ending `| refused: <reason>`. A keyholder's refusal is a line too. No line carries a body, an assertion or a token, and the API server keeps no log of its own requests.
- **Scenarios.** `farcast-rehearsal scenario --dir <dir> <name>` switches what the next read shows, with no restart:
  - `healthy`, `sealed`, `stale-checkpoint`, `cost-reached`, `at-floor` and `denied` — `cost-reached` stops `web` with no record of why, and `at-floor` has the kernel record stopping both applications and reaching the floor. In both, `web` ran hot for the sixteen hours before it was stopped, so spending stands over the $50 limit, as a real kernel's does when it acts;
  - `slow-cluster`, where the API server and its token endpoint hold every answer 25 seconds, past `world`'s 20-second read deadline;
  - `token-refused`, where the token endpoint refuses every assertion: the cluster sections read `credential_refused`;
  - `unauthorized`, where every read answers 401, the read after a fresh token too;
  - `forbidden`, where the kernel's checkpoint and the egress policy answer 403: spend and policy read `forbidden`, and apps still read;
  - `reader-missing`, where `reader.key` is moved aside to `reader.key.away`, and back on any other scenario: the cluster sections read `credential_missing`, and `instances` says `key_missing`;
  - `tunnel-down`, where FatLine's tunnel stops listening within a moment, and listens again on the same port on any other scenario, while the cluster stays up.

  `signed-out` and `identity-mismatch` were retired with the gcloud identity: every command that takes a scenario name refuses them, and names `token-refused` and `forbidden`.

  The kernel's ledger is anchored to the rehearsal's start, never the calendar, so spending reads split, confirmed and expected, on any day of a month. The kernel's level is its own assessment of that ledger against the limit, never set by hand. A rehearsal lives 25 days; after that, every read answers 500 and says it expired.

  A scenario name given where a command goes, as in `farcast-rehearsal sealed`, starts nothing. The harness says it is a scenario, and prints the `scenario` command that switches to it, with the directory filled in when `--dir` was given.
- **Settings.** Its banner prints the two paths the app's Settings record, `farcast` and the farcast configuration directory, and the instance's reader state as the app's Check shows it: `reader granted`, or `reader key missing` in `reader-missing`.
- **Restart.** Stopped with Ctrl-C, it starts again with `--dir <dir>` on the same tunnel and cluster ports, with its own leaves and a new `cluster-ca.crt`, so nothing in the app's Settings changes.
- **`summarize`.** `farcast-rehearsal summarize < world.json` prints only a document's shape: each section's outcome and kind, counts, and the alert kinds. Every word it prints is a number or a value from a closed set, so it never prints a name, host, repository, commit, replica, message, title or time of day. It is the walk's scrub tool for a live read.

The walk is [the Phase 7 Connected-view runbook](../../docs/runbooks/phase-7-connected-view.md).

## Diagnostics

Diagnostic logging is for the operator debugging the CLI, not for command output. It is plain text on **stderr**, gated by `--verbose`, built on the standard library's `log/slog` with a text handler. It is intentionally **not** the farcast SDK logger: the SDK is for in-instance applications and emitting JSON to stdout, which is the opposite of what an operator CLI wants. Keeping them separate also keeps the root module free of a dependency on the `sdk/go` module.

## Internal architecture

A command is a small, self-contained unit. The router parses global flags, finds the command, and hands it an `Env`:

```go
// Command is one farcast subcommand.
type Command interface {
	Name() string                 // e.g. "version"
	Synopsis() string             // one line, shown in `help`
	Usage() string                // full usage, shown in `help <command>`
	SetFlags(fs *flag.FlagSet)    // register command-specific flags
	Run(ctx context.Context, env *Env, args []string) error
}

// Env is the ambient context handed to every command.
type Env struct {
	Out, Err io.Writer       // stdout, stderr
	In       io.Reader       // stdin (for interactive commands later)
	Printer  *output.Printer // renders results per the --output mode
	Config   *config.Config  // loaded local configuration
	Verbose  bool
	Log      *slog.Logger    // diagnostics → Err
}
```

- **Routing** (`cli.go`): split global flags from the command and its flags, look the command up in the registry, dispatch. Unknown command or bad usage → exit `2` with a help hint. A root `context.Context` is cancelled on `SIGINT`/`SIGTERM` so long-running commands (logs, run) can shut down cleanly later.
- **Output** (`output.go`): a `Printer` with a `Mode` (human/JSON) and the stdout writer. Commands return a typed result value; in JSON mode the printer marshals it, in human mode it calls the value's `Human(io.Writer)` renderer. One place owns formatting, so every command is automatically scriptable.
- **Config** (`config.go`): path resolution, `0700`/`0600` enforcement, typed load/save.
- **buildinfo** (`buildinfo.go`): `Version`/`Commit`/`Date` set via `-ldflags -X`, with a `runtime/debug.ReadBuildInfo` fallback.

`main.go` stays a thin shell: build the `Env`, call `cli.Main`, `os.Exit` with the returned code.

## Testing & guardrails

Per [AGENTS.md](../../AGENTS.md) and [ADR 0002](../../docs/adr/0002-backend-language-strategy.md), the CLI is held to the same bar as every Go module: `go test -race`, `go vet`, and `golangci-lint`, with tests beside the code.

- **Routing** — known command dispatches; unknown command and bad flags exit `2`; `--help`/`-h` at both levels.
- **`version`** — human and JSON output, with `buildinfo` values injected.
- **Output** — human vs JSON rendering; error formatting in both modes; exit codes.

- Commands are tested by calling `Run` with buffers for `Out`/`Err` — process spawning only where a subprocess is what is tested: the certificate-root children of `TestCertFileVariablesCannotAddARoot`, `sh -n` over the reader's Cloud Shell scripts, and cluster's tests of kubectl's built environment, which run the test binary as kubectl. *(Since ADR 0023 M2.5 also a `/bin/sh` fake kubectl that records a writer's `Apply`, in cluster's tests and in cli's `TestAWriterOpensAsTheInstallerKey`; it has run on macOS only.)* *(Since ADR 0023 M2.6, 2026-11-17, also the succeeding `/bin/sh` stand-in kubectl above, in `TestConfirmWritesThePlannedDocumentsExceptTheirSecrets`.)* *(Until ADR 0023 M2.4 also cli's and the rehearsal's fake kubectl, auth plugin and gcloud, which went with the gcloud guard.)*

## Decisions

The choices made for the scaffold, with rationale:

1. **CLI framework: standard library (not Cobra).** The CLI holds cloud admin credentials, so minimizing the dependency/supply-chain surface is a security decision, consistent with the SDK's stdlib-only stance and FarCast's first pillar. The command tree is shallow enough (mostly `farcast <verb>`, with `storage` as the only two-level case) that Cobra's machinery isn't required. Trade-off: help rendering is hand-written and there is no shell completion yet. If the command tree grows unwieldy, adopting Cobra later is mechanical.
2. **Config format: YAML.** Reuses the already-vendored `goccy/go-yaml` (no new dependency) and keeps config operator-readable and consistent with the manifest.
3. **Single module.** The stray per-module `go.mod` files were removed; the CLI lives in the root module per the repository convention, and only `sdk/go` remains a separate module.
4. **The cost limit is mandatory, enforced at install (1.3).** No default, no "unlimited", no skip — recorded into instance metadata at creation, so "no instance without a limit" is structural. Enforcement is TechnoCore's (4.1); `install` owns capture.
5. **Record before create (1.3).** Local state is written before `CreateCluster`, so an interruption never leaves an untracked, billable cluster — a cost-pillar safety property, at the cost of a possible orphaned *record* (which `release` cleans up).
6. **Dependency-free interaction & health check (1.3).** Prompting and TTY detection use the standard library (`os.ModeCharDevice`), not a prompt library; the health check uses the GKE management API plus the IAM-gated DNS endpoint ([ADR 0004](../../docs/adr/0004-private-control-plane.md)), not a vendored Kubernetes client or a raw public-IP dial — consistent with principle 1, since every dependency is attack surface against stored credentials.
7. **Release initiates the cloud delete before removing local state (1.4).** The inverse of record-before-create: `release` issues the cluster delete first and removes the local record only after the cloud accepts it, so a failed delete call never strands a billable cluster with no way to find it again (deletion itself completes asynchronously — see 1.4's known limitation). `DeleteCluster` is idempotent, so re-running `release` converges. The interactive confirmation requires **retyping the instance name** — stronger than install's y/N, because the operation is destructive; `--yes` skips it.
8. **`connect` deploys via kubectl subprocess, not a vendored Kubernetes client (2.3, [ADR 0006](../../docs/adr/0006-connect-bootstrap-kubectl.md)).** Consistent with principle 1 and decision 6: a vendored `client-go` is a large supply-chain surface against stored cloud credentials. The stored kubeconfig already drives the control plane through an **external auth-plugin exec** (`gke-gcloud-auth-plugin`), so shelling to `kubectl` for the one-off FatLine bootstrap adds an external-tool runtime dependency, not a Go dependency — the same line the kubeconfig already draws. The exec boundary is injectable, so orchestration is unit-tested without a cluster.
9. **`connect` mints the data-plane identity locally; the CA private key never leaves the machine (2.3).** The per-instance CA is the sovereign data-plane trust root ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)). `connect` mints it (and the operator client + FatLine server leaves) on first connect and pushes only the CA *certificate* + server leaf+key to the cluster Secret — never the CA key. The default carrier is the public mTLS-gated load balancer; its **standing ~$18/mo cost is confirmed against the cost limit** before provisioning (the carrier was ratified at 2.3 per [ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)).
10. **The instance owns its image registry, and the default image reference moves there (1.3/2.3, [ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)).** Kubernetes has exactly one way to put code into a Pod — the kubelet pulls from a registry — so the only open question is *whose*. A Sofmon-published default (`ghcr.io/sofmon/farcast/fatline:<version>`, the first 2.3 cut) made every instance's network boundary depend on a third party's artifact feed: a standing central dependency, and a supply-chain injection point aimed at FatLine itself. It is **deleted, not deprecated**. `install` creates `farcast-<instance>` in the instance's own project and region and grants that cluster's nodes a repository-scoped `roles/artifactregistry.reader`; `connect` re-ensures it and defaults `--fatline-image` to `<prefix>/system/fatline:<version>`; `release` deletes it. Deploys **pin the digest**, never the tag, so whoever can write the tag cannot redirect a running Deployment. The capability is an *optional* Planck interface (`RegistryProvider`) promising an image-path prefix plus a credential — not "one repository object" — so a second cloud can realize the same contract without a caller changing.
11. **The CLI builds and pushes FarCast's own images itself — no container engine, and no new dependency (2.3, [ADR 0007](../../docs/adr/0007-instance-owned-image-registry.md)).** FatLine's image is a static Go binary laid onto a digest-pinned distroless base, with no `RUN` steps to execute, so there is nothing an engine would do here that the CLI cannot: the compile shells to the **Go toolchain** (already a prerequisite for having a `farcast` binary at all, behind an injectable seam), and image assembly and push ride an OCI-distribution client the CLI owns, on `net/http` + `encoding/json` + `archive/tar` + `compress/gzip` + `crypto/sha256`. Requiring docker or podman would add an engine — on macOS, a Linux VM — to a tool whose premise is a small trusted base, and would write a push credential for the instance's registry into some other tool's credential store. Vendoring a registry library instead would have dragged seven to nine modules, docker's config and credential-helper packages among them, into the binary that holds the operator's cloud credentials and the instance's CA key. Both were measured and rejected: this feature ships with the vendored module count **unchanged at 31**. The cost lands as code FarCast owns — wire-protocol correctness is now ours to test, which is what the `oci` package's `httptest` suite and its opt-in run against a real registry are for. *(ADR 0023 M1, built 2026-11-13.)* A release farcast no longer compiles at all: it pushes the layers it carries, checked against the digests compiled into it, and builds only for `--source`; a farcast built from source builds a missing image as before. So Go is no longer a prerequisite for a release farcast, and the decision's "already a prerequisite for having a `farcast` binary at all" holds only for one built from source.
12. **Changing a connected instance's FatLine is its own top-level command, and it is consent-gated, not cost-gated (2.3).** Three choices, taken together:
    - **A verb, not a flag.** `farcast redeploy <instance>` rather than `connect --redeploy`. It matches the `farcast <verb>` tree this CLI is built on (decision 1 — `storage` is the only two-level case) and keeps the two concerns legible: `connect` opens the tunnel, `redeploy` changes what runs inside it. A flag would have made the bootstrap-or-not branch inside `connect` a third mode of one command that already has two.
    - **It re-applies even when the image digest is unchanged.** The failure that motivated it was a workload-*template* defect — FatLine's mTLS `Secret` mounted root-only, unreadable by the non-root container — with the image byte-identical, so a redeploy that no-opped on a matching digest would be useless for exactly the case it exists for. When the digest has not moved it says so plainly rather than implying something did.
    - **A consent gate, not a cost gate.** The load balancer already exists and a redeploy makes nothing new billable, so re-prompting the ~$18/mo confirmation ([ADR 0005](../../docs/adr/0005-fatline-data-plane-ingress.md)) would attach the money prompt to an operation whose answer is always "nothing changes" — the way a gate that guards real money gets trained into a reflex. The prompt shows the change instead (old digest → new, or template-only); `--yes` waives it and a non-interactive session without `--yes` is a usage error, exactly as connect's gates behave.

    It never re-provisions the carrier and never re-mints the CA — those stay `connect`'s, because the carrier is the standing cost and the per-instance CA is the sovereign trust root, and neither should move because someone rolled a new image. The reason this is a command at all is that the alternative was `release` plus a reinstall: destroying an entire instance to patch its network boundary is the price that makes an operator postpone a security fix.

13. **Storage is operator-side, addressed scp-style, and its destructive edges are gated on data rather than configuration (3.3).** Four choices that hang together:
    - **It needs no cluster and no tunnel.** `farcast storage` runs against the recorded bucket with the stored cloud credentials and the local keyring, so it works on an instance that was never `connect`ed — and it is why 3.3 is not blocked on 3.2's in-cluster key-delivery ADR. Serving storage to in-cluster applications is a different problem with a different trust model.
    - **`<instance>:<key>`, with ambiguity as a usage error.** One addressing form for the whole group, in the shape operators already have from `scp`. When both readings of an operand are genuinely available it refuses rather than guesses, because a wrong guess either uploads the wrong bytes or overwrites the wrong file, and neither is recoverable.
    - **`key` is the CLI's only third level**, because the noun changes: the data verbs address objects in a bucket, the key verbs address the file whose loss destroys all of them. Flattening would seat a keyring verb next to `storage rm` in tab completion, and `storage rotate` would read as though it rotates data.
    - **`release` refuses while the bucket holds data, and `--delete-data` is a scope flag, not a consent flag.** Stored data is the first thing in FarCast that derives from nothing, and soft delete is off by design. The gate is **data-triggered**, so an empty bucket produces no gate at all and a test instance behaves exactly as it does today; and `--yes` never implies `--delete-data`, so the confirmation an operator clicks through daily cannot destroy the irreplaceable thing. The count comes from `datasphere.BucketUsage` over the `Provider` with **no keyring**, because an operator who has lost `keys.yaml` still needs to be able to stop paying — and a gate built on what the keyring can *name* would announce an empty bucket while billable ciphertext sat in it.
