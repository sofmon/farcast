## Context

AGENTS.md says the provider is blind to *content*. Workload logs broke that.

Planck created every cluster with `Name`, `ResourceLabels`, `Autopilot`, `InitialClusterVersion` and `ControlPlaneEndpointsConfig`, and nothing else. It never set `LoggingConfig`, so GKE's default applied: **system logs and workload logs**, both ingested into the project's Cloud Logging. GKE's "system" means its own namespaces (`kube-system` and similar). `farcast-system` is not one of them. So every line FatLine, Shrike, the kernel and the keyholder wrote to stdout, and every line every application wrote, was copied into a service the provider runs and indexes, in plaintext, and kept for the project's retention period.

`farcast logs` never needed any of that. It runs `kubectl logs`, which reads the file on the node through the API server. *(2026-11-15: since [ADR 0023](0023-one-download-farcast.md) M2.4 it reads the same file through the same API server, in-process; decision 6's note.)* Nothing in the repository reads Cloud Logging or Cloud Monitoring, and no client for either is vendored. The export was a default nobody asked for, and no FarCast function depended on it.

The finding came from the Phase 5 Session A walk (2026-11-10). The walk record does not carry its evidence yet. The read-back below makes the next walk produce that evidence.

What GKE's public documentation says (Sources). Where it contradicts itself, both sides are given, and the next walk decides.

- **Logging.** SYSTEM is required on every cluster type, and it includes Kubernetes **Events** (*About GKE logs*). `NONE` is not supported on Autopilot, and an empty component list means "disable all logging" (API reference). Whether Autopilot lets WORKLOADS be left out is **not settled by the documentation**:
  - *For.* *About GKE logs* calls WORKLOADS "on by default but optional for all cluster types". The Autopilot create command's own `--logging` example is `--logging=SYSTEM` (*create-auto*).
  - *Against.* The same *About GKE logs* page offers system-only capture to Standard clusters, and only exclusion filters to Autopilot. The Autopilot/Standard comparison lists workload-level logs as *pre-configured* on Autopilot, a term it defines as features you "can't change or disable". The logging troubleshooting page says the cluster's logging setting is "always enabled by default on Autopilot clusters and can't be disabled". The Autopilot overview lists workload logs among what Autopilot collects automatically.

  So Autopilot may reject a SYSTEM-only create. It may accept the create and read back WORKLOADS. Or it may read back SYSTEM_COMPONENTS and collect workload logs anyway. Decision 1 handles the first two. Only the walk's namespace-scoped count (Verification, step 2) can rule out the third. **Until that walk, system-only logging on Autopilot is unverified.** *(2026-11-24, ADR 0023's M2 walked: verified on that walk: SYSTEM_COMPONENTS read back, and 0 `k8s_container` entries from FarCast's namespaces since install (Verification steps 1 and 2).)*
- **Control-plane logs.** API server, scheduler and controller-manager logs are each optional, and the Autopilot create default is `SYSTEM,WORKLOAD`. There is one documented exception. Since 2024-02-20, observability packages "including control plane logs" are on by default for new managed GKE Enterprise clusters (release notes). A cluster in a project with GKE Enterprise may therefore read back control-plane components that FarCast did not ask for. The documentation does not say whether fleet registration alone does the same.
- **Audit.** Admin Activity audit logs are always on and cannot be disabled. They sit in the `_Required` bucket for **400 days**, which the project can neither shorten nor empty. Data Access audit covers reads, including `kubectl logs`, and status writes (below), and it is off by default. An organization or folder can turn it on for every project beneath it, though, and a project cannot turn off what a parent turned on.
- **The audit policy.** Requests on Secrets, ConfigMaps and TokenReviews are logged at **Metadata** level: verb, object name and namespace, caller, source IP, user agent, time and response code, with no body. Writes on the built-in API groups are, in general, logged at **RequestResponse**, with the full object. The kubelet's updates to `pods/status` are logged at **Request** level: the status it sends, without the response. GKE writes creates, updates and deletes to Admin Activity. It writes gets, lists and status updates to Data Access, and its own example of a Data Access write is updating Pod status.
- **Metrics.** On Autopilot, system metrics cannot be disabled, and they are not billed. They carry the `kubernetes.io/` prefix: per-container CPU, memory and restarts, and per-Pod network bytes, labelled by namespace, Pod and container. Managed Service for Prometheus' managed collection is on by default on Autopilot from 1.25 and cannot be turned off. **Managed collection is not idle without a user `PodMonitoring`.** GKE's own metric packages ride it and are on by default for new clusters:
  - **Kube state metrics**, on Autopilot from 1.27.4-gke.900. They record each Pod's phase, each container's readiness and waiting reason (CrashLoopBackOff, ImagePullBackOff), and Deployment and StatefulSet replica counts, sampled every 30 seconds. The package skips system namespaces. GKE lists those only for logging (`kube-system`, `gke-system` and three others), and FarCast's namespaces are not on that list, so these metrics are expected to cover them (Verification, step 1). Kube state metrics are billed per sample ingested.
  - **cAdvisor/Kubelet**, from 1.29.3-gke.1093000. They record per-container CPU, memory, filesystem and network usage, sampled every 30 seconds.
  - **JobSet**, from 1.32.1-gke.1357001. FarCast renders no JobSet.

  GKE's metrics page describes turning these packages off (`--monitoring=SYSTEM`). It makes Autopilot exceptions only for system metrics and for `NONE`. That is documented, not tried (decision 3).
- **Retention.** `_Default` keeps 30 days unless the project changes it (1–3650). `_Required` keeps 400 days, fixed. Managed Service for Prometheus data, which covers every package above, is kept for **24 months**, and so are most GKE system metrics. The data is downsampled as it ages and ends as one point every 10 minutes. Only deleting the project guarantees that metric data goes sooner.

## Decisions

**1. Every cluster is created with system-only logging, and install fails unless it reads back that way.** `buildCluster` sets `LoggingConfig{ComponentConfig{EnableComponents: [SYSTEM_COMPONENTS]}}` unconditionally. There is no knob, because there is no FarCast cluster that ships its applications' output. Once the cluster reports Running, the adapter reads its logging config back. If the config is not exactly SYSTEM_COMPONENTS, `CreateCluster` returns an error naming this ADR. That covers WORKLOADS, a nil or absent config (the provider default), an empty list, a control-plane stream nobody asked for, and a value the vendored client does not know. `farcast install` already turns that error into an instance recorded as `error`, with a pointer to `farcast release`. **An instance whose cluster reads back with workload logs is never reported as installed.**

The check also applies to a cluster that already existed under the name. `install` refuses an instance it already records, so an existing cluster there is one FarCast lost track of, and it is not adopted as private on trust.

**If Autopilot refuses system-only logging, every install fails.** That is the cost of failing closed, and it is stated here up front. A create that Autopilot rejects makes no cluster: install records `error`, and `farcast release` clears the record. A create that Autopilot accepts but that reads back WORKLOADS leaves a running, billable cluster. Install records it as `error`, and the operator must release it. Either way, nothing installs until the operator chooses a fallback. This ADR takes neither of them:
- *A project-level Log Router exclusion on the instance's container logs.* This is weaker. Exclusion filters are applied after the Logging API has received the entries, so the provider still receives every line before it discards it. The exclusion is also standing project configuration (decision 4).
- *GKE Standard*, which can turn workload logs off, at ADR 0003's cost.

The read-back is the provider's word about its configuration, not about its behaviour. A cluster that reads back SYSTEM_COMPONENTS and still collects workload logs passes it. Verification step 2 checks the behaviour.

**2. No convergence path.** An `UpdateCluster` with `DesiredLoggingConfig` exists in the API, but nothing reaches it. `install` refuses an existing instance, and no live instance predates this ADR: p5a was released, and farcast.one is pending. Whether Autopilot accepts that update is unverified. Adding an unverified mutation to the cloud for a case that cannot occur would be the wrong trade. An instance from before this ADR is reinstalled, not repaired.

**3. Monitoring is read back, not pinned.** FarCast does not set `MonitoringConfig`. Autopilot's system metrics and managed collection cannot be turned off. The adapter reads the monitoring config back alongside logging, and the opt-in integration test logs it, so the walk records what is on. The read-back is expected to list GKE's packages, with components such as POD, DEPLOYMENT, STATEFULSET, DAEMONSET, HPA, STORAGE, CADVISOR, KUBELET and JOBSET. That is recorded, not enforced. Those packages report on FarCast's namespaces, and the provider keeps the data for 24 months (*What the provider still sees*). FarCast renders no `PodMonitoring` or `ClusterPodMonitoring`, so no application's own metrics endpoint is scraped. The translator test that pins the kinds an application deployment renders enforces that, and that is all it keeps out.

*Open decision: pinning the packages off.* GKE's metrics page describes turning the packages off and makes no Autopilot exception for them. By that page, creating every cluster with monitoring pinned to SYSTEM_COMPONENTS would stop the readiness, phase and usage series for FarCast's namespaces, and system metrics would remain. This ADR does not do it. It is untried on a live Autopilot create, and a rejection would fail every install, which would compound decision 1's open question. The operator decides it after the next walk has shown what Autopilot does with logging. Auto-monitoring is opt-in and left unset. *(2026-11-24, ADR 0023's M2 walked: the walk showed it and recorded the monitoring read-back (Verification step 1). The decision is the operator's and is not made.)*

**4. The mandatory remainder is disclosed, not fought.** System logs and Events, Admin Activity audit and system metrics stay, and so, for now, do the metric packages (decision 3). FarCast installs no project-level log exclusion, no sink and no bucket change. Each of those is standing project configuration that outlives the instance, touches every other cluster in the project, and cannot reach `_Required` anyway.

**5. Release names what outlives it, with dates, and deletes nothing there.** `farcast release` gives approximate dates for what the provider keeps:
- the audit log, until about 400 days from now;
- system logs and Events, until about 30 days from now under the default retention;
- metrics about the instance's Pods, until about 24 months from now.

For an instance not recorded as system-only, release also says that the applications' output may be among the logs. The output says the dates are approximate: audit entries expire 400 days after *each* write, a project may have changed `_Default`, and metric points expire 24 months after each sample. Ingested entries cannot be deleted per cluster. The `stdout`/`stderr` log names are project-wide, so deleting them would destroy other clusters' logs. For metric data, only deleting the project guarantees it goes sooner.

**6. `farcast logs` stays on kubectl.** It reads the node's file through the API server. Its usage text now says where logs live and who can see them, rather than claiming nothing collects them. *(2026-11-13: [ADR 0023](0023-one-download-farcast.md), accepted that day, changes this at its M2: `logs` reads the pod `log` subresource with an in-process client, still through the provider-run API server. ADR 0023 restates the caller (a read-only service account instead of a human email) and the user agent, and M3b adds where a device subject is logged. Until M2 lands, `logs` runs `kubectl` as here.)* *(2026-11-15: M2.4 did this for `logs`. It reads the pod `log` subresource in-process as the instance's reader service account, still through the provider-run API server, and runs no kubectl. Audit entries, where Data Access audit is on, then name that service account as the caller instead of a human email, and `farcast` as the user agent. Not yet walked: no audit entry of it has been seen.)* *(2026-11-16: at 2482810 GKE's DNS endpoint refuses the token `logs` minted, scoped to `userinfo.email` alone, as ADR 0023's [probe walk](../runbooks/adr-0023-m2-probe-walk.md) found, so there `logs` reads nothing from GKE. A fix built later that day mints it with `cloud-platform` and `userinfo.email`, so a leaked reader token works for every Google API the reader's IAM allows, not only the cluster. It is not walked.)* *(2026-11-24, ADR 0023's M2 walked: under [B] no reader exists, so `farcast logs` returned no lines and was refused for want of the reader's key; `logs` as the reader is not walked.)*

## What the provider still sees

Stated plainly, because this ADR would be an overpromise without it:

- **System logs and Events, about 30 days.** These carry application names, image references, scheduling, scaling, OOM kills, probe failures and restarts. A keyholder replica passes its readiness probe only when it is unsealed. So a sealed replica's failed probes are Events here, and they date the seal.
- **Admin Activity audit, 400 days, beyond release, undeletable.**
  - *Metadata only* for ConfigMaps and Secrets: FatLine's egress policy, the key pin, TechnoCore's cost ledger (`technocore-ledger`), and the `<app>-egress` Secrets. The provider sees the name, the time and the caller of every write, and never the content. That is enough to read the kernel's write cadence. *(2026-11-12: the ledger's checkpoint also records the kernel's cost stops and the instance floor ([ADR 0009](0009-technocore-kernel-and-cost-metering.md) decision 2's note), and is written at once after a stop, or when the floor is first reached, as well as every five minutes. So its cadence now dates each cost stop too — which the scale-down's own full-body entry, below, very likely already does — and the moment the floor is first reached, which follows from the scale-downs, the limit in the kernel's Deployment arguments and the provider's own bill. The usage profiles' ConfigMap is not written off its schedule.)* It also dates each `run`, key rotation, pin change and keyholder deploy, which are the commands that write the pin. And it tells the operator apart from in-cluster service accounts. *(2026-11-15, [ADR 0023](0023-one-download-farcast.md) M2.5: those commands now create and replace the pin in-process as the instance's installer service account, so the pin's entries name that account as the caller, not the operator's gcloud identity. Their other writes, kubectl's applies, keep the gcloud identity until M2.7. Not walked: no audit entry of it has been seen.)* *(2026-11-18, ADR 0023 M2.7, built, not walked: every write farcast makes now names the installer's service account as the caller, with `farcast` as the user agent; no write keeps the gcloud identity.)* *(2026-11-20, ADR 0023 M2.8, built that day, not walked: a private repository's Git credential Secret is among them. `farcast git-credential set` writes it into `farcast-system` and `git-credential rm` deletes it, each as the installer's service account. Each is an Admin Activity entry at Metadata level: the Secret's name, the time and the installer as the caller, never the username or the token. No audit entry of it has been seen.)* `storage unseal` and a keeper's re-seed write no Kubernetes object themselves. When one brings a sealed replica back to serving, its timing reaches the provider through readiness: the Events above, the metrics below and, very likely, the endpoint updates in the next bullet, which last longest. *(2026-11-24, ADR 0023's M2 walked: in Admin Activity, 67 entries on `farcast-system` ConfigMaps carried no request or response body: the pin, the egress policy and `technocore-namespaces` written by the installer, the ledger and the profiles by the kernel's ServiceAccount. The installer's Secret writes had no body either. Its ConfigMap and Secret entries name its account, with the user agent `farcast,gzip(gfe)` [inf: Google's front end appends `,gzip(gfe)`], and are the only entries of farcast's own applies GKE kept (Verification step 7's note).)*
  - *Full bodies* for every create, update and delete on the built-in API groups, which covers Deployments, StatefulSets, Jobs, Pods, Namespaces, Services and NetworkPolicies. That includes application names, images and resource requests, and very likely TechnoCore's resizes and cost-stop scale-downs. It also includes literal values in two Jobs, and in the Pods created from them:
    - the fetch Job's `FARCAST_REPO`, `FARCAST_REF` and `FARCAST_MANIFEST` environment;
    - the Kaniko build Job's arguments: `--context=git://<repository>#<commit>`, carrying the exact approved commit, then `--context-sub-path`, `--dockerfile` and `--destination`. *(2026-11-24, ADR 0023's M2 walked: kept, in the build Pods' creates: 4 carried `--context=git://…#<commit>`, the two runs' four builds. No build Job's create entry was kept.)*

    So the provider keeps which repository and commit every build came from. The git token is a `secretKeyRef` and stays at Metadata level. *(2026-11-18, ADR 0023 M2.7, built, not walked, and inferred: farcast's applies are now PATCH requests with an apply-patch body, under the field manager `farcast`. `farcast migrate` makes one JSON PATCH per object it rewrites, so Admin Activity keeps the date an instance was migrated, by the installer's account, for 400 days, at Metadata level for its Secrets and ConfigMaps. The kernel's writes carry `fieldManager=technocore`.)* *(2026-11-20, ADR 0023 M2.8, built that day, not walked: the Secret that `secretKeyRef` names is written by `farcast git-credential set`, in place of a hand-made `kubectl create secret`. Its write, and `git-credential rm`'s delete, preconditioned on the uid it read, are Admin Activity entries at Metadata level as the installer, as the bullet above says.)* *(2026-11-20, ADR 0023 M2.9a, built 2026-11-20, not walked: `farcast migrate` is removed, so farcast makes no JSON PATCH, and Admin Activity keeps no date of a migration.)* *(2026-11-24, ADR 0023's M2 walked: the provider keeps them still, but not through farcast's applies. Admin Activity held no entry by the installer on FarCast's Namespaces, Deployments, StatefulSet, Services, NetworkPolicies, ServiceAccounts, Roles, RoleBindings or Jobs. A probe in the walk applied two throwaway ServiceAccounts server-side: GKE kept the apply sent with a JSON body and dropped the one sent with a YAML body (why is Google's), and farcast sends YAML (`kube/apply.go`). So the full bodies above do not hold for farcast's own writes. The content reaches Admin Activity through the controllers: 24 Pod creates in `farcast-system` and `sdk-demo`, by the Job, StatefulSet and ReplicaSet controllers, each with a body, the build Pods' carrying the commit and the applications' carrying their images by digest. The fetch Pods' 2 creates carry a body too; that it holds the fetch environment is [inf]. The kernel's resizes, JSON merge patches, were kept with a body.)*

    Very likely it also dates every readiness transition, per replica: every seal, every keeper re-seed, and every unseal that brings a sealed replica back to serving. An unseal pushed to a replica that is already serving (the remedy when replicas hold the newest keys without using them yet) changes no readiness, so it is not among them. The `datasphered` data Service is the one Service that gates on readiness: it has no `publishNotReadyAddresses`. So each time a keyholder replica turns Ready or NotReady, the control plane's endpoints controllers update that Service's Endpoints and EndpointSlice in `farcast-system`, moving the replica's address, with its Pod named in `targetRef`, between ready and not ready. The audit policy leaves such updates unlogged only in `kube-system`. An update to the core group's Endpoints is an Admin Activity entry with its full body: a 400-day record of each transition, at the moment it happened, finer than the downsampled metrics below. EndpointSlices are in `discovery.k8s.io`, which is not among the policy's listed groups, so their entries would be at Metadata level, which still carries the time. This is inferred from the documented policy and the deploy code. Verification step 8 checks it. *(2026-11-24, ADR 0023's M2 walked: confirmed, and the EndpointSlices are not at Metadata level. After a seal and an unseal Admin Activity held 16 updates, each with a request and a response body: the data Service's Endpoints, 4, and the EndpointSlices of `datasphered`, `datasphered-status` and `datasphered-unseal`, 4 each. Each body carries every replica's address, node name, Pod name, namespace and uid, its ready and serving conditions, hostname and zone (Verification step 8).)*
- **Pod status, if Data Access audit is on.** By the audit policy, the kubelet's `pods/status` updates go to Data Access, which is off unless the project or a parent turned it on. Where it is on, they carry:
  - every keyholder replica's readiness transitions and restarts;
  - the termination messages FarCast reads results from: the fetch report's commit and manifest digest (or, when the manifest is missing, the repository, path and commit) and the build's image digest.

  Verification step 6 checks where they land. *(2026-11-24, ADR 0023's M2 walked: no `pods/status` entry in Admin Activity for `farcast-system` or `sdk-demo`; Data Access was off in the project and its organization (Verification step 6).)*
- **Metrics, up to 24 months.** System metrics record per-container CPU, memory and restarts and per-Pod network bytes, by namespace, Pod and container. By the documentation, GKE's default packages record the following for FarCast's namespaces (Verification, step 1, shows it):
  - Pod and container names, each Pod's phase, and each container's readiness and waiting reason;
  - Deployment and StatefulSet replica counts;
  - per-container CPU, memory, network and filesystem use.

  They are sampled every 30 seconds, downsampled as they age, and outlive release. A keyholder replica is ready exactly when it is unsealed. So the readiness series is a record of when each replica was sealed, at 30-second resolution for its first week. It dates every seal, every keeper re-seed, and every unseal that brings a sealed replica back to serving; an unseal onto a replica already serving changes no readiness and shows in none of it. *(2026-11-24, ADR 0023's M2 walked: shown: Metrics Explorer held a kube state readiness series for each `datasphered` replica, each named by its Pod's name and uid (Verification step 1).)*
- **Container logs on the node's disk.** Standard kubelet rotation keeps about 10 MiB × 5 files per container. They are removed with the Pod and destroyed with the node. Autopilot nodes are the provider's. In ADR 0008's terms this is *protected by the provider not looking*, not *hidden*.
- **`kubectl logs` passes through the provider-run API server**, which terminates TLS. Nothing records the read unless Data Access audit is enabled. *(2026-11-15: since ADR 0023 M2.4 `farcast logs` reads it in-process as the reader, through the same API server, which sees and may record it the same way.)*
- **Each operator read mints a token at Google** *(2026-11-15, ADR 0023 M2.4)*. `world`, `ps`, `costs`, `usage` and `logs` read the cluster as the instance's reader service account. Its token is held in memory only, and each command is one process, so each of them mints one at `oauth2.googleapis.com` first. Google can therefore time each operator read, by the reader's account and the source address, and records each key's last use (inferred, not walked). The gcloud auth plugin these reads used before kept its token in a file, and minted about once an hour (inferred). *(2026-11-15, ADR 0023 M2.5: a writing command that reads the cluster or writes the pin — `connect` when it deploys, `redeploy`, `build`, `run`, `kernel deploy`, `storage deploy`, `storage key pin` and `rotate` — first mints the installer service account's token the same way, one per process. That tells Google the installer's account, the time and the source address. Its reads, where Data Access audit is on, and its pin writes name the installer's service account as the caller. Its applies keep the gcloud identity, and the plugin's own token, until M2.7. `kernel meter`, `kernel confirm` and `reader grant` make no in-process call as the installer, and mint nothing as it. Not walked.)* *(2026-11-16, ADR 0023's [probe walk](../runbooks/adr-0023-m2-probe-walk.md): GKE's DNS endpoint refuses these tokens as built at 2482810, scoped to `userinfo.email` alone, with 401. So there the reads and writes above are refused against GKE, until `cloud-platform` comes back (the next note). The walk's mints with that scope succeeded: the cluster endpoint refuses, not Google's token endpoint. So a command refused this way has still told Google of its mint (inferred). With `cloud-platform`, a token held in memory reaches any Google API the account's IAM allows, not only the cluster: for the reader its read-only role, for the installer everything it holds.)* *(2026-11-16, the fix, built after the walk and not walked: each of these tokens is now minted with `cloud-platform` and `userinfo.email`. It is tested against a local API server only.)* *(2026-11-17, ADR 0023 M2.6, built, not walked: plans mint too. A plan that reads the cluster, `kernel deploy`'s, `storage deploy`'s, `storage key pin`'s, and `storage key rotate`'s with a keyholder deployed, mints the reader's token, so Google can time each such plan by the reader's account, as it times a read, and the API server sees the reader as the caller of its reads. - **The cluster's etcd** holds every Pod's status too, readiness and termination messages included. It is already named in DataSphere's section, and the control plane itself in ADR 0004.

What the cluster is configured not to send to the provider's logging is the stdout and stderr of FarCast's own components and of every application. Install reads that configuration back. That Autopilot honours it is unverified until the next walk (Context, *Logging*). *(2026-11-24, ADR 0023's M2 walked: it honoured it there: 0 `k8s_container` entries from `farcast-system` and `sdk-demo` since install, while `kube-system`'s were present (Verification step 2).)*

## Consequences

- **Log history ends with the Pod.** A deleted, evicted or rescheduled Pod takes its logs with it, and a busy container keeps only about 50 MiB. Shrike and the cost meter never depended on Cloud Logging, so no FarCast function changes. An operator who wants durable logs has to build them (Revisit triggers).
- **If Autopilot refuses system-only logging, nothing installs** until the operator chooses a fallback (decision 1). Failing closed is meant to work this way.
- **The strict read-back can fail an install whose workload logs are off.** A project with GKE Enterprise may get control-plane logs by default. A logging component newer than the vendored client reads back as unknown. Both are refused (Revisit triggers).
- **Cost.** The kernel's `expected` meter never modelled Cloud Logging ingestion, which is billed above a per-project monthly free allotment. The ingestion this removes was a cost the meter did not see. The ingestion that remains (system logs, Events, audit) is still unmodelled, and so are the metric packages' samples, which are billed per sample ingested. Nothing measures how large either is at FarCast's scale.
- **The audit log is a second etcd, and it outlives release.** The DataSphere README's etcd line says rotation frequency is visible. Through the audit log it stays visible for 400 days after the cluster is gone. By the documentation, the metric packages keep each keyholder replica's readiness, and so its sealing and unsealing, for 24 months. Very likely the audit log keeps each of those transitions too, through the data Service's endpoint updates, for 400 days. *(2026-11-24, ADR 0023's M2 walked: both shown: a readiness series for each keyholder replica, and the Endpoints and EndpointSlice updates after a seal and an unseal, with full bodies, in Admin Activity (Verification steps 1 and 8).)*
- **A known leak class: plain values in a workload spec.** Anything put as a literal in a Job's or Deployment's `env` or `args` is kept by the provider for 400 days, in the workload's body and in each of its Pods'. Two instances are known:
  - the fetch Job's repository, ref and manifest path;
  - the Kaniko build Job's `--context=git://<repository>#<commit>` and the arguments beside it.

  The follow-up, recorded separately and not done here, must cover both. The fetch values move into a Secret. Kaniko's context has to come from a Secret-backed env or file, not from an argument. Until it lands, the repository URL and the full commit stay in every build Job's body for 400 days. Image names carry the application names and a 12-character commit as well. *(2026-11-24, ADR 0023's M2 walked: it stays in the build Pods' create entries: farcast's apply of the Job left none of its own, and 4 of the 5 build Pods' creates, the two runs' four builds, carried the commit; W4.12's extra build named a branch, not a commit [inf].)*

## Alternatives considered

- **A Cloud Logging exclusion filter on the instance's cluster.** Rejected. It is project configuration that outlives the instance, and it cannot touch `_Required`. Exclusion filters apply only after the Logging API has received the entries, so the provider still receives them. It remains the weaker fallback if Autopilot refuses decision 1.
- **Deleting the sink, or the `stdout`/`stderr` logs, at release.** Rejected. Those names are project-wide, so deleting them destroys other clusters' logs. The `_Required` bucket cannot be emptied.
- **Converging existing clusters with `UpdateCluster`.** Rejected for now (decision 2).
- **Pinning `MonitoringConfig`.** Deferred to an open decision (decision 3).
- **An opt-in for workload logging.** Not offered. If one is ever added, it is a privacy-lowering flag behind its own confirmation, recorded in the instance metadata and named again by `release`.
- **GKE Standard.** It can turn off more, but at ADR 0003's cost and operational price. It stays the home for a later Standard/Spot hybrid, and it is the other fallback if Autopilot refuses decision 1.

## Revisit triggers

- A live run shows GKE echoing more than SYSTEM_COMPONENTS, rejecting the create, or ingesting `k8s_container` entries from FarCast's namespaces while it reads back SYSTEM_COMPONENTS. The fallbacks in decision 1 are then the operator's to choose. *(2026-11-24, ADR 0023's M2 walked: not met on that walk.)*
- The project has GKE Enterprise (or, undocumented, fleet registration). GKE may then enable control-plane logs by default, and the strict read-back fails an install whose workload logs are off. That failure is closed and correct until someone decides whether control-plane logs are acceptable.
- GKE reads back a logging component that the vendored client does not know. The client's enum stops at `KCP_HPA`, and the API already has `KCP_VPA`, which would read back as unknown and be refused. That also fails closed. The fix is updating the client, not loosening the check.
- The next walk records the monitoring read-back. Then the operator decides whether to pin the metric packages off (decision 3). *(2026-11-24, ADR 0023's M2 walked: recorded 2026-11-24 (Verification step 1). Whether to pin the packages off is the operator's, and is not decided.)*
- An operator needs log history beyond a Pod's life. The answer is in-instance retention: encrypted, through DataSphere, under the operator's keys. It is never the provider's logging.
- Autopilot allows system metrics or managed collection to be turned off.
- A second cloud provider (8.1). Its defaults get the same read-back before its first install.
