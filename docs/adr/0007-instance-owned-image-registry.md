# ADR 0007 — The Instance Owns Its Image Registry

**Status:** Accepted (2026-08-25); implemented the same day. Two mechanisms were refined at implementation under the inspect-the-diff clause — Artifact Registry's admin calls are issued as direct REST over the vendored auth stack (Google's generated client would have added a module via `gensupport`), and the image data plane is a stdlib OCI client rather than a vendored registry library. Measured result: **zero new modules**, 31 before and after.

**Date:** 2026-08-25

**Relates to:** Closes the image-distribution gap [ADR 0005](0005-fatline-data-plane-ingress.md)/[ADR 0006](0006-connect-bootstrap-kubectl.md) left open — `farcast connect` deploys a FatLine *image*, but nothing defined where that image lives. Extends the CLI's minimal-dependency stance ([`../../farsight/cli/README.md`](../../farsight/cli/README.md) decisions 6/8) and Planck's provider abstraction ([`../../planck/README.md`](../../planck/README.md)). Pre-figures Phase 4's app builds ([`../../PLAN.md`](../../PLAN.md) 4.2/4.3) and Shrike's per-app attribution (4.4). Serves the two pillars of [AGENTS.md](../../AGENTS.md).

---

## Context

Kubernetes has exactly one native way to put code into a Pod: the kubelet pulls an image from a registry. So *some* registry is structural — the decision is **which registry, who populates it, when, and from what**.

As shipped at 2.3, `farcast connect`'s default `--fatline-image` is `ghcr.io/sofmon/farcast/fatline:<version>` — an unpublished, Sofmon-controlled distribution point. That default quietly contradicts the **zero-central-dependency** principle: it makes every instance's security boundary depend on an artifact feed a third party (Sofmon) controls, exactly the phone-home shape FarCast rejects. Meanwhile Phase 4 looms: each app's Containerfile must be built by *something* and the result put somewhere the cluster can pull — the registry question returns, bigger, in 4.2/4.3.

The operator's stated principle (2026-08-25): *nothing the instance runs should come from outside the operator's control; the Git repository is the source of truth.* The repo cannot be the *runtime* source (kubelet pulls registries, not repos), but the principle has a faithful translation: **everything the instance runs is derived from Git by the operator's machine and hosted in infrastructure the instance itself owns.**

### The decision space

- **R1 — a central published image (the 2.3 default).** Convenient, conventional — and a standing central dependency plus a supply-chain injection point aimed at the network boundary itself. Contradicts the principle; rejected.
- **R2 — build in-cluster at deploy time.** "From source on the spot" sounds sovereign but isn't: it needs a builder (kaniko/BuildKit — images from a third-party registry), running inside the *blind* cloud, with source uploaded to it — and it still pushes to a registry for the kubelet to pull. More moving parts, slower `connect`, and it inverts the trust model: the operator's machine — which already holds the CA key and the cloud credentials — is FarCast's sovereign build anchor. Rejected for system images; whether apps warrant a builder inside the operator's *own* instance is the 4.2-era question decision 5 defers.
- **R3 — commit the image into Git.** The repo already contains everything the image *is* (Containerfile + vendored source; the build is hermetic: `-mod=vendor`, CGO off, `-trimpath`, no network fetch). Committing the blob stores a derivable artifact, bloats history with every release, and creates a second copy of the truth that can diverge from the source beside it. Rejected.
- **R4 — the instance owns a registry in its own project; the operator's machine builds from Git and pushes to it.** No third party in the runtime path, teardown scoped to the instance, and the same mechanism Phase 4 needs anyway. **Chosen.**

## Decision

1. **Every instance owns an Artifact Registry repo: `farcast-<instance>`, Docker format, in the instance's region, in the instance's project.** It is created at `farcast install` (the registry is instance identity, like the cluster and the CA — and it must exist *before* the first image push, which precedes the first `connect`), via an idempotent **ensure** that `connect` also calls defensively. A registry failure at install is reported, not fatal — it must never strand a cluster created seconds earlier, and connect's ensure converges it. That defensive ensure also covers instances installed before this ADR, where a permission-denied ensure (the stored installer SA predates the new role) degrades to a warning on paths that need no registry access, rather than breaking working reconnects. `farcast release` deletes the repo unconditionally and idempotently (absent-repo-is-success), under the same delete-before-local-cleanup discipline as the cluster ([CLI README](../../farsight/cli/README.md) decision 7). Images are derivable from Git, so nothing sovereign is lost at teardown.

2. **The CLI reaches Artifact Registry over its REST API behind a Planck capability interface — never by shelling to `gcloud`, and with token minting and refresh left inside the vendored `cloud.google.com/go/auth`.** [ADR 0006](0006-connect-bootstrap-kubectl.md)'s anti-`client-go` math inverts here: the gRPC `apiv1` client would have added thirteen modules, and Google's *generated* REST client (`google.golang.org/api/artifactregistry/v1`) — expected to be free, since its module is already vendored — turned out to add one: every generated client imports `internal/gensupport`, which imports `github.com/google/uuid` in non-test code. Measured, not assumed. With the zero-new-module budget binding, the seven admin calls (create, inspect and delete the repository, poll the resulting operation, get and set the repository's IAM policy, and look up the project number) are issued directly with `net/http` + `encoding/json`. A 409 `ALREADY_EXISTS` on create is what makes ensure idempotent — and it is followed by an inspect, because `release` deletes this repository and everything in it, so a name collision must prove it is FarCast's before being adopted. This is narrow, and it is *not* the thing [ADR 0006](0006-connect-bootstrap-kubectl.md)'s K3 rejected: K3's objection was re-owning credential and auth-refresh semantics, and those stay wholly inside the vendored `cloud.google.com/go/auth` — no hand-rolled JWT, signing, or token refresh. `gcloud` would be a brand-new external-tool dependency the CLI has never had, and authenticating it with the instance's SA key mutates the operator's global gcloud state — entanglement the isolated per-instance credential store exists to prevent. The registry surface is an **optional Planck capability** (type-asserted `RegistryProvider`: ensure the registry, delete it, mint a short-lived credential for it — digests, layers and pushes stay in the CLI's OCI client), kept deliberately minimal so an ECR adapter can realize the same contract at 8.1 — the contract is "a per-instance image-path prefix", not "one AR repo object" (ECR's repo-per-image model realizes the prefix differently).

3. **Pull authorization is an explicit, repo-scoped grant.** At ensure time, the CLI binds `roles/artifactregistry.reader` **on the one repo** to the cluster's node service account (today the Compute Engine default SA; a dedicated per-instance node SA is recorded as follow-up hardening). Never rely on the default SA's automatic project `Editor` grant — it is org-policy-conditional (Google recommends disabling it), so pulls that lean on it work by accident and break on hardened projects. The installer SA gains exactly one new role, **`roles/artifactregistry.admin`** — the narrowest predefined role that can create repositories (`repoAdmin` cannot; create-on-push exists only for legacy gcr.io-mapped repos, not standard `pkg.dev` ones) — and it covers repo create/delete *and* repo-level `setIamPolicy`, so the CLI's credential never holds project-IAM power. Discovering the node SA's email needs the project *number* (the cluster object reports the SA as the literal `default`): the adapter looks it up through Cloud Resource Manager (`projects.get` — a permission the installer SA's `container.admin` already includes), by the same direct-REST path as the Artifact Registry calls, and returns it for recording in `metadata.yaml`. The [Phase 1 runbook](../runbooks/phase-1-validation.md) is updated accordingly: the SA step adds the role, and the API-enablement step adds `artifactregistry.googleapis.com` and `cloudresourcemanager.googleapis.com`.

4. **The operator's machine is the only build anchor for system images, and the default image ref moves to the instance.** `--fatline-image` defaults to `<region>-docker.pkg.dev/<project>/farcast-<instance>/system/fatline:<version>` computed from stored metadata (tag from the CLI's build info); the ghcr.io default is **deleted, not deprecated**. `connect` preflights the ref over the OCI distribution protocol (the registry host, not Artifact Registry's admin API): if present, it resolves and deploys **pinned by digest** (`image@sha256:…`, recorded in `metadata.yaml`) — a registry-write compromise cannot swap the image under an existing Deployment; if absent, it offers to build-and-push in place (decision 5) — or, without a Git checkout, fails naming exactly what is missing.

5. **Building and pushing FatLine is baked into the CLI — no container engine on the operator's machine** (operator challenge, 2026-08-25, replacing an earlier docker-subprocess draft). FatLine's image needs no Containerfile *execution* — it is a static, cross-compiled Go binary laid onto a digest-pinned base, with no `RUN` steps. So the CLI does the whole thing natively: the compile shells to the **Go toolchain** (the one tool a source-built `farcast` already guarantees — `go.mod` floors the version, and an exact `toolchain` pin is added at implementation, auto-fetched through the checksum-verified Go module proxy where the local toolchain is older; behind an injectable Runner seam), and image assembly + push ride a **stdlib OCI-distribution client** the CLI owns (`net/http` + `encoding/json` + `archive/tar` + `compress/gzip` + `crypto/sha256`): fetch the digest-pinned base manifest and config, copy its layers, append the binary layer, push to the instance registry — authenticated with a short-lived OAuth2 access token (60-minute validity) minted in-process from the stored SA key. No docker, no podman, no daemon, no VM, no credential written into any tool's store — **and no new module in the dependency tree**. Vendoring a registry library (`go-containerregistry`, `regclient`) was measured and rejected at implementation under this ADR's own inspect-the-diff clause: both drag ~7–9 third-party modules — including docker's config/credential libraries — into a binary whose entire non-Google third-party surface is one YAML library, to serve a case that needs none of what they handle (one digest-pinned base, one target registry, small blobs, our own auth). Owning ~600 auditable lines is the better trade for a credential-holding binary; the risk is wire-protocol correctness, met with `httptest`-level tests and the Part B run. The alternatives fail the no-new-tools bar (nothing beyond what a source-built `farcast` already requires): docker/podman-as-CLI need an engine (on macOS, podman *is* a Linux VM via `podman machine`); buildah/libpod-as-library — podman's build core — is Linux-only and cannot live inside a darwin binary; the stdlib client chosen here is what remains once both are ruled out. `connect`'s preflight-miss becomes self-healing: with the Git checkout present it offers to build-and-push in place (confirmed interactively; `--yes` in automation). This narrows the 4.2 question rather than answering it: *system* images never need a builder, but app Containerfiles execute arbitrary `RUN` steps and do need one — that choice (a local engine where present, an in-instance builder, a ko-style path for Go apps) is deferred to its own 4.2-era decision, and the registry contract here (paths, auth, digest pinning) is independent of which builder populates it.

6. **The image path convention is fixed now.** FarCast's own images live under `system/` (`system/fatline` today; `technocore`, `shrike`, `datasphere` later); Phase 4 app images under `app/<deployment>/<app>:<git-sha>` (manifest top-level name / `apps[]` entry — mirroring the K8s namespace/name shape Planck 4.2 generates). The path mirrors the per-app identity that 4.4's attribution actually keys on (`Event.Tenant`/`Event.App`, fed by the per-app SPIFFE SAN `farcast://<instance>/app/<name>` — see the [FatLine](../../fatline/README.md)/[Shrike](../../shrike/README.md) READMEs), so image provenance joins cleanly with Shrike's violation reports. The `system/` prefix costs one path segment today and prevents a rename migration (and an operator app named `fatline`) later.

7. **The build itself becomes content-addressed — and smaller.** The canonical (in-CLI) build has exactly **one** external input: the distroless base, pinned by digest as a recorded constant (`gcr.io/distroless/static:nonroot@sha256:…`) — the `golang` builder image vanishes from the canonical path entirely, since the compile runs on the operator's toolchain against vendored source. Digest pinning turns gcr.io from a trusted authority into an untrusted transport — the same move `vendor/` makes for Go modules — and bumps are deliberate, reviewed commits (pin the manifest-list digest; keep the source tag in a comment). `fatline/Containerfile` is retained as an independently-verifiable *reference* build, both of its bases digest-pinned and its builder kept in step with `go.mod`'s toolchain, rather than as the canonical path. Full bit-for-bit reproducibility is a stated goal, not a gate.

8. **Cost is surfaced, not gated.** AR bills storage (~$0.10/GiB/month beyond a free tier); FatLine's image is ~20 MB and same-region pulls are free, so the registry is effectively $0 today and cents with Phase 4 apps — orders of magnitude under the ~$18/mo LB that earns [ADR 0005](0005-fatline-data-plane-ingress.md)'s confirmation gate; gating cents would train the operator to click through the gate that matters. `connect`'s cost block (and `farcast costs`, 4.3) name the registry as a line item. (The free tier is per *billing account*, not per project — still immaterial at this scale.) The registry contract includes a retention policy (AR cleanup policies: keep-most-recent-N per path, keep rules winning over delete; a static policy cannot see what is deployed, so the CLI maintains a keep rule naming the currently-deployed version, rewritten at each deploy); it is dormant until `run` starts pushing per-commit tags and is wired up at 4.3. AR's per-repo *immutable tags* option was considered and left off: deploys pin digests anyway, and mutable tags keep the rebuild-and-repush development loop workable.

## Consequences

**Positive**

- **Zero central dependency restored end-to-end:** no Sofmon-published artifact, no third-party registry in the runtime path; the trust chain is Git repo → operator's machine → the instance's own registry → the instance.
- Phase 4 inherits a *tested* mechanism instead of building one: the ensured registry, the path convention, the repo-scoped grant (already covering every future app image — zero new IAM per app), in-process token auth, and digest-pin-at-deploy.
- Teardown symmetry: `release` removes cluster + carrier + registry; post-teardown standing cost is zero.
- Digest pinning at both ends (base images in, deployed image out) makes the entire artifact chain content-addressed.

**Negative / constraints**

- The installer SA's grant grows by `roles/artifactregistry.admin` (AR-confined; still no project-IAM power) — a Phase 1 runbook change operators must re-apply.
- **The dependency tree does not grow at all** — measured at implementation (31 vendored modules before and after): both the admin calls and the data plane are stdlib over the already-vendored auth stack. The cost lands instead as code FarCast owns: an OCI-distribution client whose correctness is ours to test and maintain (and to revisit if a second registry flavour ever strains it).
- The repo-scoped reader grant lands on the *shared* default compute SA, so other same-project workloads using that SA could pull — accepted for the instance-per-project posture, closed properly by the dedicated per-instance node SA (follow-up hardening).
- First bootstrap is `install` → `connect`: on a preflight miss, `connect` builds and pushes in place given the Git checkout and Go toolchain — both already prerequisites for having a `farcast` binary at all (source-first distribution is the model). Without them, it names exactly what is missing.
- `release`'s known accept-vs-complete gap (GKE delete) now sits beside a second resource; the repo delete is a short long-running operation the CLI waits to completion; a failure between the two deletes must keep the local record so a re-run converges.

**Per-module implications**

- **Planck** — gains the optional `RegistryProvider` capability (GKE adapter: Artifact Registry REST over the vendored auth stack); node-SA discovery lives here (the cluster object reports `default`; the email derives from the project number looked up via Cloud Resource Manager).
- **FarSight CLI** — `install`/`connect`/`redeploy`/`release` call ensure/preflight/delete; owns the image build/push seam (Go-toolchain Runner + the stdlib `internal/oci` data plane, in-process token auth); `--fatline-image` default recomputed; deploys by digest. (`farcast redeploy` — replacing a connected instance's FatLine workload — landed just after this ADR and reaches the registry through the *same* resolution code as `connect`, so ensure, preflight, build-and-push and the digest pin cannot drift between the first deploy and every one after it. One rule is redeploy's alone: an explicit `--source` forces a rebuild, since the tag derives from the CLI's version and a preflight against a connected instance would otherwise resolve the image already there.)
- **FatLine** — the canonical image is assembled by the CLI (single pinned distroless base); `fatline/Containerfile` becomes the digest-pinned reference build; the deploy renders `image@sha256:…`.
- **Shrike / TechnoCore (later)** — 4.4 attribution reads the `app/<deployment>/<app>` path; 4.1 cost breakdown gets registry storage as an attributable line.

### Phasing

**Now (pre-Part B, so the validation exercises the real flow):** ensure-at-install + defensive ensure-at-connect, delete-at-release, repo-scoped node-SA grant, instance-registry default ref + preflight + digest-pin deploy, the baked-in build/push (Go-toolchain Runner + the stdlib `internal/oci` client), an exact `toolchain` pin in `go.mod`, the Containerfile's digest pins and reference-build framing, runbook updates (installer SA role + API enablement in Phase 1; [Part B](../runbooks/phase-2-validation.md)'s B1 replaced by the in-CLI flow, with the B2/cost/troubleshooting references that assume the manual docker flow updated alongside). **Deferred:** the app-image builder decision (4.2-era ADR), retention-policy wiring (4.3), per-instance node SA (hardening), ECR realization (8.1).
